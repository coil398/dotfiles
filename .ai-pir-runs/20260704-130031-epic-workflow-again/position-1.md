## 3. 段階的推論（第一原理レンズ: 「動くか不明なランナー用の配管を先に作るか」の裁定）

### 3-1. epic の load-bearing 構造の同定

epic 全体の依存グラフを第一原理で描くと、**P5 は他のすべての投資の上流にある単一の gate 仮定**である:

```
P5（L1 が pir2 を自律完遂できる）
 ├─ 真なら: W2 §1-1 起動契約（L1 に渡す7項目）が意味を持つ
 │          W2 §1-2 return 契約（L1 が返す見出し）が意味を持つ
 │          B 恒久（Fable5 対立#1）が維持される
 └─ 偽なら: A-lite（L0 直接統率）へ再設計。§1-1 は死蔵、§1-2/§1-3/台帳は
            「L0 が L2 を直接検証する」形へ**再標的化**（全損ではないが形が変わる）
```

**自己点検（飛躍がないか）**: 「P5 偽なら W2 全損」は言い過ぎ。§1-2 return 契約・§8 台帳・§1-3 検証パイプラインは A-lite でも約半分が転用可能。よって正確な主張は「**P5 の真偽は W2 の設計形状を大きく変える。形状が未確定の配管を先に固めるのは、安価な形状確定手段があるなら非合理**」である。

### 3-2. 情報価値（VoI）の第一原理計算

投資判断の定石: gate 仮定の検証が (a) 安価で (b) 結果が投資判断を実際に変え (c) 事前確率が真に不確実なとき、検証を投資に先行させる。

- **(a) 安価か**: G0 は attended 1時間程度・ビルドゼロ。W2 は SKILL.md/epic-planner の大規模改訂＋L0 検証パイプライン＋台帳スキーマの実装（deepthink 3 の実測で「prose 指示駆動の fix は可謬・fix にフィクスチャが要る」ことが分かっており、W2 も相応のフィクスチャコストを伴う）。**桁が違う**。
- **(b) 判断を変えるか**: 3-1 のとおり P5 偽なら W2 は形状ごと変わる。真なら W2 は de-risk されて設計どおり進む。**どちらの結果でも次の行動が変わる＝gate の定義そのもの**。
- **(c) 不確実か**: 未実証（F2）。外部知見は両方向（「LLMs Get Lost in Multi-Turn」の 39% 劣化 vs. pir2 SKILL.md がそもそも「メイン Claude が手順として追う」ために書かれた手続き文書で L0 は日常的に完遂している事実、model=opus 固定）。事前確率は真に中間。

∴ **第一原理の裁定: W2 を P5 検証に先行させるのは投資順序として非合理。「動くか不明なランナー用の配管を先に作る」は、配管の形状が P5 の真偽に依存する以上、順序が逆**。

### 3-3. 「計器なしの1回は学びゼロ」との整合（本推論の最大の内部障害）

deepthink 1/Fable5 は「計器なしの1回は観測無価値」を確立した。素の dry-run はこれに違反しないか。**しない**。理由は2段:

1. **W1 がまさにその計器で、既に nested run の内部に同乗している**。Fable5 が W1 を「まず作る（素の pir2 の資産にもなる）」と最優先配置した投資回収設計の帰結として、nested pir2 が 6-1/6-3 を実行すれば `verify-*.list` という**物理痕跡**がサブ RUN_DIR に残る。実行しなければ**物理不在**が残る。どちらでも決定論的に事後監査できる（deepthink 3 の可監査性3段チェーンの第①段が epic 境界にもそのまま適用される）。
2. **§1-3 の C 経路（git 集合照合）は W2 の実装を待たずに L0 が手動で運転できる**。pre/post の `git diff --name-only`＋untracked リスト取得はアドホック bash 数行であり、Fable5 自身が「純 bash・完全に可能」と実現可能性を確定済み。W2 が自動化するものを、1-unit なら人間つき L0 が手で回せる。

∴ G0 は「無計器の裸ラン」ではなく「**手持ち計器つきラン**」。deepthink 1 の原則は違反されず、むしろ「W1 を最初に作った理由」がここで初めて回収される。

**自己点検**: この論理は「1-unit・直列・attended」でのみ成立する。並列や多ノードでは手動計器が破綻する（それこそが W2 の存在理由）。よって G0 の構成制約は論理の成立条件そのものであり、後述の安全構成と一体。

## 4. 反証・対立仮説の検討（レッドチームレンズ: 3案の steelman と衝突の裁定）

### 4-1. steelman (ii)「W2 を先に作る」— 最強の反論

> **S-ii**: (1) exp-02 の裁定どおり、W2 なしでは G1 の観測4項目のうち②しか完全観測できず、対立#1 の U1 判定トリガ（契約不履行の連続2回）は「契約」が無いと発火し得ない。今回しても設計上の G1 は成立せず、W2 後にもう一度回すことになる＝二度手間。(2) より鋭く: **素の起動プロンプトには B1〜B3 の既知ギャップがあるため、素のランで L1 が失敗しても「P5 が偽」なのか「プロンプトが不備」なのか切り分けられない＝交絡した偽陰性**で、W2 §1-1 はまさにその交絡を除去する装置である。(3) W2 は P5 偽でも半分生き残る（3-1）ので全損リスクは誇張。

**応答**:
- (1) へ: G0 は G1 の代替だと主張しない（後述 4-4 の裁定）。二度手間のコストは attended 1時間の再ラン。W2 を先に作って P5 が偽だったときのコストは W2 ビルド全体の手戻り。**非対称性はラン再実行側が圧倒的に安い**。
- (2) へ（最重要・部分譲歩）: 交絡の指摘は正しい。ただしその処方は「W2 を実装する」ではなく「**起動プロンプトを丁寧に合成する**」である。B1（`$ARGUMENTS`＝Ti と読み替えよ）・B2（references ポインタも追って Read せよ）・B3（PROJECT_MEMORY_DIR の値渡し）は、L0 がラン時にプロンプトへ足す**数行のオペレータ・パッチ**であり、契約スキーマ設計・検証パイプライン実装・台帳実装（＝W2 の実体）とは別物。SSOT は編集しない。合成した起動プロンプト全文を EPIC_RUN_DIR に記録して再現性を担保する。これで G0 の測定対象は「**まともなプロンプトの下での P5**」になる — そもそも誰も「不備プロンプトでの L1」を運用する計画はないのだから、これが意思決定に効く correct な測定対象である。
- (3) へ: 認める。だからこそ主張を「W2 全損」でなく「形状未確定の配管の先行固定は非合理」（3-1）に置いている。半分生き残るとしても、どの半分かは P5 の結果で決まる。

**裁定**: S-ii は G0 の設計を改善した（プロンプト・パッチと記録の要求）が、順序の結論は覆せない。

### 4-2. steelman (iii)「保留」

> **S-iii**: 本セッションだけで3件の実失敗を観測したプラットフォーム状況で、未検証機構（epic）の上に未検証機構（6-3・実行0回）を積んだ初回ランを回すのは時期尚早。まず通常の pir2 run で 6-3 を数回自然発火させ、6-3 の挙動を既知量にしてから epic を回せば、nested run での異常が「6-3 のバグ」か「ネスト効果」かを綺麗に帰属できる。

**応答**:
- 帰属の綺麗さという価値は認める。だが (1) 6-3 は must-fix #1 でフィクスチャ2本を同一コミットに内包済みで、機構レベルは検証済み。残る未知は「実 run で L0 が 6-3 を実行するか」（観測項目 b）であり、これは**G0 でも観測できる**（nested pir2 の「L0」は L1 なので、G0 は観測項目 (b) の L1 版を初回供給する）。異常時も「L1 が reference を Read したか・pre-set を書いたか」の痕跡でほぼ切り分く。(2) 3件の実失敗は epic 機構外の共通層事象（F5）で、「epic を回すな」ではなく「あらゆるランに監査痕跡を」の論拠。それは W1＋手動計器で満たされる。(3) deepthink 3 の保留棄却基準「待って得られる追加情報がない」に照らすと、保留が生む情報（通常 pir2 での 6-3 成熟）は**受動的・別トラック**で、epic の判断をブロックする理由にならない — 通常運用の pir2 は G0 と無関係に走り続け、その観測は勝手に貯まる。(4) 保留の隠れコスト: 3本の deepthink と W2 設計がプラットフォーム更新（v2.1.x の速い churn）に対して陳腐化していく。
- **取り込む妥当な核**: G0 は「フレッシュなセッション・クリーンツリー」で行う（本セッションのような戦傷まみれの context で回さない）。これは S-iii の懸念の正当な部分の反映。

### 4-3. steelman (i) 自身への最強反論（自案を甘やかさない）

> **S-i-против**: n=1 の成功は P5 を証明しない。成功しても「たまたま自明タスクで通った」だけかもしれず、G0 PASS を過大評価して W2 をスキップしたり fan-out を解禁したりする anchoring が起きる。

**応答（設計で吸収）**: G0 の PASS が**ライセンスする範囲を事前に固定**する — PASS は「P5 が反証されなかった。W2 投資を解禁」のみを意味し、G1 のスキップ・fan-out 解禁・契約省略は一切ライセンスしない。この事前宣言を position に埋め込む（本節がそれ）。逆に FAIL は α/β を診断分類してからのみ効力を持つ（後述 6-3）。n=1 の限界は「P5 の証明」でなく「投資 gate の通過判定」という弱い主張に切り詰めることで正直に扱う。

### 4-4. 中心対立の裁定: 「予備観測」か「最高情報価値の gate 検証」か

exp-02 の「W2 なし dry-run は設計 G1 の代替でなく予備観測」と、「P5 は epic の gate 仮定だから素の dry-run は投資判断を gate する最高情報価値の検証では」の対立は、**観測対象の取り違えを解けば両立する**:

- exp-02 が正しいこと: このランは **G1 ではない**。G1 の固有目的（Fable5 契約への遵守測定・U1 トリガの発火判定）は契約が存在しないと原理的に成立しない（F3）。
- 対立側が正しいこと: このランは「予備」でもない。**結果がロードマップを分岐させる（W2 へ進む / A-lite 再設計へ折れる）以上、意味論は gate である**。
- **裁定＝命名で解消**: このランを **G0（P5 ゲート・投資判断ゲート）** として移行パスに正式挿入する。G1（契約遵守ゲート）は W2/W3 後に温存。「G1 の劣化代替を先食いする」のではなく「G1 から P5 成分を切り出して前倒しする」。これで exp-02 の裁定を一切否定せずに (i) を採れる。

### 4-5. 「今の epic は素の版で穴があるから回すな」への応答

指摘される穴3つを機序で個別に裁く:

| 穴 | 発現条件 | G0（完全直列・1-unit）での帰結 |
|---|---|---|
| HANDOFF 競合（F4） | **並列**: 2つ以上の L1 が同一 `handoff.md` を同時 Write/削除 | 書き手が1体しか存在しないため**発現しない**。ただし**直列でも残る亜種**が1つある: 過去セッションの stale な `handoff.md` が残存していると L1 の RESUME_MODE 判定が誤発火する。→ プレフライトで `.ai-pir-runs/handoff.md` の不在確認（あれば退避）を必須化。反論の正当な核はここに取り込む |
| 共有ツリー汚染（F4） | **並列**: 時間的に重なる複数書き手の git diff 相互混入 | 書き手は L1 系1本のみ。L0 は run 中ファイル編集をしない（attended の自己規律）ため**発現しない** |
| CLAUDE.md 継承不明（F6 B4） | 層を問わず常在 | **リポジトリを壊す危険ではなく、ランの品質が落ちる可能性**。そしてこれ自体が G0 の観測項目（継承シグナルの実測）。最悪ケースでも「劣化が痕跡から検知され、必要なデータそのものが得られる」 |

∴ 「穴があるから回すな」は並列 fan-out に対しては全面的に正しく、**直列 1-unit に対しては stale-handoff プレフライト1点を除いて当たらない**。確信度: 高（3つとも発現機序が「≥2 の同時アクター」または「品質劣化どまり」に分解できるため）。

### 5-1. 本セッション3失敗の epic ネストへの波及（頻度と検知性）

### 5-2. 安全な最小構成（具体・rubric #4）

1. **フレッシュな対話セッション**で実行（本セッションの続きで回さない）。attended 必須（P6）。
2. **プレフライト（アドホック bash・SSOT 編集なし）**: ① `git status --porcelain` クリーン確認＋`git rev-parse HEAD` を記録（baseline）。② `.ai-pir-runs/handoff.md` 不在確認（あれば退避）。③ pre-set: `git diff --name-only`＋untracked 一覧を `pre.list` として EPIC_RUN_DIR に保存。
3. **1-unit・完全直列・fan-out OFF**: epic-planner が2分割以上を返したら Phase 1.5 で 1-unit（許容上限: 直列2）に絞らせる。並列集合は承認しない。

5. **L1 起動プロンプトのオペレータ・パッチ**（4-1 応答の3行: `$ARGUMENTS` 読み替え・references 追跡 Read・PROJECT_MEMORY_DIR 値渡し）＋既存 3-3/3-4 文言。**合成した全文を EPIC_RUN_DIR に保存**（再現性と「素の epic＋文書化された差分」の正直な記録）。

### 5-3. 初回タスク題材（具体・rubric #5）

推奨: **「`bin/count-md.sh`（指定ディレクトリ配下の `.md` ファイル数を出す小ユーティリティ）を新規追加し、`docs/` に使い方メモ1本を追加する」**

- 満たす性質: additive-only（既存ファイル変更ゼロ）／2ファイルで 6-3 の集合照合が非自明に働く（1ファイルだと照合が退化）／tester が実行検証できる（`bash bin/count-md.sh docs` の出力確認）／非 SSOT パス（`bin/`・`docs/` は sync hook の発火対象外、`bin/` は link.sh の `.??*` パターン外でグローバル波及なし）／失敗しても残骸が消しやすい。
- `.sh` 編集で shellcheck-hook（非ブロッキング）が触れるのは許容（むしろ L2 編集への PostToolUse hook 挙動の弱いシグナルになる可能性があるが、L0 から観測できない場合は「未観測」と正直に記録する）。
- 題材の代替は「同性質（additive・2ファイル・実行検証可能・非 SSOT）」を満たせば何でもよい。性質のほうが特定の題材より重要。

### 5-5. 境界条件（この推奨が成り立たなくなる条件）

- attended で回せない（無人運転しか選べない）→ **保留に反転**（フリーズ検知手段が消える）。
- クリーンツリーが確保できない（進行中作業が dirty）→ 実施を延期（集合照合の前提が崩れる）。
