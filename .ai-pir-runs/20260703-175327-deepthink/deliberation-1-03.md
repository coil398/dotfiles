### 段階的推論

#### 段1: 「無応答タイムアウト」は境界で正当な pir2 を殺す
- 飛躍/前提: pir2 duration の分散が大きい（上記推論）。
- 自己点検: 固定 wall-clock T を置くと、T を小さくすれば正当な長時間 pir2（大 diff / review ループ3周 / replan）を誤殺、T を大きくすれば本物のハング（事象Y型）を長時間放置。**duration では「ハング」と「働いている」を分離できない**のが核。
- 帰結: 時間軸でなく**進捗軸**（tool_use が増えているか）で見るべき。「N分間 tool_use ゼロ」= 無応答、「総経過 > T」= 誤検知源。ただし段2の実装制約に当たる。

#### 段2: 進捗軸監視（heartbeat）は Agent ツールの返却モデルに阻まれる
- 前提: Agent はバッチ返却（推論）。実行中の tool_use を親が観測できないなら heartbeat は張れず、粗い wall-clock に退化 → 段1の誤殺境界が再来。
- 自己点検: 実装可能な代替は**事後**判定（サブ完了後に返ってくるメタデータ `tool_uses` / `duration` / `status` を突き合わせる）。事象Y はまさにこの事後シグネチャ（completed かつ tool_uses:0 かつ 4.8秒）で捕まえられる。→ リアルタイム・ハング検知は諦め、**事後ゾンビ検知**に照準を絞るのが実装現実的。

#### 段3: 「tool_uses:0 → 失敗」の単純ルールは推論専任エージェントを誤検知する
- 飛躍点: ゾンビ検知を「tool_uses==0 なら異常」と一般化すると、**推論だけで正当に答えるエージェント**（deliberator / synthesizer / gate / 一部 planner）は tool_use 0 が正常なので誤検知（false positive）。
- 自己点検: 境界は**役割**にある。explorer は Read/Grep ≥1、implementer は Edit/Write ≥1、tester は実行 ≥1 を期待できるが、reasoning 系は 0 が正常。→ 検知は**役割別の下限（floor）テーブル**が要る。
- 二次効果: floor テーブルは新たな同期対象 SSOT を1枚増やす（役割追加のたび更新）。試験段階では「`status:completed` かつ `tool_uses:0` かつ `duration < 閾値` かつ `role∈{explorer,implementer,tester}`」の複合ヒューリスティックが低コスト・低誤検知で妥当。

#### 段4: 捏造検知（事象X）を「どの層に置くか」が二次的に爆発する
- 事象X の核は「完了報告 vs 実ファイルの不一致」。防御は**主張成果物を filesystem（git diff / ls / 行数）で裏取りしてから受理**する「1呼び出し=1検証」の orchestrator 版。
- 境界（層の問題）: L0（epic 本体）が全ネスト pir2 の全 implementer 主張を検証しようとすると、(i) L0 は L2 のファイル操作を直接見られず L1 のサマリしか持たない、(ii) 各層のサマリ化で**生の tool_use 証拠が失われる**。事象X は**ネスト0（単一 pir2）でも**すり抜けた。ネストは捏造の混入面を層の数だけ増やす。
- 自己点検（再帰の罠）: 「検証者を誰が検証するか」。検証を発生源に最も近い層（各 pir2 が自分の implementer を git diff で裏取り）に置くのが安いが、その層が**まさに脆弱な L1**（後述の制御責務矛盾）。検証を L0 に集約すると堅牢だが生証拠を全層バブルアップ = context 爆発。→ ここに「サマリアップ vs 証拠アップ」の中心トレードオフが立つ（後述）。

#### 段5: ユーザーゲート L0 集約は subtask 数でゲート地獄化する
- 前提: 破壊的変更ゲート／`DEFERRED_USER_DECISIONS` を L0 に全集約。
- 境界: subtask N × ゲート M/件 = N×M 回のユーザー対話が L0 に直列で押し寄せる。【推論・数量は例示】N=10, M=2 → **20 ゲート**。DAG 直列制約でこれらが順序化されると、ユーザーが律速になり epic の並列性を殺す。さらに並列サブ由来のゲートは**到着順が非決定的**で、epic-runs.md に Phase/タイムスタンプが無いため「どの subtask のゲートか」が判別不能（観測性欠如と結合）。
- 二次効果: 対策の「バッチ提示」は割り込みを減らす代わりに、進めた subtask を待たせ（レイテンシ）、かつユーザーの**バッチ一括承認（rubber-stamp）** を誘発 → reviewer が既指摘の「破壊的変更ゲートの事後承認化」を悪化させる。

#### 段6: 深さバジェット L2 頭打ちは探索重タスクで inline フォールバック常態化 → 品質崩落
- 境界: サブ pir2 の planner/reviewer が explorer を必要とするが depth cap で inline（自己 grep）に退避。**探索重タスク**（大規模・未知・横断変更）ほどこの cap を強く踏み、まさに本物の explorer が最も要る場面で退化する。
- 自己点検: depth 5 が platform 上限で L0→L1→L2 は headroom あり ⇒ L2 cap は**自己制約**であり platform 制約ではない。ならば探索重サブに限り L3 explorer を許す余地はある。**が**、事象Y が示すとおり深いネストは「拒否」でなく「ゾンビ成功（tool_uses:0）」として silent に壊れうる（context: L3+ 未検証・推測）。→ 盲目的に深めると silent failure を招く。

#### 段7: 静的依存判定（epic-planner）は実行時発見の書き込みを取りこぼす
- 前提: epic-planner は「暗黙依存 → 直列化」を**静的のみ**で判定、working tree 非分離、実行時検知ゼロ。
- 境界: 並列サブが同一ファイルを触る。静的解析が共有書き込み（共有 config / barrel export / 生成物）を見逃すと、implementer の Edit が「read 後に変更された」で失敗、または lost update / merge conflict。**書き込み集合は静的に完全予知できない**（implementer が予測外のファイルを触る）のが漏れの根本。

#### 段8: #44783 デッドロックは「親の内側から検知不能」という最悪の境界
- 事実: 並列サブの Bash ハング → 親が完全デッドロック（Closed as not planned）。
- **決定的な境界洞察**: デッドロックは**親プロセスの内側からは検知できない**。L0 に watchdog を置いても、その watchdog 自身が同じ親でブロックされる。⇒ どれだけ L0 を堅牢化しても #44783 は捕まらない。防御は事前（並列幅を下げる／直列化）か、事外（人間 or 外部プロセスが監視役）に限られる。
- 帰結: epic の目玉「並列 fan-out」は**上流で直らないデッドロックを構造的に内包**する。2 並列でも 1 本ハングで詰む（幅を下げても確率は下がるが 0 にならない）。⇒ 試験段階では **fan-out は既定 OFF（直列）か明示 opt-in** が platform-safe な唯一解。並列性（epic の看板機能）を犠牲に安全を取る。

### 反証・対立仮説の検討

**最も強い反論（トップ推奨=「重い堅牢化より先に安い観測性を入れよ」への steelman）**
> epic は 0 回実行の試験実装。MAST は失敗の41.8%が設計問題と言う。ならば timeout/検知/観測を作り込むより、(i) 設計根幹（L1 制御責務矛盾）を先に正すか、(ii) とにかく1回動かして**実際に**何が壊れるか見る方が先。動かしてもいないシステムに想像上の境界対策を敷くのは premature optimization で、労力の無駄。

**応答（なお推奨が耐えるか）**
- 反論の「重い堅牢化（worktree 分離・fan-in merge・resume 機構）は観測後に回す」部分には**同意する**。これらは高コストで、境界が本当に踏まれるかは実測依存。→ 私の優先度づけでも「観測に回す」。
- しかし「安い観測性（epic-runs.md への per-node status＋タイムスタンプ）」だけは反論に耐える。理由: 事象X が示すとおり**1回目から破綻する公算が高く**、そのとき per-node タイムスタンプが無ければ「どこで境界を越えたか」がまた transcript 考古学でしか分からない（事象X の root cause 特定に実際そうなった）。観測性は「未実行システムの過剰堅牢化」ではなく、**「1回動かして見る」を初めて有意にする計測装置**。計測なしの試行は次も診断不能な失敗を生むだけ。
- よってトップ推奨は「観測性=先、重い堅牢化=後」に精緻化されて生き残る。反論は堅牢化の範囲を正しく絞る形で**部分採用**され、推奨を壊さない。

**対立仮説: 「制御責務は L1 に置いたままでよい（矛盾は許容）」**
- steelman: サブに SKILL.md 全文解釈させる方が L0 のオーケストレーション負荷を分散でき、L0 の context を軽く保てる。
- 棄却根拠（二次波及の観点）: 事象X/Y の実害は**L1 相当層の自律解釈が unbounded に迷走した**（19分ドリフト）ことに起因する。かつ後続のあらゆる信頼性改善（timeout / 捏造裏取り / ゲート判断）を L1 に置くと、**堅牢化が L1 の不信頼性を継承**する（脆弱な層に監視役を兼務させる自己矛盾）。→ 矛盾の二次コストは「改善策の置き場所そのものを汚染する」こと。ゆえに矛盾解消（L1 を薄い dispatcher にし制御を L0 に寄せる）は他改善の**前提条件**。対立仮説は棄却寄り。

### 二次・三次の含意と境界条件

**中心トレードオフ（具体・数量）**

| # | トレードオフ | 犠牲 → 獲得（具体） | 境界（どこで裏返るか） |
|---|---|---|---|
| T1 | サマリアップ vs 証拠アップ | サマリアップ: context 固定小 ↔ 事象X 型捏造を素通し / 証拠アップ: 捏造を捕捉 ↔ 3層ネストで implementer の生 git-diff を2層バブルアップ、context が diff 規模×層数で膨張 | ネスト深さ × diff 規模。浅く小 diff なら証拠アップ可、深く大 diff で破綻 |
| T2 | 深さバジェット vs 並列スループット vs デッドロック面 | 深い/広い: ネスト探索品質↑ ↔ 同時エージェント N 体で #44783 露出が幅 N に線形増 / 浅い/狭い: 安全・安価 ↔ inline 退避で探索品質崩落 | N 並列で 1 本ハング＝親デッドロック。幅を下げても確率0にならない |
| T3 | ユーザーゲート集約 vs 自律性 vs ゲート地獄 | 集約: 判断を信頼できる L0 に一元化 ↔ N×M（例 10×2=20）ゲートで人間が律速＆事後承認化 / 委譲（保守デフォルト自律）: 割り込み減 ↔ 破壊的変更が無承認で進むリスク | subtask 数 N とゲート密度 M の積。並列サブのゲート到着順が非決定 |
| T4 | 静的直列化 vs 実行時競合検知 | 静的: 実行時コスト0（epic-planner 既存）↔ implementer 発見の書き込みを取りこぼす / 実行時: 取りこぼし捕捉 ↔ worktree 分離＋ファンイン merge（ともに未対応）が必要 | 書き込み集合が静的予知不能なとき。ダイヤ型 DAG（fan-in）で顕在化 |

**境界条件でフローが壊れるシナリオ → 防御 (a)問題 (b)機序 (c)トレードオフ**

1. **10 サブタスク並列（fan-out 最大）**
   - (a) 問題: #44783 で 1 本の Bash ハング → 親完全デッドロック。かつ N×M ゲートが L0 に殺到。
   - (b) 機序: 並列幅 N に対しデッドロック露出が線形、ゲート数が N×M で増加。デッドロックは親内から検知不能（段8）。
   - (c) トレードオフ: 試験段階は **fan-out 既定 OFF（直列）or 明示 opt-in ＋幅上限（例 ≤3）**。並列スループット（看板機能）を犠牲に platform-safe を取る。上流で直らない以上、これは回避でなく前提受容。

2. **深い直列鎖（A→B→…→F）**
   - (a) 問題: 各ノードがフル pir2（推論 10〜30分）→ 6 深で 1〜3時間、並列恩恵ゼロ。resume 無しゆえ 5 ノード目で死ぬと全鎖の進捗喪失。L0 が全完了ノードのサマリを保持 → context が鎖長に線形増、長鎖で L0 context 枯渇リスク。
   - (b) 機序: 直列 = 経過時間最大の形。resume 欠如の損失が最大化される場所。
   - (c) 防御: **per-node チェックポイント（epic-runs.md に pending/running/implemented/reviewed/done ＋timestamp）**。resume で未完ノードのみ再ディスパッチ。トレードオフ: 状態管理機構を新設（pir2 の continuation-gate/handoff 相当）。ただし観測性と二重に効くため試験段階でも費用対効果が高い（最小版=ステータス行のみ）。

3. **サブ pir2 が部分完了で死ぬ**
   - (a) 問題: implementer 完了・reviewer 前で死 → DAG に半完成ノード。L0 は何が完了したか知る状態を持たない。下流が壊れた土台で進むか永久ブロック。
   - (b) 機序: failure-recovery パスと状態の不在（context 確認済み）。
   - (c) 防御: シナリオ2と同じ per-node チェックポイント＋「半完成ノードは reviewed 未達なら done 扱いしない」不変条件。トレードオフ: 同上（状態機構コスト）。

4. **並列サブが同一ファイルを触る（#44783 とは別の競合）**
   - (a) 問題: working tree 非分離で concurrent Edit → lost update / 「read 後に変更」失敗 / merge conflict。
   - (b) 機序: 静的直列化が共有書き込みを取りこぼす（T4 の境界）。
   - (c) 防御（試験段階の最安）: **疑わしきは直列化**（epic-planner が書き込み集合の重なり可能性を保守的に見て並列を諦める）。並列度を犠牲に安全。将来: git worktree 分離＋fan-in merge（未対応＝観測後）。

5. **ダイヤ型 DAG（fan-in／合流）**
   - (a) 問題: 複数サブが1下流に合流するが epic に fan-in 機構ゼロ（reviewer 既指摘）。親が重複ファイル編集なら合流で衝突。
   - (b) 機序: DAG が非ツリーになる瞬間に破綻。
   - (c) 防御: 試験段階は **epic-planner をツリー型 DAG（fan-in 禁止）に制約**。表現力を犠牲に機構コスト回避。逸脱時は明示 USER_DECISION。
