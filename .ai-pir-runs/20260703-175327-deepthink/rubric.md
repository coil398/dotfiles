## 成功基準（rubric）: /epic オーケストレーションフローの改善点抽出

### この熟考のゴール
`/epic`（大規模タスクを epic-planner で分割し、DAG 順に各サブタスクを /pir2 としてネスト起動する上位オーケストレーションフロー）の設計を分解し、**具体的で優先度づけされた改善点**を、根拠・機序・トレードオフつきで導く。単なる粗探しでなく「試験実装として何を今直し、何を観測に回し、何を捨てるか」まで判断できる状態にする。

### スコープ / 制約（ユーザー確定: (B) epic＋ネスト全般に拡大）
- **対象（in scope）**: `.claude/skills/epic/SKILL.md` の Phase 1 → 1.5 → 2 → 3 と、ネスト pir2 起動機構（3 階層ネスト・深さバジェット・fan-out・依存直列化・ユーザーゲート bubble-up・retrospector 統合・成果物永続化）、`.claude/agents/epic-planner.md` の役割分担、pir2 慣習との接続整合。
- **対象（in scope・拡大）**: 事象X が示す**ネスト多エージェント全般の信頼性**まで照準を広げる ―― (a) resume 直後の完了報告**捏造**の検知、(b) サブエージェントの**無応答/ハング**・**ゾンビ成功（tool_uses:0 で status completed）**の検知、(c) 並列サブエージェント Bash ハングによる親デッドロック（GitHub #44783）、(d) 中断復帰（resume）。**pir2 側・共通機構（hook / references）に波及する改善提案も可**とする。
- **対象外（out of scope）**: pir2 本体の全面再設計、epic 以外のスキル（research / article 等）の改修、改善点の実コード実装（本熟考は「改善点の抽出と優先度づけ」まで。実装は別途）。pir2 への波及は「epic を安全に回すために最小限必要な範囲」に限る。
- **前提**: epic は試験実装（experimental.md に SSOT 化済み・Epic executions 0）。「動かして観測してから恒久採用」の段階。過剰設計を避け、実験を回せる最小の堅牢性を優先する。

### 充足基準（gate はこれを一項目ずつ客観照合する）
| # | 基準 | 充足の判定方法（何があれば充足か） |
|---|------|-----------------------------------|
| 1 | フローの端から端まで分解され、各段（Phase 1/1.5/2/3 + ネスト機構）の弱点・失敗モードが**機序つき**で列挙されている | 各 Phase について「どこで・なぜ・どう壊れる/漏れるか」が抽象語（"改善余地がある"等）でなく具体機序で最低1つずつ示されている |
| 2 | 具体的な改善点が**5件以上**、各々に (a) 解決する問題 (b) 修正の機序 (c) コスト/トレードオフ が揃って示されている | 改善点リストが存在し、各項目に a/b/c の3要素が明記されている |
| 3 | 今回実観測された失敗（レビューフェーズのフリーズ＝捏造起点 / サブエージェントのゾンビ成功）の**根本原因分析**があり、**ネスト多エージェント全般の信頼性**（捏造検知・無応答/ゾンビ成功検知・親デッドロック回避・タイムアウト・resume・観測可能性）に応える改善が最低1つ含まれている | 事象X/Y の root cause が言語化され、対応する信頼性改善（epic 内 or pir2/共通機構への波及）が改善点リストに含まれている |
| 8 | reviewer が既指摘済みの**設計根幹の矛盾**（L1 ネスト pir2 ランナーに制御責務を持たせる設計 vs CLAUDE.md「サブエージェントに制御責務を持たせない」規定）に対し、解消方針か、逸脱を正当化する明示的判断が示されている | 当該矛盾が論点として扱われ、解消案 or 正当化のいずれかが根拠つきで示されている |
| 4 | 各改善点が既存リポ慣習（pir2 / pir2async / deepthink / research の SSOT・references）と照合され、**整合 or 逸脱**が明示され逸脱には理由がある | 改善点ごとに「既存 SSOT との関係（準拠/逸脱/新規）」が付されている |
| 5 | 改善点が**優先度づけ**（今直す必須 / 観測に回す / 試験段階として許容・見送り）され、epic の試験実装という位置づけに紐づいた判断根拠がある | 各改善点に優先度ラベルと、experimental 位置づけを踏まえた採否理由がある |
| 6 | トップ推奨に対する**最有力の反論が steelman され応答**されている（例: 「試験実装に堅牢化は過剰、まず0回を1回動かせ」） | 反論が最低1つ明示され、それへの応答がある |
| 7 | 主要なトレードオフが**具体**で示されている（深さバジェット vs 並列スループット、ユーザーゲート集約 vs 自律性、堅牢化コスト vs 実験速度 等） | トレードオフが最低2つ、定性でなく具体（何を犠牲に何を得るか）で示されている |
