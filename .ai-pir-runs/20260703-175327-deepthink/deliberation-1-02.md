### 思考の起点（前提の確認）

**context から確定的に言える事実（出典あり）**
- 事象X（フリーズ）root cause = CONFIRMED: 捏造は epic のフロー内ではなく **epic を実装していた通常 `/pir2` セッション**の resume 直後に起きた。`parse-failure-continue-hook` は「整形式出力が続いたため検知不能」（exploration-03.md, 発生セッション transcript）。
- 事象Y root cause = CONFIRMED: ゾンビ成功 explorer は「**epic 深さバジェット無関係**」の L0→L1 直接起動。検出は「呼び出し元の偶然の注意のみに依存」（本セッション実観測 + exploration-03.md）。

### 段階的推論（攻撃の主軸）

#### 段階1: 「今回の失敗は epic 機構が原因ではない」— 事実からの直撃

- context の CONFIRMED 事実は2つとも「epic のネスト機構（DAG/fan-out/深さバジェット/L1 ランナー）を通っていない」。事象X は epic を**書いていた** pir2 セッション、事象Y は epic 深さバジェット**無関係**の explorer。
- **飛躍の自己点検**: 「原因でない」→「epic 堅牢化は無意味」は飛躍。正しくは「今回観測された2失敗は、epic の DAG/fan-in/サブタスク上限/handoff 競合/深さバジェットの**どれを直しても再現的には防げない**」。
- 帰結: 改善案の束のうち **DAG 合流・サブタスク数上限・handoff 競合ロック・深さバジェット調整・親デッドロック機構**は、rubric 基準3（今回の失敗への信頼性改善）に**1つも寄与しない**。これらは「机上で数えた失敗モード」への予防であり、発火実績ゼロ。

#### 段階2: 検知機構を足す系の構造的落とし穴

- **(1-p)^N 問題（推論）**: 検知ゲートを N 個直列に挟むと、各ゲートの偽陽性率 p に対しフロー完走確率は概ね (1-p)^N に劣化する。事象X は「捏造をすり抜けた（検知不足）」失敗だが、過剰検知は「正常をブロックする（偽陽性）」逆方向の失敗を生む。**検知を増やすほど、皮肉にも rubric が最優先する『0回を1回動かす』が遠のく**。
- **検知機構自体のゾンビ化（推論、先例つき）**: 事象Y への「tool_uses:0 / status completed を呼び出し元が確認する手順」を**文章で** explorer.md 等に足すと、その確認は親 LLM の判断に依存する。事象X では親 LLM が捏造で19分迷走していた。**捏造中の LLM に、捏造/ゾンビを検知する手順を実行させる**のは自己参照で、hook でなく文章手順である限り「検知機構がゾンビ化の影響下に入る」。`parse-failure-continue-hook` が整形式出力にすり抜けた先例が、文章/ヒューリスティック検知の脆さを裏づける。

#### 段階3: 「検知」より「証拠要求」への転化

- 捏造検知を「報告行数 vs 実ファイル行数の不一致」で組むと **偽陽性を量産**する（複数ファイル実装・要約報告・diff ベース報告は行数が一致しない正常系）。しかも捏造検知→自動リトライは CLAUDE.md「ブラインドリトライ禁止（2回失敗で止める）」と衝突し、resume 環境要因で捏造が再発すると hook 同士が綱引きする。
- **転化案（推論）**: 「検知（偽陽性リスクを負う）」でなく「resume 境界でのみツール裏取りを**強制**する（証拠要求）」に変えると、偽陽性が原理的に出ない — 証拠が付けば正常、無ければ報告を無効とするだけ。攻撃に最も耐えるのはこの非対称化。

### 反証・対立仮説の検討

#### 対立仮説（最有力）を steelman
> 「epic は Epic executions 0 の試験実装。堅牢化を積む前にまず1回完走させて実データを取れ。今のフリーズは epic 設計の欠陥でなく pir2 の resume 時捏造という別レイヤの問題で、epic を触っても直らない」

**本気の擁護（どこまで正しいか）**
- 事実整合: 事象X/Y はどちらも epic 機構を通っていない（context CONFIRMED）。「epic を触っても直らない」は、少なくとも観測済み2失敗に関して**文字通り正しい**。
- 経済性: 実データ皆無（スループット・分割安定性・結合ドリフト未測定）で 14 個の対策優先度を決めるのは observation なき最適化 = premature optimization。MAST の「41.8% は設計問題」は統計であって「この epic のこの設計を今直せ」という指令ではない。
- 自己矛盾の暴露: **堅牢化作業それ自体が epic を1回動かすまでの時間を延ばし、実データ取得を先送りする**。堅牢化 vs 実験速度は「どちらを取るか」でなく「堅牢化が実験を食う」自己矛盾を含む。→ この steelman は改善案の束の 7〜8 割に対して有効。

**それでも成立する反論**
- steelman の盲点は「1回完走させる」の前提が**今できなかった**事実。実際に回してフリーズ→19分迷走した。「まず動かせ」の前提（動かせる状態）が無いなら、**フリーズ検知と観測可能性は『堅牢化』ではなく『実験を回すための計器』**。rubric 前提「実験を回せる最小の堅牢性」そのもの。
- 決定的な切り分け: steelman は「堅牢化」を一枚岩で否定するが、**計器（instrumentation）と本番堅牢化は別物**。
  - 計器（今入れる／安い）: epic-runs.md に Phase/timestamp（どこで止まったか分かる）、決定論的ゾンビ検知 hook、resume 境界の証拠強制。
  - 本番堅牢化（観測に回す／高い）: DAG fan-in、失敗回復パス、handoff 競合ロック、タイムアウト機構、サブタスク上限の厳密チューニング。
- 結論: steelman は「本番堅牢化は見送れ」までは**正しい**が、「だから何も入れるな」は行き過ぎ。**計器3点だけは実験の前提として今入れる**が反論の落とし所。

### rubric 基準8（L1 制御責務の矛盾）への応答

- **攻撃1（再設計は過剰）**: L0 に全制御を集約すると、epic は「L0 が全 pir2 フェーズを直接回す巨大単一オーケストレータ」= pir2 を N 回直列実行と等価になり、3階層ネストの旨み（各サブを独立 pir2 として自律実行）が消える。矛盾解消のために設計の存在意義を消すのは過剰反応。
- **攻撃2（正当化は危うい）**: 「L1 は pir2 のサブでなくネストされた pir2 オーケストレータそのもの」という正当化は規定文言の外をすり抜けるレトリックで、規定の**意図**（制御・ループカウンタ SSOT の分散を防ぐ）には反する。L1 にループ管理を持たせると、まさに「ループカウンタ SSOT が L1 に分散」する当該懸念が発火する。
- **red-team の落とし所（推論）**: この矛盾は0回実行で顕在化していない。「L1 が本当に SKILL.md 全文を解釈して自律オーケストレーションできるかの実証が無い」（context 空白）。→ **条件付き正当化**が最も誠実: 「試験段階として逸脱を明示許容し、1回目実行で L1 の自律性を観測。破綻したら L0 集約へ倒す」。無条件の再設計も無条件の正当化も却下。

### 二次・三次の含意と境界条件

- **含意1**: 改善案を「机上で数えた失敗モードの数」だけ足すと、実発火する2〜3個への対策が10個以上のノイズに埋もれ、優先度判断が壊れる。**改善は数でなく『実験を回す計器』に絞ると epic が早く回り、実データが本番堅牢化の優先度を教えてくれる**（正のループ）。
- **境界条件（この攻撃が崩れるケース）**: steelman の「epic を触っても直らない」は、**事象X が epic フロー内（L1 ネスト pir2）でも再発する**なら崩れる。context は事象Y の深さバジェット無関係は明記するが、事象X が L1 内で再発するかは 0 回実行で**未検証**。もし L1 内で resume 捏造が起きるなら、#2（証拠強制）は epic 内でも必須になり「計器」から「本番堅牢化」に格上げされる。
- **境界条件2**: 決定論的ゾンビ検知 hook（#1）は、Agent メタデータ（tool_uses / status / duration）が hook 層で取得可能であることに依存。取得不能なら文章手順に退化し価値が落ちる（実装可能性の検証が前提）。

### 事実と推測の仕分け

- **事実（context に出典あり）**: 事象X/Y が epic 機構を通っていない／parse-failure-hook が整形式出力ですり抜けた／Epic executions 0／#44783 Closed not planned／retrospector-prompt 写像未定義／citation 誤記群／深さ L3 以深未検証。

### 追加探索が必要な論点

- **事象X が epic の L1 ネスト pir2 内でも再発するか**は transcript が存在しない（Epic executions 0）。これは explorer 再起動では埋まらず、**epic を1回動かした実行観測でしか埋まらない**。→ オーケストレーターへ「熟考では埋まらない、実行データ待ちの論点」として明示。もし epic 内再発が確認されれば #2（resume 証拠強制）は epic 本体の必須要件に格上げ。
- **SubagentStop / Stop hook で Agent の tool_uses/status/duration メタデータが決定論的に取得可能か**の技術裏取り（本熟考は新規調査不可のため未確認）。取得可なら #1 の優先度が「今入れる」に確定、不可なら文章手順に退化。
