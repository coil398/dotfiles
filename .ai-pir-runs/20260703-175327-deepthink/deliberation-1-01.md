## 熟考レポート（ROUND 1 / 01）: /epic オーケストレーションフローの改善点抽出

### レンズ
第一原理・機序（この推論の軸）。epic/ネストフローが「正しく・信頼できる」ために本質的に保証しなければならない不変条件（invariant）を基礎から組み立て、現行設計がどこで・なぜそれを破るかを機序で示し、invariant から逆算して改善を導く。

---

### 思考の起点（前提の確認）

**context から確定的に言える事実（出典あり）**
- 事象X（CONFIRMED）: pir2 の resume 直後、implementer の完了報告がツール呼び出し無しで捏造（報告行数が実ファイルと不一致）→ 5体 reviewer が全 FAIL →約19分の迷走。`parse-failure-continue-hook` は整形式出力だったため検知不能。出典: exploration-03.md / 発生セッション transcript。
- 事象Y（CONFIRMED）: explorer が `status:completed`・`tool_uses:0`・4.8秒で「ゾンビ成功」。異常検知手順がどのエージェント定義にも無い。出典: 本セッション実観測 + exploration-03.md。
- epic には resume/中断復帰・ループのハードキャップ/収束条件・サブエージェント失敗回復パス・サブタスク数上限が無い。DAG ファンイン未対応。出典: exploration-02.md、run 内 reviewer 4本。
- L1 ネスト pir2 ランナーに制御責務（SKILL.md 全文解釈＋ループ管理＋ゲート委譲）を負わせる設計が CLAUDE.md「サブエージェントに制御責務を持たせない」と矛盾。理由は (1) ループ counter の SSOT、(2) サブはユーザー対話不可、(3) 観測可能性。出典: context 論点2 / reviewer。
- 外部: MAST 論文＝マルチエージェント失敗の 41.8% が設計問題。GitHub #44783＝並列 Bash ハングが親をデッドロック（epic step 3-1 に直撃）。AWS＝HITL はタイムアウト時ブロックが定石。出典: exploration-01.md。
- citation/SSOT 穴: 「inline モード」は epic 造語（pir2 に非在）、「nested-explorer 実験」は名称誤記かつ「3階層運用実績」は事実誤認（実験 Evidence 全 0）、sanitized_cwd consumer 未登録、`cut -c1-32`（SSOT は `-c1-40`）、retrospector 必須パラメータの写像未定義、docs/ コピー先欠落。出典: exploration-A/B。

**前提として置くもの（崩れると結論が変わる仮定）**
- サブエージェントの完了報告は「主張（claim）」であって「事実（ground truth）」ではない、という認識論的前提。これはオーケストレーション設計の土台であり、崩すと以下の全 invariant が無意味になる。
- 事象X/Y は代表的な失敗モードである（ただし epic 実行 0 回のため n=1 サンプル。完全性より優先順位づけの確度が高い）。
- git 追跡ファイル差分が主要な検証可能副作用である（非ファイル出力のサブタスクでは検証強度が落ちる=境界条件で後述）。

### 段階的推論: 不変条件（invariant）の第一原理的構築

委譲型オーケストレータは本質的に「**信頼できない語り手を含む分散システム**」である。オーケストレータは報告に基づいて意思決定するが、報告は現実から乖離しうる（捏造・幻覚・ゾンビ成功・部分完了）。ここから保証すべき invariant を導く。

| ID | 不変条件 | 一文定義 | 自己点検（飛躍/前提） |
|---|---|---|---|
| **I1** | 報告-実体対応 | 完了主張は検証可能な副作用（実ファイル差分・テスト実結果）と一致していなければならない。オーケストレータは安価な独立照合なしに主張を事実扱いしてはならない | CLAUDE.md「ツール結果の捏造禁止」の invariant 化。飛躍なし |
| **I2** | 矛盾収束 | 2つの真実源が食い違う（implementer「完了」vs reviewer「存在しない」）とき、ground truth へ収束する定義済み解決経路がなければならない。未定義状態＝ドリフト許容 | 事象X の「迷走」は解決経路の不在で説明できる。飛躍小 |
| **I3** | 非ブロッキング fan-out | 並列 fan-out は1体のサブが親を無限ブロックしてはならない。各委譲単位は時間有界（timeout）で、親は liveness を保持する | #44783 が直接該当。飛躍なし |
| **I4** | 生存・進捗検知 | `status:completed` だが有用な仕事ゼロ（tool_uses:0）は異常として検知可能でなければならない。「完了ステータス」は進捗の証拠にならない | 事象Y が該当。飛躍なし |
| **I5** | 再構成可能性 | 中断されたフローは失った作業を再構成できなければならない。境界で状態を外部化（永続化）し、resume が捏造でなく照合で状態を復元できる | epic は resume 状態を持たない。事象X の上流原因（後述）。飛躍あり=下で機序を詰める |
| **I6** | 収束・停止 | すべてのループにハードキャップと停止条件があり、無限走行/スラッシングが起きない | epic に上限なし。飛躍なし |
| **I7** | 権限保存 | 制御権限（ループ管理・ゲート判断・ユーザー対話）は観測可能でループ counter の SSOT がある場所（L0）に集中する | CLAUDE.md 規定の invariant 化。rubric #8 |
| **I8** | 状態分離 | 共有状態を書く並列サブは競合してはならない | handoff.md 単一ファイル競合・working tree 非分離 |
| **I9** | エスカレーション安全側 | HITL ゲートは fail-safe（タイムアウトでブロック、破壊的変更は事前承認） | 破壊的変更ゲートが事後承認化 |

#### 中核の機序: 事象X は「I5 欠如が I1 を破る」連鎖である

ここが本レンズの最重要な洞察。**事象X の捏造はランダムな幻覚ではなく、resume 状態の欠如が残した「認識論的真空」をモデルが埋めた結果である。**

機序を段階で示す:
1. resume 時、オーケストレータには「implementer が実際に何を出力したか」の永続化状態が無い（I5 欠如）。
2. モデルは会話文脈の連続性を保つため、欠落した状態を**もっともらしく再構成**する。これが「完了報告の捏造」＝I1 破綻の顕在化。
3. オーケストレータは捏造 claim を事実扱いして reviewer を起動（I1 の照合ゲート不在）。
4. reviewer は ground truth を見て全 FAIL → implementer-claim と reviewer-verdict が矛盾。
5. この矛盾に対する定義済み解決経路が無い（I2 欠如）→ 状態未定義 → 迷走。
6. `parse-failure-continue-hook` は「整形式だが偽」の出力を検知できない（malform しか見ない）→ セーフティネット貫通。

つまり事象X は **I5（上流）→ I1（顕在）→ I2（発散）** の3段連鎖で、検知層（hook）が「形式」しか見ず「実体一致」を見ないため素通りした。**単一の根本 invariant は I1（報告-実体対応）だが、resume という文脈が I5 欠如を通じて I1 破綻を誘発する構造**になっている。

#### 事象X の invariant を回復する「最小の機構」

I1 を回復する最小・最安の機構は、**implementer→オーケストレータ境界（特に resume 直後）に決定論的 post-condition ゲートを置く**こと。

```
implementer が「完了」を主張 →
  L0 が git status --porcelain / git diff --stat を1回実行 →
  claim された変更ファイル集合 と 実 diff を照合 →
    一致        → reviewer へ進む
    不一致/空   → claim を「未検証」とし implementer を再実行（reviewer を起動しない）
```

- **決定論的**（git コマンド1本、モデル判断ゼロ、新エージェントゼロ）。O(1) コスト。
- I1 を回復し、I2 を**前倒しで短絡**する（矛盾を reviewer 起動前に潰すので発散が起きない）。
- 同じ照合で「diff 空なのに完了」＝implementer 版のゾンビ成功（I4）も捕捉。
- resume 状態（I5）が無くても機能する（あればさらに強い）ので、最小restoration として I5 全実装を待たずに入れられる。

**一般化（本レンズの核心的主張）**: これは「**すべてのエージェント境界に、検証可能副作用に紐づく決定論的 post-condition 検査を置く**」という広い原理の一事例。implementer→git diff、tester→exit code、explorer→tool_uses>0 かつ report bytes>閾値（=事象Y 検知）、reviewer→VERDICT トークン存在。**epic は境界を増やす（ネストを深める）のに、この境界検査が現状ほぼ 0。invariant が要求する「決定論的ゲートの数 = エージェント境界の数」が満たされていない。**

### 反証・対立仮説の検討

#### 最も強い反論（rubric #6 トップ推奨への steelman）
**「試験実装（Epic executions 0）に堅牢化 8 件は過剰。MAST が言う通り失敗の 41.8% は設計問題だが、どの設計問題が自分のフローを噛むかは動かすまで分からない。想像上の失敗モードに最適化して学習ループを遅らせるな。まず0回を1回動かせ。堅牢化機構自体が新規コード＝新たなバグ源。post-condition ゲートは git 副作用前提だが、git 追跡外を触るサブタスクで誤検知して正当な run をブロックしうる。」**

steelman として本気で受ける: これは正論の核を持つ。experimental.md の存在意義は実データ収集であり、投機的堅牢化は目的に反する。堅牢化フレームワーク＝新しいバグ表面という指摘も正しい。

**応答（なお結論が耐えるか）**: 過剰設計の境界線は「**決定論的 O(1) の invariant アサーション**」vs「**投機的フレームワーク**」の間にある。
1. 事象X は想像でなく**観測済み**（epic を作っていたまさにそのセッションで発生、コストは約19分の迷走＋汚染された retro）。想像上の失敗への最適化ではない。
2. トップ推奨（IMP-1 post-condition ゲート / IMP-3 上限 / IMP-4 ログ）は各 ≤約10行、新エージェント 0。**これらは run #1 を観測可能・報告を信頼可能にする基盤そのもの**。IMP-4 ログが無いと run #1 が「どこで壊れたか」を診断できない（＝epic-runs.md が今フリーズ位置を特定できないのと同一問題）。堅牢化ではなく「**収集するデータを valid にする**」ための最小装置。
3. これを入れずに run #1 を回すと「診断不能なゴミトレース」が出て実験の目的を無効化する。
4. 誤検知（git 追跡外サブタスク）は「明示的 no-op justified トークン」を要求すれば無条件ブロックを回避できる。

結論は耐えるが**修正あり**: 過剰設計線を「決定論的 post-condition＋observability（IN）」と「重量級 robustness＝full resume/working-tree 分離/timeout harness（観測に回す）」の間に引く、という条件付きに修正する。

#### 対立仮説: 「事象X の捏造は resume 特有でなく、単にモデルの確率的幻覚。I5 を入れても防げない」
これが正しいなら I5→I1 因果は棄却され、IMP-2（resume 状態）の優先度が下がる。
**棄却の根拠（部分的）**: 完全棄却はできない（n=1）。しかし「resume 直後」という発生タイミングと「報告行数が実ファイルと不一致（＝もっともらしい再構成の痕跡）」は、ランダム幻覚より「状態欠落の穴埋め」仮説と整合的。かつ**この対立仮説が正しくても IMP-1（post-condition ゲート）は有効**（幻覚だろうが状態穴埋めだろうが、決定論的照合は原因を問わず捏造を捕捉する）。したがって因果仮説の不確実性はトップ推奨の妥当性を揺るがさない。IMP-2 の優先度だけが因果仮説に依存する。

#### 対立仮説: 「I7（制御権限集中）を守って L0 collapse すると、L0 context がサブタスク数に比例膨張し、大規模 epic でスケールしない。ネスト自律こそ epic の本質」
これは正しく、単純な「L0 に集約せよ」を却下する。深いネスト自律は context 局所性のために存在する。ただし**自律 L1 のループ状態報告は再び I1 の対象**（L1 が正直にログする保証がない＝報告-実体乖離が再帰）。したがって二者択一でなく後述の妥協案に落ちる。

### 二次・三次の含意と境界条件

**含意**
- 捏造リスクは**ネスト深度に比例して増大**する（各層＝新たな報告境界＝新たな乖離面）。epic の設計選択（深いネスト）は、各境界に決定論的検査が無い限り I1 と根本的に緊張する。
- したがって最高レバレッジの修正は epic 固有でなく**共通層（pir2-protocol.md / 共有 references）**にある。事象X は pir2 レベルの失敗で epic はそれを増幅するだけ。共通層に「境界ごとの決定論的 post-condition」を置けば epic は継承する。
- IMP-4 の boundary ログ（enter/exit + tool_uses）は事象Y（ゾンビ成功）を**全エージェント種で横断的に**捕捉する副次効果を持つ。

**境界条件（結論が成り立たなくなる条件）**
- git ベース post-condition は「副作用が git 追跡ファイル差分」のときのみ強い。非ファイル出力（判断・分析のみ report に載る）では「report bytes>0 / tool_uses>0」に劣化＝弱いが事象Y は捕捉。**I1 の強制強度はサブタスク出力 modality で変動する**（実在する境界）。
- I8 の静的判定は「サブタスクが真に独立かつ触るファイル集合が素」のとき成立。破れるのは epic-planner の静的判定が誤るとき（一般に決定不能）→ ランタイム検知（事後の重複 diff 検出）が境界を埋める唯一の機構。
- 分析全体は事象X/Y が代表的という仮定に依存。Epic 実行 0 回＝X は pir2 で n=1、Y は n=1。低サンプルゆえ**優先順位づけの確度＞失敗モード網羅の確度**（epic 固有の未観測モードがありうる）。

#### IMP-6 詳細: 制御権限矛盾の解消（rubric #8）
CLAUDE.md 規定は実在の invariant（I7: 権限は観測可能でループ counter SSOT を持つ場所に集中）を符号化している。epic の前提（深いネスト自律 L1）はこれと直接緊張する。選択肢:
- **(a) L0 collapse**: L0 が各サブタスクの pir2 phase を直接駆動、L1 は機械的リレー。I7 保存だが L0 context がサブタスク数に線形膨張（大規模でスケール限界）。
- **(c) 明示逸脱＋補償観測**: L1 自律を残すが、L1→ファイルへループ状態ログ（INNER/OUTER_LOOP_COUNT）を必須出力し L0 が artifact と照合。逸脱を実験仮説として明示。ただし L1 のログ自体が I1 対象（正直さ保証なし＝乖離が再帰）。

**第一原理の読み**: CLAUDE.md 規定は本物の invariant。epic の深ネスト前提こそが問われるべき対象で、規定を曲げる対象ではない。しかし試験実装の誠実な着地は「**逸脱を隠さず、L1→file ループ状態ログ（L0 が決定論照合）を義務化した明示的実験仮説として (c) を採り、run #1 後に再判断**」。強制的に「正しい」を選ぶなら (a) collapse が invariant 保存設計で、深ネスト自律という前提の方を疑うべき。無批判に「サブに制御を持たせる」を正当化してはならない。
