### 判断根拠

#### 1. `--codex` パースの正しさ
`SKILL.md` ステップ1の `case "$TASK" in "--codex "*) ... ;; "--codex") ... ;; esac` を実際に手で trace した。
- `"--codex build X"` → `"--codex "*` にマッチし `TASK="build X"` に正しく除去される
- `"--codex"`（単体）→ 完全一致ケースで `TASK=""` になる
- `"--codex   "`（末尾空白のみ）→ `"--codex "*` にマッチし、リテラル8文字 `"--codex "` のみを剥がすため `TASK="  "`（残り空白）になる。空タスクは epic-planner 側「入力の確認: 不足があればスキル本体に確認する」で拾われる設計なので破綻はしない
- `"implement --codex support in bin/foo"` のように文中に `--codex` を含むが先頭一致しない文字列は、どちらの case パターンにもマッチせず `SUBTASK_SKILL="pir2"` のまま素通りする（誤爆なし）
- `$ARGUMENTS` の埋め込み方（`TASK="$ARGUMENTS"`）は pir2 本体の既存慣習（`run_feature="$(printf '%s' "$ARGUMENTS" | ...)"`）をそのまま踏襲しており、新規に導入されたリスクではない

結論: パースロジック自体は正しく、エッジケースでの誤爆・クラッシュは確認できなかった。**問題なし**。

#### 2. ネスト起動方式の実行可能性
「general-purpose を `model=opus` で Agent 起動し `~/.claude/skills/${SUBTASK_SKILL}/SKILL.md` を Read させてオーケストレーターとして実行させる」方式そのものは、Claude Code v2.1.172 のネスト起動機構と整合しており実行可能。ただし、以下の点でプロンプトに渡す情報の欠落（問題一覧 #2）を検出した。

`$ARGUMENTS` は Claude Code のスラッシュコマンド実行時（`/pir2 <text>` の実入力）にディスパッチャがマクロ置換する仕組みであり、サブエージェントが `Read` ツールで SKILL.md をファイルとして読み込む場合はこの置換は発生しない（`Read` は生テキストを返すだけ）。したがって L1 ランナーが pir2 SKILL.md 本文中の `TASK="$ARGUMENTS"`（ステップ1のbashブロック）や `**タスク**: $ARGUMENTS`（冒頭プロース）をそのまま解釈しようとすると、リテラルな `$ARGUMENTS` という未定義シェル変数（bashブロックでは空文字列に評価される）または字面通りのプレースホルダ文字列として扱われるおそれがある。pir2 のステップ4（planner 起動）は「タスク内容と探索レポート全文を渡してください」と明示されており、L1 ランナーが epic 側から渡された `<Ti タスク記述>` を独自に把握していれば実質的な破綻は避けられる可能性が高い（opus の文脈推論に依存）が、epic SKILL.md ステップ3-0のプロンプトテンプレートには「読み込んだ SKILL.md 内の `$ARGUMENTS` はこの `<Ti タスク記述>` を指すものとして扱え」という明示的な束縛指示が一切ない。RUN_DIR 命名（run_feature スラグ）・RESUME_MODE 判定・REVIEWER_SET のフラグパース等、複数箇所が暗黙の推論に依存する形になっている。

#### 3. 依存グラフ制御
`epic-planner.md`「エピック分割レポートフォーマット」の DAG 表現は
```
- 並列実行可能グループ: {T1, T2, ...}
- 直列辺: [T_a → T_b ...]
```
という「独立集合（辺なし） vs 直列辺リスト」の二極構造。SKILL.md 側の実行手順も 3-1（独立集合の並列 fan-out）と 3-2（依存辺のあるサブタスクの直列実行）の二つに分かれているが、両者を統合する「DAG をトポロジカル順に波状実行する」というアルゴリズム（各波で、それまでに完了した依存を持つタスクのうち相互に辺のないものを並列起動し、完了を待って次の波へ進む）が明文化されていない。具体的には T1→{T2,T3}→T4 のようなダイヤモンド型 DAG（T2, T3 は T1 完了後に並列実行可、T4 は T2 と T3 の両方完了後にのみ実行可）をどう実行するかの記述がなく、3-1 の「辺のない独立集合は並列実行」を字面通り解釈すると、T1 完了前に T2/T3 を「互いに辺がない独立集合」として誤って並列起動してしまう危険（依存未解決のまま実行）を排除できていない。
さらに 3-2 の記述「後続の起動プロンプトに、**先行サブタスク**の返り値から得た...パスを注入」は単数の "先行サブタスク" を前提にした書き方であり、複数の先行タスクに依存するファンイン（T4 が T2 と T3 の両方に依存するケース）で複数の先行結果をどう注入するかが明記されていない。
循環依存の自動検知手順もない（唯一のセーフティネットは Phase 1.5 のユーザー確認ゲートでの目視レビュー）。
→ **依存グラフを持つ「大規模タスクの分割実行」という本機能の中核ロジックに、実行アルゴリズムの明文化漏れがある**。単純な「独立集合1つ＋直列チェーン1本」を超える DAG（複数サブシステムが絡む epic では十分起こりうる形）で誤動作・依存未解決実行のリスクが残る。

#### 4. 深さバジェット フォールバック
3-3 の記述「L2 での `Agent` 起動が深さ超過で拒否された場合は、その pir2 は `IMPLEMENTATION_ACTOR=main`／直接探索の inline モードにフォールバックして完遂すること」を pir2 SKILL.md 実物と突き合わせた。`IMPLEMENTATION_ACTOR=main` は**ステップ6（実装フェーズ、L1→L2 の implementer 起動）**の fallback 概念であり、「L2 のエージェント（planner/reviewer）がさらに explorer をネスト起動（L2→L3）しようとして拒否される」ケースとは境界レイヤーが異なる。両者を同一条件文の中で「／」（どちらでもよい二択）として並記しているため、実際にどちらの階層でどちらの障害が起きたときにどちらの fallback を適用すべきかが曖昧。L1 ランナーが「explorer 起動失敗」を「implementer の main フォールバック」と混同する余地がある。
また「深さ超過で拒否された場合」がプラットフォーム側でどう検出可能なシグナルとして現れるか（明示エラーか、無応答か）は plan.md 自身も「L3以深は未確認」「初回 `/epic` 実行時の検証事項」と正直に明記しており、これは authoring 時点でブロッキングにしない判断として妥当。ただし conditional の分岐先が2層のレイヤー境界を混同している点は文書としての論理的正しさの問題として残る。

#### 5. ユーザーゲート bubble-up
`DEFERRED_USER_DECISIONS` の集約は「サブ pir2 完了ごとに集約」「ブロッキングなら都度提示、軽微なら Phase 3 で一括報告」という設計自体は妥当（既存の 6.5/continuation-gate/plan-choice-gate という実在する pir2 内部ゲート名を正しく参照している）。「本質的にブロッキング」の判定基準は明文化されていないが、これは他の pir2 ステップでも同様に "スキル本体の判断" に委ねられている慣習の範囲内であり、致命的な欠落とは判断しなかった。並列 fan-out 中の兄弟タスクへの「動的な」ブロッキング通知（実行中のサブタスクへ割り込む機構）は存在しないが、Agent 起動モデル自体の制約（起動後は完了まで介入不能）に起因するものであり、epic 固有の欠陥ではない。

#### 6. epic SKILL.md ステップ2 と epic-planner.md 出力フォーマットの契約一致
SKILL.md ステップ2.5「サブタスク一覧＋依存グラフ＋各 pir2 タスク記述をユーザーに提示」という要求と、epic-planner.md の「エピック分割レポートフォーマット」（`### サブタスク一覧` / `### 依存グラフ（DAG）` / `### 各 pir2 へ渡すタスク記述`）は見出しレベルで完全一致している。`USER_DECISION_REQUIRED` / `EXPLORATION_NEEDED` の扱いも両ファイルで整合。**契約不一致は検出されなかった**。
