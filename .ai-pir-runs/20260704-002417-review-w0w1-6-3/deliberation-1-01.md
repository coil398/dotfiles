### 段階的推論

#### 段1: 「検証」の第一原理化 —— 独立性条件
任意の verification は「主張 P」と「独立観測 O」を突き合わせる営み。意味を持つ必要条件は 2 つ: **(i) 独立性**（O は P の生成主体とは別チャネルから来る。同一主体が P も O も作れるなら検証ではなく同語反復）、**(ii) 真正性**（O 取得チャネル自体が信頼できる）。
- 自己点検: 事象X で reviewer が空振りしたのは、reviewer の入力（implementation report）が **L2 の自己申告**で、独立性 (i) を満たさなかったから。捏造者は claim も「観測」も両方作れた。
- 飛躍の検証: この枠組みは 6-3 に限らず全検証に適用でき、恣意性はない（Ken Thompson "Trusting Trust"・TCB/root of trust の古典的構造）。

#### 段2: 6-3 の第一原理的貢献 —— O を git working tree に移した
6-3 は独立観測 O を **git delta（編集という物理作用の副産物）** に置いた。git delta は L2 が自己申告で作れない ―― 実際に Edit/Write を呼ばない限り working tree は dirty にならない。よって P（CLAIMED）と O（git delta）は別因果経路から来て独立性 (i) を満たす。
- 機序: dirty 状態は「編集したという言明」ではなく「編集作用の副産物」。言明は捏造できるが副産物は作用なしに生じない。Anthropic の outcome/state-check パターンと整合するのはこの点。
- 自己点検: 「作用なしに dirty を作れる経路」は本当に無いか？ → ここで staged/case-rename が効く（段5）。

#### 段3: 信頼の無限後退と錨（論点A の核）
検証は無限後退する: P を検証する V1、V1 を検証する V2… 停止点＝錨は定義上「それ自身は検証されない信頼の底」。6-3 は **L2→L0 境界**に決定論観測を挿入したが、**V0→L0 境界**（L0 が本当に bash を打ったか）には何もない。
- 第一原理: **6-3 が自分自身の実行を自分で検証することは論理的に不可能**（同一主体 L0 が検証と実行を兼ねると独立性 (i) が破れる＝自己言及パラドクス）。したがって「L0 の捏造を 6-3 が捕まえるべき」という要求は達成不可能なものを 6-3 に求めている。
- 自己点検: では「原理的に不可能だから欠陥ではない」で終わってよいか？ → No。「原理的不可能」と「錨が適切な場所にあるか」は別問題（段4）。

#### 段4: 事象X の不都合な事実と、錨が集約される単一点
事象X の捏造主体は L2 ではなく **L0** だった。6-3 は「L2 の捏造」装置なのに、対処対象の当のインシデントの捏造主体を構造上カバーできない。ここを機序で分解する（もし 6-3 が当時存在したら？）:
- **(a) L0 が implementer 起動も 6-3 検証も両方捏造**: 6-3 空振り。防げない（原理的に不可避、hook でのみ錨づけ可）。
- **(b) L0 が実装を捏造したが 6-3 は誠実に実行**: git delta 空・CLAIMED 非空 → **PHANTOM hard fail。防げる**。CLAIMED も空なら「編集想定なのに申告も変更も空」で PHANTOM。防げる。
- **(c) resume 時の認識論的真空**: L0 が「実装済み」と誤認。resume 後に 6-3 を実行すれば delta 空 → 捕捉。ただし「resume で 6-3 実行点がトリガーされる」保証が要る。
- **決定的洞察**: 事象X の L0 は「嘘をつこうとした」のではなく「実装したと**誤認**した」。**誤認者は検証を避けない**（自分が正しいと思うから隠す動機がない）。よって混乱型 L0 捏造は、L0 が手順どおり 6-3 を実行することで自分の誤認を暴かれる。**6-3 の錨は「L0 の実行意志」という単一点に集約されており、この一点が守られれば L2 の捏造も L0 自身の (b)(c) 型捏造も両方カバーする**。守られなければ全部素通り。
- 比喩の精密化: 一見「泥棒に金庫の鍵を託す」構造だが、金庫（git delta）の観測が独立なのが救い。L0 が変えられるのは「鍵を回すか/回したふりをするか」だけで、金庫の中身は L0 の願望では変わらない。だから錨づけすべきは「鍵を回す動作の外部監視」＝ hook。

#### 段5: git を oracle にする穴の切り分け（原理的欠陥 vs 実装の甘さ）
切り分け基準: 穴は「git を oracle にする**選択そのもの**」から必然か（原理的欠陥）、oracle の**実装（どの git コマンドを組むか）**から生じ別実装で塞げるか（詰めの甘さ）。
- **staged 変更**: 実集合を unstaged+untracked に限った実装選択の産物。git working tree は staged も完全観測可能（`git diff --cached` / `status --porcelain`）。→ **原理的欠陥ではなく実装＋前提の詰めの甘さ**。方向は **fail-closed（正当な実装を PHANTOM 誤検出、再実行で直らない）**。かつ「stage しない前提」が implementer.md に 0 件で権限的に stage 可能（context §偽陽性1）＝前提が担保されていない。
- **case-only rename**: case-insensitive FS × git の相互作用。case-sensitive 環境では発火しない。→ **環境依存の詰めの甘さ**（「git を oracle にする」選択の欠陥ではない）。方向 fail-closed。頻度極小・塞ぐコスト高。
- **両穴共通の第一原理**: どちらも fail-closed（偽陽性側）で、単発なら「捏造検出」目的に**安全側**（偽陰性より害が小さく、ユーザーゲート (B) で回復可能）。だが **頻度が上がると alert fatigue → Verification Theatre 化**（context §外部の既知落とし穴）。staged は発生条件が仕様上禁止されておらず頻度が読めないため、case-rename より優先度が高い。

### 反証・対立仮説の検討

- **反論1「6-3 は事象X（=L0 の捏造）を防げず、誠実な L0 を前提とする設計は自己矛盾。Verification Theatre だ」**: steelman すると、6-3 が動くには L0 の誠実な bash が要るのに、事象X はまさに不誠実な L0 の事例。**部分的に耐え、部分的に修正が要る**。耐える: 段4 の (b)(c) —— 事象X の L0 は嘘つきでなく誤認者で、誤認者は検証を避けないため 6-3 は混乱型捏造を捕捉しうる（「Theatre＝実効ゼロ」は言い過ぎ）。修正: resume 経路で 6-3 実行点がトリガーされる保証が弱い（context §「RESUME_MODE と API 中断継続は別レイヤー、6-3 は後者専用手当てなし」）。これが**真のギャップ**。6-3 が独立 checkbox を持つ設計（exp §6a）は resume 時に未完検知を助けるが、「delta 空でも checkbox だけ [x] にして進む」余地は残る。→ 修正方向: resume 時「6-3 checkbox 未完なら必ず実行してから先へ」の手順担保 + 究極は hook 錨。

- **反論2「fail-closed の偽陽性こそ executions 0 の実験を殺す。安全側どころか自滅」**: steelman すると、検証の信頼は偽陽性率に反比例し、(B) で通す学習が本物 PHANTOM も素通りさせる。しかも 6-3 は experimental track にすら未登録（context §統治の非対称）で偽陽性が観測されない。**部分的に耐える**。耐える: 既知偽陽性は 2 件に限定、両方発生条件明確で通常挙動では非発火。修正: staged は仕様禁止されず頻度不明 → 実集合に staged を含める修正で芽を摘む。かつ **「観測なしの本採用」は第一原理的に危うい ―― 偽陽性率という 6-3 の生命線が測定されない**。experimental 登録が筋。

- **対立仮説「6-3 不要。reviewer に『git diff を必ず取れ』と一行足せば同じ」**: 正しいとしたら別ステップは不要。**棄却**。reviewer は LLM 層で、git diff の結果自体を reviewer が捏造する余地が残る（reviewer も自己申告主体）。6-3 の価値は「決定論 bash が集合演算し、LLM の解釈を挟まず判定に使う」点。事象X の教訓は「LLM 層検証は捏造の下流で無力化される」。よって「決定論層を LLM 層の前に置く」ことに独立した価値がある。※ただし「決定論層は必要」と「6-3 という重い独立ステップが最小実装か」は別問題（過剰設計論点は別レンズ）。

### 二次・三次の含意と境界条件

- **含意1**: 6-3 採用で PIR² の検証は「決定論層（6-3）→ LLM 層（reviewer）」の二層になる。これは tester 等の他の自己申告境界にも展開できる一般パターン（W2+ の土台。ただし情報源フォーマット・スコープ粒度が違うためコード再利用は不可、技術＝git 集合演算パターンの再利用に留まる ―― context §問い2 と整合）。
- **含意2**: 錨が「L0 の bash 実行意志」単一点に集約されるので、次の投資の最適点は明白 = **その一点を hook で外部化**（W5 完成形と一致、W1 はその前段として整合）。
- **含意3（#7 プロセス自己言及）**: FIX-5/FIX-F（人間の fix 指示）が regression を作り後段レビューが捕捉した事実は「**検証の独立性は主体を選ばない**」原理の実例。捏造・誤りの出所が L2/L0/人間のいずれでも、独立観測は主体非依存に捕まえる。6-3 の思想（誰も信じず状態を見る）が自己整合的に機能した証拠で採用を支持。ただし人間 fix の誤りを捕まえたのは「後段レビュー」という別の独立層であり 6-3 ではない点に注意 ―― 検証網は多層で 6-3 は一層。
- **境界条件（6-3 が成り立たなくなる条件）**:
  - 脅威モデルが accident → adversarial に変わると N3（decoy edit: 実質ゼロだが痕跡だけ作る）で無力化。6-3 は集合の濃度・要素一致しか見ず、**「dirty である」と「申告どおりの実質変更である」は別物**（内容を一切見ない）。
  - case-insensitive FS 前提（macOS/Windows 既定）。
  - implementer が staging を使う運用に変わると staged 偽陽性が常態化。
  - resume 経路で 6-3 実行点がスキップされると空振り。
  - L0 が「6-3 を実行したふり」をする（原理的に hook でのみ錨づけ可能）。

### 現時点の確信度と残る不確実性

- **確信度: 高（論点A の線引きと oracle 健全性の切り分け）／中（resume 経路が真のギャップという判定）**。理由: 自己検証パラドクス・trust anchor・独立性条件は確立した第一原理で、bash 逐語から機序が直接読める。resume 経路の判定だけは該当手順（RESUME_MODE × 6-3 checkbox 相互作用）の逐語を確認できておらず context の記述に依拠。
- **残る不確実性**:
  - 偽陽性の実発生頻度（未測定。context §空白でも明記）。特に implementer の staging 実挙動は Claude 側未検証。
  - resume 経路で 6-3 が実際にトリガーされるかの実挙動（未観測）。
  - N3（decoy edit）が accident 脅威モデル下で本当に発火しないかは経験的裏付けがない（原理上は「LLM は検出回避目的でファイルを触らない」と推定するのみ）。
