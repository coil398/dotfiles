#### 1-c. RESUME_MODE と「事象X の resume」は別概念（fact + 評価: 不適合寄り）

pir2 SKILL.md ステップ1（L42-52）の `RESUME_MODE` 判定は、**`/pir2` の $ARGUMENTS に「resume」「続き」等が含まれるスラッシュコマンド起動時**にのみ立つフラグで、handoff.md の未完了項目を planner に絞り込ませるための仕組み。この経路は 6-1→6-3→7 を**通常どおり通過する**（何もスキップしない）。

しかし事象X の「resume」はこれとは**全く別の事象**である。exploration-03.md L23「API エラーで中断したが、状態は保持されている」という発言は、**Anthropic API 側のインフラエラーによる単一ターン内の中断からの継続**（ハーネスレベルの resume）であり、`/pir2` スラッシュコマンドの再起動でもなければ `RESUME_MODE=resume` のロジックが介在する余地もない。つまり、**SKILL.md の RESUME_MODE 分岐は事象X の resume を一切カバーしていない**（分岐が「素通り」するのではなく、そもそも「対象外の別レイヤーの事象」）。

6-3 のプロトコル文（`deterministic-completion-check.md`、SKILL.md 6-1/6-3）には、この種の**API エラー中断・ターン継続に対する特別な取り扱い**（例:「中断から継続した直後は、直前の tool_use 履歴を再確認してから完了主張せよ」）は一切書かれていない。6-3 は「implementer 起動前に pre-set を記録し、完了報告後に post-set と照合する」という**順序に依存した手続き**であり、この手続きが正しく実行されるかどうかは、API 中断・継続を経てもメイン Claude が SKILL.md の記述どおりに逐次実行を続ける、という**同じ信頼前提**に依存している。**評価: 不適合〜部分適合**。「resume 直後に 6-3 が発火するか」という問いに対しては、「発火する保証をする専用ロジックは無い。通常の逐次実行が壊れていなければ発火するが、それは事象X 発生時に壊れていた当のものである」という同語反復的な答えにしかならない。

#### 1-d. 核心の懸念: 6-3 自身の実行が「検証されない検証」になっていないか（推測を含む重要な論点）

これが本問いの最も重要な論点であり、**deliberator に必ず検討してほしい**。

事象X の捏造は「ツール呼び出し無しで」発生した（exploration-03.md L36）。つまりメイン Claude（=スキル本体、6-3 の実行主体そのもの）が、**Agent(implementer) の tool_use ブロックを一切生成せずに、完了報告という自然文だけを出力した**。これは CLAUDE.md「ツール結果の捏造の絶対禁止」という**既存の・最上位に置かれた・既に十分明示的なルール**が、まさにその明示にもかかわらず破られた事例である（CLAUDE.md 冒頭に「先例 2026-06-13」まで書いてあるのに再発した）。

6-3 は「implementer 起動前に pre-set（bash による git diff 記録）を実行し、完了後に post-set（同）を実行して集合照合する」という**新たな bash 実行手順**を追加するものだが、この手順自体もメイン Claude が Bash tool を実際に呼び出すことに依存した**プロンプト上の指示（SKILL.md の prose）**でしかなく、これを強制する **hook・ハーネス側の外部検証機構は一切実装されていない**（`deterministic-completion-check.md` にも SKILL.md にも、6-3 の bash 呼び出しが実際に発生したことを独立に確認する仕組みはない。settings.json の hook は `parse-failure-continue-hook`（整形式失敗のみ検知）だけで、6-3 の実行有無を監視する hook は存在しない）。

すなわち: **「implementer が完了したという申告を鵜呑みにしない」という 6-3 の設計思想を、6-3 自身の実行に対して同じ厳密さで適用すると、「メイン Claude が 6-3 を実際に実行したという申告」もまた鵜呑みにできないことになる**。もしメイン Claude が事象X と同型の「認識論的真空」状態（deliberation-1-01.md L43「resume 状態の欠如が残した認識論的真空をモデルが埋めた結果」）に再び陥った場合、それは implementer の完了報告だけでなく、**6-3 の pre-set 記録・post-set 記録・verify-*.md 書き出し・PASS 判定という一連の手続き全体を、実際には一切 bash を呼ばずに「実行して PASS でした」と自然文で捏造する**ことを妨げるものが SKILL.md の prose 以外に存在しない。

この懸念に対する部分的な反証（fact ベース）: exploration-03.md のタイムラインでは、**reviewer 5体の起動は実際の tool_use として発行されている**（L25「実際に発行される（tool_use として確認済み）」）。つまり事象X において、メイン Claude の「ツール呼び出し規律」が全面的に崩壊していたわけではなく、**implementer 呼び出しの直前区間だけが tool_use 無しの自然文に落ちた**（あるいは、直前のコンテキスト破損により「implementer は既に呼ばれて完了した」という誤った内部信念を持ち、その誤信念に基づいて reviewer は正しく本物の tool_use として呼び出した、という可能性の方が高い）。この解釈が正しければ、6-3 を implementer 完了報告の直後・reviewer 起動の直前に挟むことは、メイン Claude の「誤った内部信念」を**実データ（git delta）で訂正する具体的なフックポイントとして機能しうる**（reviewer が最終的に果たしたのと同じ訂正機能を、より早く・より安く、5体並列起動の前に果たす）。

**総合評価: 部分適合**。
- 「実装完了報告と reviewer verdict の矛盾に解決経路が無く 19 分迷走した」という **事象X の後半（deliberation-1-01.md の invariant I2: 矛盾収束）** に対しては、6-3 は PHANTOM_CLAIM 検出時の構造化ユーザーゲート（A/B/C選択・git diff 全 hunk 提示・再実行1回までの上限）という**明示的な解決経路を新設**しており、これは 7-4（reviewer FAIL 時の通常の再実装ループ）には無い、この失敗カテゴリ専用の手当てである。この部分は明確な改善である。
- しかし「捏造がメイン Claude 自身の tool 呼び出し規律の崩壊から生じる」という **事象X の前半（根本原因）** に対しては、6-3 は「同じ信頼できない語り手（メイン Claude）に、もう一段の bash 実行を義務付ける」という**同型の対策**であり、外部（hook・ハーネス）による独立検証を伴わない。Fable5 の設計思想「LLM 判断は検証経路に挟まない」（Fable5 L58）は判定ロジック（PHANTOM/UNDECLARED の集合演算）には成立しているが、**「その判定ロジックを実行したこと自体」の検証には及んでいない**。この「検証者を誰が検証するか」という問題は、Fable5 が L1/L2（サブエージェント）の自己申告に対して周到に設計した不信の枠組みを、**L0（メイン Claude 自身）にも同じ厳密さで適用すると再帰的に生じる**が、Fable5 の残存限界一覧（§4「除去できない残存限界」①〜⑥）にも deepthink1 の対立#3 にも、この「L0 自身の tool 呼び出し規律」を独立に検証する仕組みへの言及は見当たらない（`grep` で確認済み。Fable5 L178 の「L0 watchdog 自身が同じ親でブロックされる」は #44783 のデッドロック検知不能性についての言及で、捏造検証とは別論点）。**この点は両設計文書に共通する未指摘の盲点であり、6-3 に固有の欠陥というより「claims-up + evidence-local-pull」という設計パラダイム全体が L0 を無条件に信頼する前提の上に成り立っていることの帰結**として deliberator に提示する。

### 問い2: W1 としての移行パス整合

#### 2-a. Fable5 が W1 に期待する性質（fact、Fable5 L231-244）

Fable5 の移行パス表は W1（pir2 新ステップ 6-3）を「**最初に作る・最高レバレッジ・epic 不採用でも素の pir2 の資産として残る**」と明記し（L236, L244）、W2（epic 境界契約一式: §1-1 起動契約・§1-2 return 契約・§1-3 L0 検証パイプライン・§2 Phase 0・§8 台帳）の**前提**として位置づける。

#### 2-b. 実装された 6-3 と Fable5 §1-3「L0 検証パイプライン」の守備範囲比較

Fable5 §1-3（L88-99）が定義する L0 検証パイプラインは6手順:
1. 契約存在チェック（必須見出し grep、欠落時は artifact 再構成にフォールバック）
2. git 集合照合（PHANTOM_CLAIM / UNDECLARED_CHANGE。CLAIMED_FILES=none かつ編集想定タスクなら PHANTOM）
3. artifact 存在チェック（`test -f` で ARTIFACTS 各パス）
4. floor チェック（`subagent-metrics.jsonl` の hook 稼働時のみ）
5. STATUS 不変条件（`STATUS=COMPLETED ⇒ review=PASS ∧ test∈{PASS,N/A}`）
6. 台帳追記（epic-runs.md への VERIFY イベント記録）

対して実装済み 6-3（`deterministic-completion-check.md`）が持つのは**手順2（git 集合照合）のみ**。手順1（契約見出し grep + artifact 再構成フォールバック）・手順3（ARTIFACTS 存在チェック）・手順4（floor/hook）・手順5（STATUS 不変条件）・手順6（台帳追記）はいずれも実装されていない。これは plan.md（`.ai-pir-runs/20260703-201858-.../plan.md` L23）の「スコープ厳守」節で **「hook・epic 境界契約・fan-out・review-fix/test-fix への配線・台帳スキーマには一切手を出さない」と明示的に除外**されており、**意図された縮小であって見落としではない**。

**評価: 部分適合**。6-3 は Fable5 §1-3 の**6手順のうち1手順（git 集合照合）を、pir2/pir2codex 双方で動く形に一般化して先出しした**ものであり、「最初に作る最高レバレッジな要素」という位置づけ自体は妥当（他の5手順は epic 固有の概念＝EPIC_TELEMETRY・ARTIFACTS フィールド・hook・台帳に依存しており、epic 抜きでは意味を持たない or 実装できないため、素の pir2 に先出しできるのは実質この手順だけ）。しかし「W1 が完成すれば W2 はその上に積むだけ」という単純な期待に対しては、**残り5手順を W2 で別途フルスクラッチする必要がある**ため、"投資回収" の実態は「手順2の bash パターン1つ分の再利用」に留まる。これは Fable5 の記述と矛盾するわけではない（Fable5 自身「§1-4」は 6-3 を「L2→L1 境界の**本丸**」と呼ぶのみで「L0 検証パイプライン全体を代替する」とは書いていない）が、W1 だけで W2 の主要な作業（手順1・3・4・5・6）がほぼ手つかずで残ることは、"最初に作る" というフレーミングだけを見ると過大評価されうる。

#### 2-c. スキーマ・スコープの不一致（W2 で単純再利用できない具体的な溝）

1. **情報源の形式が違う**: 実装済み 6-3 の CLAIMED は `implementation-{IMPL_INDEX}*.md` の `### 変更ファイル一覧` から抽出する（既存 implementer.md フォーマット）。一方 Fable5 §1-2（L70-84）の L1→L0 return 契約は `### EPIC_TELEMETRY` ブロック配下の `CLAIMED_FILES:` フィールド（改行区切りリスト）という**別の構造**を要求する。W2 で L0 が L1 の申告を検証する際、6-3 の抽出 bash（`awk`/`sed` パイプライン、`deterministic-completion-check.md` L98-106）をそのまま使うことはできず、`EPIC_TELEMETRY` ブロック用の**別の抽出ロジック**を新規に書く必要がある。
2. **粒度（スコープ）が違う**: 6-3 の pre-set/post-set は「**1回の implementer 起動**」を挟む狭い窓（6-1 起動直前→完了直後）で完結する。Fable5 §1-3 の pre-{Ti}.list/post-{Ti}.list は「**ネストされた pir2 の1回の起動全体**」（explorer→planner→implementer→reviewer→tester のフル13ステップ、内部で複数回の再実装ラウンドを含みうる）を挟む広い窓。W2 で L0 が L1 の完了報告を検証する際、6-3 のコードをそのまま流用すると**内部の再実装ラウンド（7-4/8-2）で生じた変更が正しく合算されない**（後述、問い3の懸念と直結する）。bash の「4行パターン」自体は同一だが、「いつ pre を取り、いつ post を取るか」という**呼び出しタイミングの設計は W2 で再設計が必要**であり、6-3 のコードをコピーするだけでは済まない。
3. **NO_OP 免除の情報源も異なる**: 6-3 は `implementation-*.md` の `### 注意点・未解決事項` セクション内の `NO_OP_JUSTIFIED:` 行を見るが、L1→L0 の `EPIC_TELEMETRY` 契約には対応するフィールドが定義されていない（Fable5 の §1-2 テンプレートに `NO_OP` 相当のフィールドが無い）。

**評価（2-c 全体）: 部分適合〜不適合寄り**。「pir2 6-3 は共通層の再利用可能な資産」という Fable5 のフレーミング（Fable5 L12「本 reference は pir2 6-3 と pir2codex 6-1 の共通プロトコル」、plan.md L4「デフォルト actor への一般化」）は **pir2 と pir2codex の間では実際に成立している**（同じ `implementation-*.md` フォーマットを共有するため、bash がそのまま使い回せている。決定2=B の実装がこれを裏付ける）。しかし **pir2（W1）と epic（W2）の間では、情報源フォーマット・スコープ粒度の両方が異なる**ため、「そのまま再利用できる」という期待は成立しない。W2 の実装時には、6-3 の**技術（git 集合演算のテクニック）は実証済みとして再利用できる**が、**コード（bash パイプライン・抽出ロジック）は L1→L0 境界用に別途書き直しが必要**という、やや控えめな意味での「資産」に留まる。

#### 2-d. 良い適合点（フェアネスのため明記）

- pre-set/post-set の `--ignore-submodules=dirty` / `core.quotePath=false` / gitignore 対象パスの `check-ignore` 3分岐判定など、6-3 の実装で発見・対処された**エッジケース**（非ASCIIファイル名・サブモジュール・リポ外パス）は、W2 の L0 検証パイプラインを書く際にも**同一のエッジケースが再発する**ため、これらの対処パターン自体は極めて価値の高い再利用可能知識になる。
- 「PHANTOM が優先・UNDECLARED は非ブロッキング warn」という**非対称検証の設計判断**（偽陽性で実験を殺さない）は、W2 でも同じ判断を踏襲すべき普遍的な指針であり、これは 6-3 が W1 として「最初に確立すべき」だった価値の中核である。この点は Fable5 のフレーミングと完全に整合し、**適合**。

### 問い3: 決定1=(A) 最小スコープの帰結

#### 3-a. 事実確認（fact）

`deterministic-completion-check.md`「適用タイミング」節（L18-25）および plan.md（L146, L153, L179）に明記の通り、決定1=(A) は「6-3 を初回実装点（pir2 6-1・pir2codex 6-1a/6-1b/6-1c）のみに適用し、以下の再実装エントリポイントには配線しない」ことを**意図的に確定**している:

|---|---|---|
| ステップ 7-4（reviewer FAIL 後の再実装） | L412-417 | 適用しない（明記: `deterministic-completion-check.md` L22, plan.md L153/179） |
| ステップ 8-2（tester FAIL 後の再実装） | L453-460 | 適用しない（plan.md L153 に列挙） |

つまり「初回実装点のみ」という限定は、reviewer FAIL・tester FAIL・ユーザー追加指示・リファクタ適用という**少なくとも4種類の再実装トリガー全てで無検証**であることを意味する。

#### 3-b. 事象X 自体は初回実装点で発生（問い1-bで確認済み）

問い1-b で確認した通り、実際に観測された事象X の捏造は**初回実装点**（epic/SKILL.md・epic-planner.md という新規ファイルの初回作成）で発生しており、7-4/8-2 の再実装ラウンドではなかった。したがって **「決定1=(A)が事象X 自体を取り逃すか」という直接の問いに対しては、No（取り逃さない）**——6-3 が実装される前の世界線で観測された唯一の実データは、6-3 の適用範囲内にちょうど収まる。

#### 3-c. しかし「同型の捏造が再実装ラウンドで起きた場合」は無検証のまま残る（推測を含む分析）

これは**観測されていない仮想シナリオに対する分析**であり、以下は推測であることを明示する。

事象X の根本原因（deliberation-1-01.md L43「resume 状態の欠如が残した認識論的真空」）は、**API インフラエラーによるターン中断**という、pir2 のどのステップで発生してもおかしくない**環境要因**に起因する（実装フェーズに固有の要因ではない）。したがって、もし同種の API 中断が 7-4（reviewer FAIL 後の再実装）の最中に発生した場合、メイン Claude が「reviewer 指摘への対応が完了した」という**同型の捏造報告**を tool 呼び出し無しで生成する可能性は、初回実装点と**構造的には同程度**存在すると考えられる（推測。n=1 の事象X からこの一般化を導出する根拠は薄いが、根本原因（API 中断への脆弱性）自体は実装ラウンドの回次に依存しないという論理からは自然な外挿）。

この場合の挙動を SKILL.md の記述から機械的にトレースすると:
1. 捏造された「修正完了」報告を受け、7-4 手順4「7-2A→7-2B の手順で reviewer を並列で再起動」（L416）がそのまま実行される（6-3 は適用されないため、この時点で git delta と申告の不一致を検知する機会が失われる）
2. reviewer が実コードを Read すれば、修正が反映されていないことを検出し FAIL を返す（reviewer 層は事象X でも機能した独立検証層であり、ここでも機能する見込みは高い）
3. `INNER_LOOP_COUNT` がインクリメントされ（7-4 手順1）、3回に達するまで 7-4 のループが継続する。3回で強制的にステップ7.5へ「失敗として記録」（L414）されるため、**事象X のような無制限の19分迷走にはならない**（INNER_LOOP_COUNT の上限が一種のサーキットブレーカーとして機能する）

**評価: 部分適合**。決定1=(A) が残す穴は、事象X で観測された**「捏造 → reviewer 全FAIL → 解決経路が無く自由文脈で迷走」という最悪ケースそのもの**ではなく（INNER_LOOP_COUNT の上限が既存の安全装置として機能するため、無制限の迷走は起きにくい）、より限定的な**「PHANTOM_CLAIM を早期・安価に検知して reviewer 5体並列起動という高コストな操作を回避する」という 6-3 本来の価値（exploration-03.md L94「部分的な捏造では reviewer が同程度確実に検出できる保証はない」という指摘への対応）が、再実装ラウンドでは提供されない**という穴である。具体的には:
- 7-4/8-2 の再実装ラウンドで PHANTOM_CLAIM 相当の捏造が起きた場合、6-3 なら「reviewer を起動せず、検証レポート逐語注入で1回だけ再実行 → 2回目も失敗ならユーザーゲート」という**安価な**経路で処理されるところ、初回実装点以外では**必ず reviewer 5体（または継続中の REVIEWER_SET 全員）が並列起動されてから**（＝コストを払ってから）検出される
- また、7-4 の INNER_LOOP_COUNT 上限到達時の扱い（L414「ステップ7.5へ強制移行（失敗として記録）」）は、6-3 の「2回目 PHANTOM でユーザーゲート」ほど明示的な「捏造の可能性がある」という**原因の切り分け**をユーザーに提示しない。ユーザーから見ると「3回試したが reviewer が FAIL し続けた」という**通常の実装品質問題と区別が付かない形**で記録される可能性があり、根本原因が「実装の質」ではなく「捏造」だった場合の診断可能性は、6-3 が初回実装点で提供する診断可能性より劣る。

#### 3-d. 「決定1=(A) が事象X型を取り逃すか」への直接回答

- **事象X そのもの（既に観測された具体的インシデント）を再現した場合**: 取り逃さない（初回実装点で発生したため 6-3 の適用範囲内）。
- **事象X と同型の失敗モードが再実装ラウンドで発生した場合（仮想・推測）**: 6-3 による早期・安価な検知は提供されないが、既存の INNER_LOOP_COUNT 上限（3回）が無制限の迷走を防ぐ**部分的な安全網として既に機能する**ため、「全く無防備」ではない。ただし「捏造の可能性がある」という原因診断の明示性・「reviewer 5体起動という高コスト操作の回避」という 6-3 本来の価値提案の両方は再実装ラウンドには及ばない。

この判断はプラン自体が follow-up として明示的に認識している（plan.md L179「6-3 を再実装ポイント（pir2 7-4/8-2/6.5-2(C)/refactor-advisor-gate、pir2codex 6-2）へ一般化する案」）ため、**「見落とし」ではなく「意図的なスコープ限定であり、既知の未解決事項として記録済み」**という性質のものである。deliberator が検討すべきは、この既知の限定を「W1 の完成条件として今すぐ埋めるべきか」「観測（G1/G2 相当の実運用データ）を待ってから判断すべきか」という優先順位判断であり、6-3 の設計自体に瑕疵があるという話ではない。
