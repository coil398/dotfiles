# 図のレビュー手順

完成画像を観察し、読者が読み取る内容を確認する。作者の意図、コードの整然さ、配色の美しさだけを根拠に品質を判断しない。

## 入力と観察順序

対象画像とその版、掲載条件、元の要件、照合用データ・出典、掲載キャプションを受け取る。画像は実際に開く。画像の取得や表示に失敗した場合は、その事実と画像確認が未実行であることを返す。

1. **まず掲載サイズで観察する。** 画像から読み取れる中心的な主張、読む順序、主要な要素の関係を短く書く。説明を補わないと理解できない箇所を特定する。
2. **次に要件・根拠と照合する。** 読み取った主張が要件と一致するか、必須情報が欠けていないか、数値・関係が正しいかを確認する。
3. **原寸・拡大表示で原因を調べる。** 誤字、細部、描画不良を調べるために拡大してよい。ただし拡大すれば読めることを、掲載サイズで読める根拠にしない。
4. **対象の各表示幅を確認する。** モバイルの確認をデスクトップの結果で代用しない。表示した画像がツール側で拡大・縮小されていて実寸を判断できない場合、その制約を記録する。

「3秒で理解できる」等の時間目標を、計測していない性能結果として報告しない。

## 確認する内容

### 意味と正確性

- タイトル・本文・図から読み取れる主張が一致しているか。
- 矢印が処理順、情報の流れ、依存、因果のどれを示すか明確か。向きや線種の使い分けに矛盾がないか。
- 主要な要素と関係が揃い、省略によって別の仕組みに見えていないか。
- データ図では、元データとの対応、単位、期間、分母、軸、尺度、凡例、比較条件を照合する。必要な不確実性表示を消していないか、面積や長さが数値と矛盾していないかも見る。
- データや出典を取得できない部分は未確認とし、整った見た目から正確さを推測しない。

### 可読性と情報設計

- 掲載サイズで主要ラベルを読めるか。必須の意味が小さい注釈に隠れていないか。
- 概要、例、実装詳細が競合していないか。図外へ出すべき文章が箱の中に残っていないか。
- 主張から主要要素へ自然に視線が移るか。矢印の交差や長い戻り線が読み順を崩していないか。
- 余白が関係のまとまりを示しているか。空白を埋めるためだけの情報や装飾がないか。
- 色だけに意味を任せていないか。ラベル、配置、線種でも必要な区別を読めるか。
- モバイルでも主要な文字と関係を読めるか。全体を縮めるだけで読者に拡大操作を要求していないか。

### 描画・掲載の不具合

- 文字切れ、重なり、枠外へのはみ出し、欠けた矢印、凡例との対応ずれがないか。
- 日本語の字形、改行、数式、記号、フォント代替に問題がないか。
- 背景と文字・線の区別が十分か。画像単体では正常でも掲載先の背景や縮小で崩れていないか。
- キャプションと出典が実際の納品物・掲載状態に含まれているか。

機械的な測定と視覚的な判断を区別する。例えば、変形のない幅 1200 の図で文字サイズが 18、表示幅が 360 CSS px なら、表示時の字級は `18 × 360 / 1200 = 5.4 CSS px` となる。高解像度で書き出してもこの小ささは変わらない。個別の変形、CSS、フォント描画がある場合は実際の表示に基づいて確認する。

## 指摘と返却

各指摘は、対象画像と箇所、観察事実、読者への影響、最小修正、戻す工程を短く述べる。観察できたことと推測を混ぜない。修正案は必要情報を保持し、依頼された表示条件の中で成立するものにする。

例：

> 下段の実装説明はモバイル用プレビューでは判読できず、概要の矢印より文章が目立っています。本文へ移し、主図には構成要素と操作の流れを残します。情報の採否を変えるため Plan に戻します。

既存のレビュー形式がある場合はそれを使う。形式がなければ、読み取った主張、確認した画像・表示幅、修正が必要な問題、任意改善、未確認範囲と最終判断を簡潔に返す。数値スコアの平均で内容の誤りや判読困難を相殺しない。

指摘すること自体を目的にしない。問題がなければ、何を実際に確認したかを示して終了する。レビューのみの依頼では対象・ソース・共有 Skill を編集せず、結果を親へ返す。
