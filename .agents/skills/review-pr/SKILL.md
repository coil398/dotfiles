# Review PR — コードレビュー

PRまたは指定されたremote branchの変更を、`reviewer`親の配分・集約と`code-review-guidance`評価者の結果契約でレビューします。親はrepo、base、head、staged/unstaged/untrackedの境界を確定し、担当選定と最終判定を保持します。

**対象**: `$ARGUMENTS`（PR番号、ブランチ名、またはファイルパス。省略時は現在のstaged・unstaged差分）

---

## ステップ 0: プロジェクトメモリパスと RUN_DIR の確定

対象repoの実体、PR番号またはbranchのremote、base/head、取得時点を確認する。成果物を保存する場合だけ、親またはruntimeが渡した実在の`RUN_DIR`と`REPORT_PATH`を使用する。特定runtimeのhomeやmemory pathを推測しない。

```text
PROJECT_ROOT = 対象リポジトリの実体
RUN_DIR = 親またはランタイムが明示した場合だけ、その実在する保存先
REPORT_PATH = 親が明示した場合だけ、そのRUN_DIR配下の保存先
```

`/review-pr` は handoff 連携を行わないため、`HANDOFF_PATH` / `RESUME_MODE` は不要です。

---

## ステップ 1: 差分の取得

まず `$ARGUMENTS` から `--reviewers=<roles>` と `--all-reviewers` フラグを**抽出して除去**し、残りを対象指定として扱う。次にrepoとrefを確定して差分を取得する:

- **PR番号が指定された場合**: 対象repoのbase/headを確認し、`gh pr diff <番号>` で差分を取得する
- **ブランチ名が指定された場合**: 確定したremote branchとHEADのrefを確認し、明示したbase/headで差分を取得する
- **ファイルパスが指定された場合**: 該当ファイルを読み取る
- **引数なし**: 対象として明示された現在のstaged・unstaged・untracked差分を取得する

PRの変更をレビューする場合、PRのbase/headに対する差分へ現在のローカル変更を混ぜない。作業ツリーに混在があれば対象を分けて親へ示す。repo、base、headを確定できない、または取得不能な場合は変更なしやNOT_APPLICABLEにせず、未確認として返す。

取得した差分は、複数担当が同じ内容を参照する必要があり、かつ親が実在する保存先を選んだ場合だけ保存します。保存しない場合は、親が差分を直接渡します。変更ファイル一覧は実際の差分から取得します。

---

## ステップ 2: リスクに応じたレビュー

### 2-1: 観点の選定

必要なレビュー観点を決める。詳細な配分・独立性・result契約は`reviewer/SKILL.md`と、親が渡す実体の`code-review-guidance/SKILL.md`に従う:

1. `--reviewers=<roles>` があれば明示された観点集合を使う。`--all-reviewers`なら五つの基本観点を使う。両方がある場合は明示された観点指定を優先する。未知のroleは報告し、黙って無視しない。
2. 未指定時は差分、PR の説明、依頼、失敗時の具体的な実害から必要な観点を選ぶ。対象を確定できない場合は、観点を増やすのではなく blocker として報告する。
3. 選んだ観点と、それぞれを追加した根拠をユーザー提示または親の記録に含める。

- `correctness`: 要件、挙動、データ整合性、性能、回帰
- `consistency`: 既存パターン、命名、関連箇所の適用漏れ
- `quality`: 局所的な保守性、重複、テスト可能性、scope
- `security`: 認証・認可、入力、秘密情報、外部境界、権限
- `architecture`: API・schema、レイヤー、責務、依存境界
- `ui-ux`: UI変更は共有ui-ux基準で評価し、指定されたUI原本・スタック基準を追加で読む
- `reference-fidelity`: 実際の移植・再現・参照実装との照合を求める依頼または計画がある場合に選ぶ。単なるキーワードや参照元の存在だけでは必須化せず、参照pathが未提供または取得不能でも観点を外さずINCOMPLETEとして返す。

### 2-2: 起動と分担

各担当にはrepo、確定したbase/head、対象diff、PRの要件、受入条件、担当観点、実在する`code-review-guidance/SKILL.md`の絶対pathと対応reference、変更禁止範囲を渡す。独立した観点は並列化し、容量不足ならwaveを分ける。明示された独立観点を捨てず、waveでも完了できなければ未完了として返す。独立性が要求されない担当だけ、親が直接確認できる。

レビュー担当は対象ファイル、PR、既存のユーザー変更を変更せず、commit、push、生成、外部への書き込みを行わない。追加取得や権限が必要な場合は親へ戻す。

レビュー結果を保存する場合だけ、親またはランタイムが選んだ実在の保存先を事前に決める。保存しない場合はメッセージの返却を使い、未生成の path、未起動担当の verdict、架空の結果を作らない。

高リスク・破壊的変更、認証・認可、権限、秘密情報、データ損失、不可逆操作、外部または本番状態に関わる場合は、実装者から独立した該当観点を省略しない。低リスクの局所変更は、親の diff 照合と focused check で足りる場合がある。

---

## ステップ 3: 結果の統合・提示

起動した評価者の実際の結果と、保存した場合だけ実在するレポートを提示する。未起動の担当や未生成の成果物を補完しない。

### 判定

起動した担当の指摘を差分・仕様・再現・テストと照合する。P0/P1または要求不成立のP2以下が確認されれば`VERDICT: FAIL`。必須観点・資料・確認が残れば`VERDICT: INCOMPLETE`。必須範囲を確認し阻害問題がなければ`PASS`。対象がなく必要な評価でない場合だけ`NOT_APPLICABLE`とし、取得失敗・timeout・未読をこの値にしない。

### ユーザーへの提示フォーマット

```
## PR レビュー完了

### 対象
[PR番号 / ブランチ名 / ファイルパス]

### 全体 VERDICT
[PASS|FAIL|INCOMPLETE|NOT_APPLICABLE]

### REVIEWER_SET
[実際に確認した観点と選定理由]

### 観点別結果
[実際に起動した観点の結果。保存した場合だけ実在する成果物への参照を含める]

### COVERAGE
[complete|partial|none]

### 主な指摘事項
- [P0|P1|P2|P3] / [完了阻害か] `ファイル:行` — [問題の要約]（出典: [ROLE]）

### 未確認
- [範囲、理由、必要な入力または操作]
```

各評価者の結果を読み、根拠を再検証して同じ原因を統合する。担当外の重大度をLowへ落とさない。未確認範囲を必ず併記し、変更後は影響を受けた観点だけを再評価する。
