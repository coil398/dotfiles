# 記憶の棚卸し

cleanup を明示的に依頼されたときだけ、この資料を読む。自動 cleanup はしない。

## 候補

1. **重複候補** — ベクトル類似度が高い（例: cosine > 0.92）ペアを提示し、統合 or 片方削除を対話で決める
2. **stale 参照** — summary/context に含まれるファイルパス・シンボル名が実在しない記憶
3. **低スコア長期未使用** — `created_at > 90日` かつ `used_count = 0` かつ最近のクエリで上位に来ない記憶
4. **プロジェクト固有すぎる decision** — 他プロジェクトで再利用できないものをプロジェクトメモリへ移せるか検討する
5. **session-summary の粒度過多** — 1日に複数ある場合に1件へまとめる

## 実行フロー

1. 候補を最大 10 件抽出して提示する
2. 各候補について `keep / archive / delete / merge` を対話で決定する（自動判定はしない）
3. 実行結果を1件 episode に記録する（タグ: `cleanup-session`）
4. IDF のズレが大きい場合は `rebuild` を推奨する

粒度がまだ固まっていない段階ではオンデマンド実行を基本とする。自動 DELETE はせず、運用を自動化する前にオンデマンド cleanup の判断パターンを蓄積する。
