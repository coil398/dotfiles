# Deepthink：探索 → 熟考 → 統合 → 十分性確認

**状況・論点**: `$ARGUMENTS`

親は確定事実と制約の受け渡し、担当とモデルの選択、framing と結論がユーザーの依頼からずれていないかの照合、最終判断を所有します。問いの分解と探索範囲を誰が決めるかは方式ごとに第2節で定めます。deepthink は考えるための手順であり、ユーザーの依頼にない実装・外部操作・保存を開始しません。各runtimeの起動方法は、そのruntimeのnative入口に従います。

## 1. モデルと方式

最初に [references/model.md](references/model.md) をReadし、熟考・統合・十分性確認の担当へ渡すモデル指定を確定します。担当モデルは各runtimeの入口が定める既定に従います。ユーザーがモデルを名前で指定した場合（`--opus-panel` を含む）の識別子と受理失敗時の扱いは同referenceを正本とします。熟考を親の直接回答だけで完了させず、熟考担当は必ず独立したコンテキストで起動します。

| 方式 | 構成 | 選ぶ条件 |
|---|---|---|
| `single` | 選定モデルの熟考担当を1体。framing、探索単位の決定と探索、熟考、十分性の自己判定まで担当が行う | 熟考担当のモデルが Fable のとき |
| `panel` | 選定モデルの熟考担当を複数体、同じ入力から独立に並列起動。レンズを体ごとに割り当てる | 熟考担当のモデルが Fable 以外（Opus・Sol・Grok など）のとき。ユーザーが `--panel` / `--opus-panel` を明示した場合も使う |

引数のフラグ語は問いの文言から除きます。panel でも全担当に同じ選定モデルを使い、担当数はレンズ数で決め、数合わせで増やしません。担当の回答を相互参照させません。

設計判断（方式・規則・データの持ち方・実装全体へ波及する選択）を考えるときは、熟考担当と並べて、同じ依頼原文・確定事実・制約を `codex` Skill の相談（expert、`SANDBOX=read-only`）にも独立に渡し、両方の結論を親が突き合わせます。Codex には熟考担当の結果を渡さず、熟考担当にも Codex の結果を渡しません。突き合わせで食い違った点や片方だけが挙げた見落としは、根拠をコードで確かめてから採否を決めます。

モデル指定が受理されない、担当が途中終了する、Skillまたは入力を読めない場合は、親の直接回答・別方式・別モデルへ黙って切り替えず、原因・対象範囲・再開条件を `INCOMPLETE` として返します。

## 2. framing と rubric

framing は「何を決めるか」「考える範囲」「非対象」「既知の制約」「小問への分解」「観点」「rubric」「探索単位」を定めます。rubric はこの熟考が満たすべき成功条件で、gate が内容を照合できる言葉で書きます。形式、見出し、担当数、ファイル数を成功条件にしません。

- 照合できない例: 「深く考えられている」「十分に検討されている」
- 照合できる例: 「主要な選択肢が列挙され、各々の利点・欠点が根拠つきで示されている」「最有力の反論に応答している」「結論が依拠する前提と、それが崩れる条件が述べられている」「トレードオフが定量または具体で示されている」

### single

親はユーザーの依頼原文と、確定事実・制約（対象版、非対象、既存のユーザー決定、受入条件）だけを熟考担当へ渡します。親の仮説、候補、叩き台、推奨、親が先に狭めた問いや探索範囲は渡しません。framing は担当が作ります。

担当の返却を受けたら、親は framing と結論を依頼原文と照合します。依頼の一部が抜けている、依頼にない範囲へ広がっている、ユーザー決定と矛盾している場合は、そのずれだけを示して同じ担当に再検討させます。候補や結論の方向は示しません。

### panel

親が framing を作り、熟考に入る前に rubric を確定します。探索で問題の実像が変わったら、熟考に入る前に rubric を更新します。

### 共通

対象、対象版、既存資料、ユーザー決定、受入条件が不足していれば親が確認します。既に確定した事項を再質問せず、結果を実質的に変える未決定だけをユーザーへ返します。

## 3. 必要な探索

探索単位は、確かめないと結論が出ない事実を経路・資料・repository ごとに分けたものです。独立した単位ごとに runtime の read-only 探索担当を1体ずつ並列に起動します。

- single では熟考担当が自分の framing に沿って探索担当を起動します。runtime が担当からの探索担当起動を許さない場合は、担当が探索単位と各単位の問いを返し、親がその単位どおりに並列起動して結果をそのまま担当へ渡します。親は単位を削ったり統合したりしません
- panel では親が framing から探索の要否と単位を決めます。実在する入力だけで判断できるなら探索を省略します

起動する側は、探索担当へ単位の問い、対象版、範囲、確定事実、調査観点、編集禁止、返却事項と、実行者用手順 `research/references/explorer.md` の実体絶対pathを渡し、子自身にReadさせ、結果はチャットで受け取ります。自分の仮説や候補は渡しません。

- 調査観点: 既知の事実とその一次出典、対立する見解・未解決の論点、関連する先行事例（ローカルの資料・コードを含む）、情報の確実性
- 外部資料・ライブラリ仕様は必要なときだけ一次資料で確認し、出典を添えさせます
- MCP経由の外部ツールが必要なサブ論点は、使うツールと対象を渡します。ツール不足で失敗した場合は不足を明示して扱い、別経路で黙って補いません
- 探索担当へ report 保存、記憶追記、テスト生成、外部投稿を要求しません。情報不足・取得不能・タイムアウトを不具合の不存在や `PASS` に変換しません

panel では親が結果を一つの context に整理し、出典のある事実、出典が弱い情報、対立、空白を区別します。コードや設定値が結論の根拠なら、熟考担当が元ファイルを再探索せずに判断できるよう、該当箇所を逐語で引用します。

## 4. 熟考・統合・十分性確認のループ

役割referenceは親が内容をReadせず実体の存在だけを確認し、絶対pathを `SKILL_PATH` として対応する担当へ渡します。担当自身が渡されたreferenceをReadします。使わない役割のreferenceは読みません。

- 熟考担当: [references/deliberator.md](references/deliberator.md)
- 統合担当: [references/synthesizer.md](references/synthesizer.md)
- 十分性確認担当: [references/gate.md](references/gate.md)

single では熟考担当へ `deliberator.md`、`gate.md`、`research/references/explorer.md` の実体絶対pathを渡し、統合担当と十分性確認担当は起動しません。panel で親が統合や十分性確認を直接行う場合は、その役割の担当を起動せず、対応するreferenceを親がReadして適用します。十分性確認は省略しません。

担当への入力は、single では依頼原文、確定事実・制約、対象版、編集禁止、返却形式、`SKILL_PATH`、panel では問い、レンズ、context、rubric、対象版、編集禁止、返却形式、`SKILL_PATH` です。どちらでも親の仮説、候補、叩き台、推奨を入力に含めません。子へ親用の deepthink 進行手順を渡して同じ委任工程を再起動させません。

各ラウンドは次の順で進めます。single ではこの全工程を熟考担当が自分で回し、最終ラウンドの position と rubric 照合表を返します。panel では親が各担当を起動して回します。**ハードキャップは4ラウンド**です。

1. **熟考**: 1ラウンド目の既定レンズは次の3本です。single では framing の観点と合わせて担当が使い、panel ではレンズを体ごとに割り当てて同時に起動します。問題が広い場合はレンズ単位で増やします。
   - 第一原理・機序: 論点を基礎から組み立てて答えを導く
   - 反証・レッドチーム: 導かれつつある答えを攻撃し、対立仮説を steelman する
   - 二次波及・境界条件: 帰結・境界・前提が崩れる条件を洗う

   2ラウンド目以降は、前回 gate が挙げた `needs-thinking` の不足をレンズにし、前回の position と gate 結果を入力に加えます。
2. **統合**: 同じラウンドの熟考結果を一つの position にまとめます。合意、真の対立、未確認事項を保持します。single では担当の結論がそのまま position です。
3. **十分性確認**: `gate.md` の基準で rubric の各項目を position と根拠つきで照合し、1行目の `VERDICT:` で分岐します。
   - `VERDICT: PASS`: 全項目が充足し重大な欠陥がない。結果へ進む
   - `VERDICT: FAIL`: `needs-exploration` の不足は第3節の探索を追加して context へ追記し、`needs-thinking` の不足は次ラウンドのレンズにする
   - `VERDICT: INCOMPLETE`: 資料未取得・timeout・権限不足・Skill未読など内容以外の中断。原因を解消できる場合だけ同じラウンドの該当担当を再実行し、解消できなければ理由・対象範囲・再開条件を結果に残す

`FAIL` の間は不足に対応する探索・レンズを加えて次のラウンドへ進み、ハードキャップ前に親や担当の判断でループを打ち切りません。同じ入力で再実行するだけのラウンドは行いません。4ラウンド目でも `PASS` しない場合は、最新 position を未達項目つきの暫定結論として扱い、gate が未達とした基準を結果に明示します。`PASS` を捏造しません。明示された独立検討を親の一回の回答で置き換えません。

## 5. ユーザーへ返す判断

熟考で得た根拠で閉じられる論点（実行可能な検証で決まる事実、依頼範囲内の実施順・スコープの詰め）は、「ユーザー判断です」と投げずにループ内で詰めます。

次の判断は親も担当も代わりに決めず、選択肢として返します。

- ユーザーが留保した判断、嗜好や方針に依存する選択
- 依頼範囲外の操作、不可逆・高リスクな操作（push、破壊的削除、本番データ変更、外部公開など）

各選択肢には推奨、根拠、推奨が覆る条件を付けます。

## 6. 結果と保存

最終結果は、中間結果を読まなくても判断できる自己完結した返答にし、結論を先に置きます。

- 問いへの結論と確信度
- framing（何を決めたか、非対象、小問、探索単位）と、親が依頼原文との照合で差し戻した点
- 確認済みの根拠と出典
- 採用・却下した選択肢と主要な反論
- 前提と、それが崩れる条件
- 未解決の対立と残る不確実性
- 十分性（`PASS` / 未達項目つきの暫定結論 / `INCOMPLETE`）と rubric 照合表
- ユーザーへ返す判断（第5節）と、必要な次の確認
- 方式、使用モデル、ラウンド数、探索単位と探索担当の数

保存はユーザーまたは呼び出し元が保存先を指定した場合だけ行います。指定された親directoryの実在を確認し、その配下の今回未使用のファイルpathだけを使い、既存ファイルを上書きしません。context、position、gate 等の中間 artifact は後段の消費者がある場合に限ります。未指定の RUN_DIR、`.gitignore` の編集、プロジェクト内の report directory、メモリ、handoff、固定台帳を作りません。担当の結果は常にチャットで受け取り、保存は親が行います。

長期作業や中断からの再開では、呼び出し元が渡した既存の状態 path を再利用し、現在の問い、rubric、完了した確認、未完了の論点、次の操作を引き継ぎます。`続けて` だけを理由に完了済み工程を最初からやり直しません。

実際に保存した場合だけ保存先を返します。deepthink は commit、push、外部投稿、ユーザーの保留判断の代行をしません。
