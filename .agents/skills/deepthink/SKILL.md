# Deepthink — 探索 → 熟考 → 統合 → 十分性確認

複雑な状況や設計判断を、探索、独立した視点からの熟考、統合、根拠の確認で整理します。親が対話、要件、スコープ、計画、所有境界、統合、受入、最終判断を保持し、必要な作業だけを現在のランタイムが提供する委譲 primitive に渡します。委譲できない場合は親が直接行い、実行方式、人数、モデル、レポート形式を完了条件にしません。

**状況・論点**: $ARGUMENTS

各フェーズの担当と実行方式:

| フェーズ | 担当 | 実行方式 |
|---------|------|--------|
| 探索 | 必要な独立調査担当、または親 | ランタイムが提供する実行方式 |
| 熟考 | 必要な視点の担当、または親 | ランタイムが提供する実行方式 |
| 統合・十分性確認 | 親、または親が選んだ担当 | 親が利用可能な実行方式 |

> この workflow は特定の handoff、メモリ、保存先を前提にしない。

## 熟考方式の選択

熟考の視点数、並列化、推論強度は、問いの独立性、失敗時の実害、利用可能な容量から親が選ぶ。ユーザーが全観点を明示した場合は、利用可能な全観点を実施する。容量不足時は wave 分割または親による直接確認へ切り替え、形式だけで結果を破棄しない。

| 観点 | 実行方法 | 選択条件 |
|------|----------|----------|
| 独立した複数視点 | 現在のランタイムの委譲 primitive で並列または wave 実行 | 問いと容量から親が選ぶ |
| 単独視点 | 親が直接確認するか、1担当へ委譲 | 小さい問いや容量不足時 |

- 引数の追加オプションは呼び出し元が指定したものだけ解釈し、未指定のモデルや実行方式を推測しない。
- 推論の深さは、問いのリスクと必要な根拠に応じて親が選ぶ。
- 実行方式に失敗した場合は、原因と利用可能な代替経路を親に返す。

> 容量や実行方式による制約がある場合も、必要な観点を形式だけで省略しない。

## ステップ 0: 実行コンテキストの確認

対象、現在の status/diff、既存の入力、親から渡された保存先を確認する。長い run で記録が必要な場合だけ、親が選んだ安全な実在ディレクトリ内の未使用 path を使う。今回読み込んだ skill package の参照は、その `SKILL.md` の実体から相対解決し、特定ランタイムのホームディレクトリや別名のツールを推測しない。

---

## ステップ 1: 論点の framing と rubric ドラフト（オーケストレーター）

深く考えるには「何をもって十分か」を先に決める必要がある。親が状況・論点を分解し、必要なら今回の問いで確認すべき成功条件（rubric）を作る。rubric の保存は後続判断に役立つ場合だけ、親が選んだ安全な実在ディレクトリ内の未使用 path に行う。

rubric の各基準は、**gate が客観的に照合できる形**で書く（主観の入りにくい停止条件にするため）:

- ❌ 曖昧: 「深く考えられている」「十分に検討されている」
- ✅ 客観照合可能: 「主要な選択肢が N 個以上列挙され、各々の利点・欠点が根拠つきで示されている」「〈想定される最有力の反論〉に対して応答している」「結論が依拠する前提が明示され、それが崩れる条件が述べられている」「トレードオフが定量または具体で示されている」

rubric を保存する場合の最小フォーマット:

```markdown
## 成功基準（rubric）: [状況・論点]

### この熟考のゴール
[何に答えを出すのか。1〜2文]

### スコープ / 制約
- [考える範囲。考えない範囲。前提として与えられている条件]

### 充足基準（gate はこれを一項目ずつ客観照合する）
| # | 基準 | 充足の判定方法（何があれば充足か） |
|---|------|-----------------------------------|
| 1 | ... | ... |
| 2 | ... | ... |
```

> ℹ️ この時点の rubric は**ドラフト**。探索（ステップ2）で問題の実像が見えたら、ステップ3で確定させる。

## ステップ 2: 探索フェーズ

状況・論点を独立した問いに分ける価値がある場合だけ、現在のランタイムが提供する read-only 委譲 primitive へ調査を渡す。分離の利益が小さい場合や primitive がない場合は、親が直接調査してよい。

### 選択ルール

- 独立した問いが複数ある場合は、容量と実害に応じて並列または wave 実行する。固定の最低数・上限・モデルを完了条件にしない。
- ユーザーが全観点を求めた場合は、利用可能な全観点を実施する。
- 入力はユーザー要件、実在する対象・資料、必要な場合の一次資料に限定し、推測で補わない。

### 担当へ渡す内容

- 対象、問い、確認済み事実、受入条件、変更禁止範囲を渡す。
- 後続判断に必要な場合だけ、親が選んだ安全な実在ディレクトリ内の未使用 path へ結果を保存する。保存しない場合は返却内容を親が統合する。
- 実装・ファイル編集・git 状態変更をさせず、実在する根拠と不確実性だけを返す。外部資料を使う場合は参照 URL を添える。

### プロンプトに必ず含める調査観点

- 論点に関する既知の事実・定説・データ（一次情報の出典つき）
- 対立する見解・論争点・未解決の論点
- 関連する先行事例・類似ケース（ローカルの資料・コードにあれば含める）
- 情報の確実性（一次ソースか二次ソースか、どこまで裏が取れているか）

## ステップ 3: 集約・rubric 確定・必要な確認

### 3-1: 集約

実在する探索結果を親が読み、熟考の土台となる背景ブリーフへ統合する。結果を保存する場合は、親が選んだ安全な実在ディレクトリ内の未使用 path に新規作成する。

- 重複して報告された事実は1つにまとめる
- 出典のある事実と、出典が弱い/推測混じりの情報を仕分ける
- explorer 間で食い違う記述は「対立点」として明示する（潰さない）
- **情報密度を落とさない**: 熟考対象がコードや構造化データ（設定・スキーマ・SQL等）に及ぶ場合、プロセス要約だけで済ませず、必要な根拠を実データまたは正確な引用で残す。後続担当が元資料を再探索せず判断できるかを親が確認する。

`context.md` のフォーマット:

```markdown
## 背景ブリーフ（context）: [状況・論点]

### 確定的な事実（出典あり）
- [事実] — 出典: [URL / ファイルパス]

### 不確実・出典が弱い情報
- [情報] — [なぜ不確実か]

### 探索で見えた対立・論点
- [論点]: [どう割れているか]

### まだ埋まっていない空白
- [分かっていないこと]

### 詳細資料（逐語抜粋）
[コード/データが絡む熟考では、根拠となる関数の実装・実際のSQL・実際の設定値等をここにコードブロックで逐語収録する。「〜という実装がある（パス:行）」という要約止まりで済ませない]

\`\`\`[言語]
[実際のコード / データを逐語で貼る]
\`\`\`
```

### 3-2: rubric の確定

探索で問題の実像が変わっていれば、親が保持する rubric または計画へ基準を反映する（基準の追加・具体化・スコープ修正）。

### 3-3: 必要な確認

rubric と context の要点を親が確認する。設計選択、スコープ、未許可の外部・不可逆操作、権限不足など結果を実質的に変える判断が残る場合だけ、根拠と選択肢を示してユーザーへ確認を求める。形式や artifact の有無だけで停止しない。

確認結果を記録する場合も、親が選んだ安全な実在ディレクトリ内の未使用 path だけを使い、未生成の記録を後段の必須入力にしない。

## ステップ 4: 熟考と統合

必要な観点を、問いの不確実性と失敗時の実害に応じて検討する。不足が正しさ、安全性、権限、データ損失に関わる場合だけ、原因に対応する追加探索または熟考を行う。固定ラウンドや固定担当数を完了条件にしない。

### 4-a: 熟考

独立した観点を複数扱う場合は、現在のランタイムの委譲 primitive で並列または wave 実行できる。起動前宣言、同一メッセージ、特定の形式を要求しない。

各担当には状況・論点、確認済み事実、受入条件、担当視点、変更禁止範囲を渡す。担当は実装や状態変更を行わず、根拠、不確実性、反証、判断を返す。

- 状況・論点（$ARGUMENTS）と、親が選んだ担当視点を渡す。
- 必要な場合だけ、親が選んだ安全な実在ディレクトリ内の未使用 path へ結果を保存する。

視点は、第一原理、反証、境界条件、利用者影響など、今回の問いと実害に関係するものから選ぶ。特定のレンズ数、ラウンド、モデルを既定にしない。

### 4-b: 統合

親が実際に返された担当結果を読み、確認済み事実、異なる見解、根拠、残る不確実性を一つの position に統合する。独立した統合を委譲する場合も、現在のランタイムの primitive を使い、親が最終的に照合する。

- position を保存する場合は、親が選んだ安全な実在ディレクトリ内の未使用 path に新規作成する。保存しない場合は親の受入判断に必要な返却内容を直接使う。

### 4-c: 十分性確認

親が position を、事前に定めた成功条件、実在する根拠、リスク、未解決事項と照合する。必要な場合だけ、現在のランタイムの read-only 委譲 primitive で独立確認を追加する。

- 独立確認を委譲する場合は対象、成功条件、変更禁止範囲、返却事項を渡す。未生成の verdict や artifact を作らない。

### 4-d: 不足時の対応

成功条件との照合で不足が見つかった場合は、影響する問いだけを追加確認する。

- 正しさ、安全性、権限、データ損失に関わる不足は、原因に対応する追加観測またはユーザー判断へ戻す。
- 非致命的な不足は、残る不確実性として親が明示して先へ進める場合がある。
- 形式、担当数、ラウンド数、artifact の有無だけで有効な結果を破棄・停止しない。未確認事項や未生成の結果を PASS として補完しない。

## ステップ 5: 結論の記録

到達した結論、根拠、トレードオフ、残る不確実性、十分性の判断を、必要な場合だけ一つのレポートに統合する。保存する場合は、親が選んだ安全な実在ディレクトリ内の未使用 path に新規作成する。

### 自己完結の原則（最重要）

読者が中間ファイル（context / deliberation-* / position-* / gate-*）を一切開かなくても、**この1本だけで結論・論拠・トレードオフ・残る不確実性・十分性の判定まで意思決定できる**ように書く。要約に痩せさせない。結論を最上部に置く（逆ピラミッド）。

### テンプレート

実際に存在する探索結果、担当結果、position、確認結果を読み、詳細を転記する:

```markdown
# [状況・論点] 熟考レポート

_作成: YYYY-MM-DD_

> 📌 このファイルは single source of truth。中間成果物を読まなくても、この1本で意思決定できるように書いてある。

## 0. Overview（結論先出し）
- 到達した結論・その確信度・最重要の論拠・残る最大の不確実性を数行で。**ここだけ読めば掴める**ように。
- 十分性: [成功条件を満たした根拠 / 未達・未確認の項目]

## 1. 論点・背景・成功基準
[状況・論点、なぜ考えるのか、rubric（判定に使った成功基準）]

## 2. 探索で分かったこと（context）
[context.md の事実・不確実情報・対立・空白を根拠つきで転記]

## 3. 熟考の到達点（position）
[position の結論・主要な論拠・統合の過程を転記。多様なレンズがどう噛み合ったか]

## 4. 未解決の対立・残る不確実性
[潰しきれなかった対立、依存する前提、崩れる条件、まだ確かめられていないこと]

## 5. 成功条件の確認
[成功条件ごとの根拠、未達、未確認を明示]

## 付録: 実在する資料 / 探索出典
[実際に使った資料・保存先・主要出典 URL。存在しない path や担当結果は書かない]
```

### 保存先

- 呼び出し元または親が指定した安全な実在ディレクトリ内の、今回まだ使われていない path に新規作成する。
- 保存しない場合は、実際に確認した内容をチャットで返す。未生成の path を報告しない。

```
## Deepthink 完了サマリー

### 論点
[状況・論点]

### 熟考レポート
[保存した場合だけ、実在する path]

### 到達した結論
[1〜3文。position の結論]

### 十分性
- 結果: [成功条件を満たした / 未達・未確認あり]
- 根拠: [実際に確認した事実・資料]
- （未達・未確認がある場合）項目: [要点と理由]

### 実施範囲
- 観点・担当: [実際に確認した範囲]
- 追加確認: [実際に行った内容。なければ none]

### 未解決の対立・残る不確実性
- [あれば。無ければ「特になし」]

### 未確認事項・blocker
[なければ none]
```
