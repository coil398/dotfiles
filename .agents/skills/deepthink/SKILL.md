# Deepthink — 探索 → 熟考 → 統合 → 十分性確認

**状況・論点**: `$ARGUMENTS`

親が問い、スコープ、成功条件、担当、モデル、統合、最終判断を所有します。deepthink は考えるための手順であり、ユーザーの依頼にない実装・外部操作・保存を開始しません。各runtimeの起動方法は、そのruntimeのnative入口に従います。

## 1. モデルと方式

最初に [references/fable-model.md](references/fable-model.md) をReadし、熟考・統合・十分性確認の担当へ渡すモデル指定を確定します。既定は Fable 5.1 です。ユーザーが Opus 5.5 を指名したとき（`--opus-panel` を含む）だけ Opus 5.5 を使います。モデル識別子、effort、受理失敗時の扱いは同referenceを正本とし、短名・別名・代替モデルを使いません。熟考を親の直接回答だけで完了させず、熟考担当は必ず独立したコンテキストで起動します。

| 方式 | 構成 | 選ぶ条件 |
|---|---|---|
| `single` | 選定モデルの熟考担当を1体。全レンズを一つの入力へ渡す | 既定 |
| `panel` | 選定モデルの熟考担当を複数体、同じ入力から独立に並列起動。レンズを体ごとに割り当てる | ユーザーが `--panel` / `--opus-panel` や複数の独立視点を明示した場合、または反証・トレードオフを分けて回収する実益がある場合 |

引数のフラグ語は問いの文言から除きます。panel でも全担当に同じ選定モデルを使い、担当数はレンズ数で決め、数合わせで増やしません。担当の回答を相互参照させません。

モデル指定が受理されない、担当が途中終了する、Skillまたは入力を読めない場合は、親の直接回答・別方式・別モデルへ黙って切り替えず、原因・対象範囲・再開条件を `INCOMPLETE` として返します。

## 2. framing と rubric

親は問いを「何を決めるか」「考える範囲」「非対象」「既知の制約」に分け、この熟考が満たすべき成功条件（rubric）を作ります。rubric は gate が内容を照合できる言葉で書きます。形式、見出し、担当数、ファイル数を成功条件にしません。

- 照合できない例: 「深く考えられている」「十分に検討されている」
- 照合できる例: 「主要な選択肢が列挙され、各々の利点・欠点が根拠つきで示されている」「最有力の反論に応答している」「結論が依拠する前提と、それが崩れる条件が述べられている」「トレードオフが定量または具体で示されている」

対象、対象版、既存資料、ユーザー決定、受入条件が不足していれば親が確認します。既に確定した事項を再質問せず、結果を実質的に変える未決定だけをユーザーへ返します。探索で問題の実像が変わったら、熟考に入る前に rubric を更新します。

## 3. 必要な探索

実在する入力だけで判断できるなら探索を省略します。不足があり独立した調査に価値がある場合だけ、runtime の read-only 探索担当へ具体的なサブ論点を渡します。独立したサブ論点は並列に起動します。担当には対象版、範囲、確定事実、調査観点、編集禁止、返却事項と、実行者用手順 `research/references/explorer.md` の実体絶対pathを渡し、子自身にReadさせ、結果はチャットで受け取ります。

- 調査観点: 既知の事実とその一次出典、対立する見解・未解決の論点、関連する先行事例（ローカルの資料・コードを含む）、情報の確実性
- 外部資料・ライブラリ仕様は必要なときだけ一次資料で確認し、出典を添えさせます
- MCP経由の外部ツールが必要なサブ論点は、使うツールと対象を渡します。ツール不足で失敗した場合は不足を明示して扱い、親が別経路で黙って補いません
- 担当へ report 保存、記憶追記、テスト生成、外部投稿を要求しません。情報不足・取得不能・タイムアウトを不具合の不存在や `PASS` に変換しません

親は結果を一つの context に整理し、出典のある事実、出典が弱い情報、対立、空白を区別します。コードや設定値が結論の根拠なら、熟考担当が元ファイルを再探索せずに判断できるよう、該当箇所を逐語で引用します。

## 4. 熟考・統合・十分性確認のループ

役割referenceは親が内容をReadせず実体の存在だけを確認し、絶対pathを `SKILL_PATH` として対応する担当へ渡します。担当自身が渡されたreferenceをReadします。親が統合や十分性確認を直接行う場合は、その役割の担当を起動せず、対応するreferenceを親がReadして適用します。使わない役割のreferenceは読みません。

- 熟考担当: [references/deliberator.md](references/deliberator.md)
- 統合担当: [references/synthesizer.md](references/synthesizer.md)
- 十分性確認担当: [references/gate.md](references/gate.md)
- モデル契約: [references/fable-model.md](references/fable-model.md)

担当への入力は、問い、レンズ、context、rubric、対象版、編集禁止、返却形式、`SKILL_PATH` です。子へ親用の deepthink 進行手順を渡して同じ委任工程を再起動させません。

各ラウンドは次の順で進めます。**ハードキャップは4ラウンド**です。

1. **熟考**: 1ラウンド目の既定レンズは次の3本です。`single` では全レンズを1体に渡し、`panel` ではレンズを体ごとに割り当てて同時に起動します。問題が広い場合はレンズ単位で増やします。
   - 第一原理・機序: 論点を基礎から組み立てて答えを導く
   - 反証・レッドチーム: 導かれつつある答えを攻撃し、対立仮説を steelman する
   - 二次波及・境界条件: 帰結・境界・前提が崩れる条件を洗う

   2ラウンド目以降は、前回 gate が挙げた `needs-thinking` の不足をレンズにし、前回の position と gate 結果を入力に加えます。
2. **統合**: 同じラウンドの熟考結果を一つの position にまとめます。合意、真の対立、未確認事項を保持します。
3. **十分性確認**: rubric の各項目を position と根拠つきで照合し、1行目の `VERDICT:` で分岐します。
   - `VERDICT: PASS`: 全項目が充足し重大な欠陥がない。結果へ進む
   - `VERDICT: FAIL`: `needs-exploration` の不足は第3節の探索を追加して context へ追記し、`needs-thinking` の不足は次ラウンドのレンズにする
   - `VERDICT: INCOMPLETE`: 資料未取得・timeout・権限不足・Skill未読など内容以外の中断。原因を解消できる場合だけ同じラウンドの該当担当を再実行し、解消できなければ理由・対象範囲・再開条件を結果に残す

次のラウンドは新しい観測、修正、反証、または未解決原因の識別がある場合だけ行い、ラウンド数を完了条件にしません。4ラウンド目でも `PASS` しない場合は、最新 position を未達項目つきの暫定結論として扱い、gate が未達とした基準を結果に明示します。`PASS` を捏造しません。明示された独立検討を親の一回の回答で置き換えません。

## 5. ユーザーへ返す判断

熟考で得た根拠で閉じられる論点（実行可能な検証で決まる事実、依頼範囲内の実施順・スコープの詰め）は、「ユーザー判断です」と投げずにループ内で詰めます。

次の判断は親も担当も代わりに決めず、選択肢として返します。

- ユーザーが留保した判断、嗜好や方針に依存する選択
- 依頼範囲外の操作、不可逆・高リスクな操作（push、破壊的削除、本番データ変更、外部公開など）

各選択肢には推奨、根拠、推奨が覆る条件を付けます。

## 6. 結果と保存

最終結果は、中間結果を読まなくても判断できる自己完結した返答にし、結論を先に置きます。

- 問いへの結論と確信度
- 確認済みの根拠と出典
- 採用・却下した選択肢と主要な反論
- 前提と、それが崩れる条件
- 未解決の対立と残る不確実性
- 十分性（`PASS` / 未達項目つきの暫定結論 / `INCOMPLETE`）と rubric 照合の要点
- ユーザーへ返す判断（第5節）と、必要な次の確認
- 方式、使用モデル、ラウンド数、追加探索の有無

保存はユーザーまたは呼び出し元が保存先を指定した場合だけ行います。指定された親directoryの実在を確認し、その配下の今回未使用のファイルpathだけを使い、既存ファイルを上書きしません。context、position、gate 等の中間 artifact は後段の消費者がある場合に限ります。未指定の RUN_DIR、`.gitignore` の編集、プロジェクト内の report directory、メモリ、handoff、固定台帳を作りません。担当の結果は常にチャットで受け取り、保存は親が行います。

長期作業や中断からの再開では、呼び出し元が渡した既存の状態 path を再利用し、現在の問い、rubric、完了した確認、未完了の論点、次の操作を引き継ぎます。`続けて` だけを理由に完了済み工程を最初からやり直しません。

実際に保存した場合だけ保存先を返します。deepthink は commit、push、外部投稿、ユーザーの保留判断の代行をしません。
