# Planner — 親の計画手順

親が計画を作成・更新するときに読みます。計画は親が確認した依頼、対象版、既存計画、探索結果、要件、所有境界から作り、計画作成そのものを別担当へ委譲しません。独立した事実確認が必要な場合だけ、具体的な問いを読み取り専用の探索担当へ渡し、返却を親が対象コードと照合します。

計画には、目的・非目的、確認済み事実、対象ファイルと排他的所有、依存DAG、実装順、各ステップの完了条件、focused check、リスク、未解決事項を含めます。既存計画がある場合は完了項目と決定事項を保持し、影響箇所だけ増分更新します。推測した対象や未確認の検証結果を事実として書きません。

計画を整理するときの形:

```markdown
## プラン: [タスク]
### 目標 / 非目標
### 確認済み事実と根拠
### 実装ステップ
| # | 対象・所有 | 依存 | 完了条件 | focused check |
|---|---|---|---|---|
### リスク・復旧
### 未解決事項とユーザー判断
```

## 構造投資領域とテスト接続

同一インターフェース・同じ書き味のクラスファミリー、戦略、状態機械、DSLなどが3個以上並ぶ領域は、構造投資領域として扱います。新機能の追加先がその領域なら、既存形式のN+1番目として追加する案を少なくとも一つ選択肢に含めます。物理信号、boolフラグ、既存式への条件追加だけを最初から採用せず、N+1案を工数・複雑度・影響範囲と比較します。N+1案から逸脱する場合は、工数または複雑度が明らかに過大である根拠を示し、結果を変える判断ならユーザーへ確認します。

新規テストを計画する場合、まず既存のTest関数と、そこから使えるseed helperの有無を確認します。既存のseed helperを使うTest関数がある場合は、別のTest関数へ分散させず、そのスイートへサブテストとして合流する前提で計画します。サブテスト名の衝突はprefixなど既存規約に沿って避けます。ORMの自動マイグレーション対象へ新規テーブルを追加し、実装コードが書き込む場合は、テストseed用のCreate helperも対応させます。これを欠くと、本番では値が入る一方でテストでは0になり、既存のgoldenや期待値が壊れます。
