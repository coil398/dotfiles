# Writing-plan — 計画・実装・記録

**タスク**: `$ARGUMENTS`

親がユーザー対話、要件、対象、計画、スコープ、依存、所有、統合、受入、最終判断を所有します。専任のplannerや固定runnerを必須にせず、独立した調査・実装・レビューだけを現在のruntimeの委譲機構へ渡します。

## 1. 計画

開始時に依頼、現在の対象版/status/diff、既存計画、関連コード、成功条件を確認します。要件を変える未決定だけをユーザーへ確認し、既に確定した事項を再質問しません。`--deepplan` が明示された場合だけ deepplan を使い、結果を親が対象コードと再照合します。

計画には以下を含めます。

- 目標、非目標、確認済み事実、受入条件
- 対象ファイル、排他的所有、変更禁止範囲、依存順
- bite-sized な実装ステップと各ステップの完了条件
- 変更された挙動に対応する focused check、レビュー、テスト
- 主要リスク、復旧方法、未解決事項

既存の計画・ユーザー資料がある場合、完了項目・決定事項・対象版を保持し、影響箇所だけ増分更新します。設計評価を存在しないコードdiffの評価へ変換しません。計画だけの依頼では、計画と残る判断を返して実装を開始しません。

## 2. 記録

後続実装が参照する、またはユーザーが保存を求めた場合に、親が計画記録を作成・更新します。保存先は既存方針または親が指定した親directoryの実在を確認したうえで、その配下の今回未使用のファイルpathに限定し、未指定のRUN_DIR、handoff、台帳、空のreportを推測・先行作成しません。通常は次の形を使います。

```markdown
# [タスク] 実装記録
_作成: YYYY-MM-DD | ステータス: 進行中_
## 目標
## 実装計画
- [ ] ステップ 1: ...
## 設計詳細
## 実装ログ
## 未確認事項
```

## 3. 実装と委譲

小さく密結合した変更は親が直接行います。独立単位を委譲するときは、目的、確認済み事実、対象版、所有範囲、制約、編集権限、完了条件、focused check、返却事項を渡します。担当同士の再委譲、無断の計画変更、所有範囲外の編集を前提にしません。readerには保存、記憶追記、コード変更、テスト生成を要求しません。

親は各ステップ後にstatus、対象diff、実在ファイル、受入条件、実行結果を照合します。担当の自己申告や終了コードだけで受入しません。ユーザーや他担当の未コミット変更を戻さず、明示範囲外のreset、restore、checkout、stash、commit、push、外部投稿を行いません。

## 4. レビューとテスト

レビューは差分と失敗時の具体的な実害から必要な観点だけ選びます。固定の全観点・人数・起動順・ラウンドを既定にしません。必要に応じて correctness、consistency、quality、security、architecture、ui-ux、reference-fidelity を使い、独立性が実害の検出に効く場合だけ別担当へ分けます。

テストは変更した挙動、回帰、公開契約、権限、生成物などのリスクに対応する既存または focused check を選びます。実行結果、未確認範囲、対象版を記録します。reader評価・テスト・runnerが失敗した場合、未完了をPASSへ変換せず、原因を特定して影響範囲だけ修正・再確認します。同じ原因を根拠なく繰り返しません。

## 5. 完了

要求された変更、必要なレビュー、必要な検証が完了したら記録を完了に更新します。任意の改善、追加規則、全体再点検を完了条件へ加えません。完了報告には実装記録の実在 path、変更ファイル、実施した確認、未確認事項を示します。未完了、権限不足、取得不能、明示モデル不在が残る場合は `INCOMPLETE` として次の操作と理由を記録します。

参照する専門手順が必要な場合は、`references/planner.md` を親が確認し、担当へ渡す内容へ必要な部分だけ反映します。plannerは親の計画・受入・ユーザー判断を置き換えません。
