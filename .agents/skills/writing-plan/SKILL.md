# ライティングプラン — 計画 → 実装 → 記録

**タスク**: $ARGUMENTS

計画書を作成し、実装結果と検証結果を追記して実装記録にする。親（main）はユーザーとの対話、探索、要件、計画、scope、依存関係、所有境界、統合、受入、最終判断を持つ。専任の plan 担当を前提にせず、担当が計画や受入を置き換えない。

## 1. 計画の作成

開始時に依頼、現在の status/diff、関連コード、既存パターン、成功条件を確認する。要件が曖昧で結果が変わる設計判断が残る場合だけ brainstorm または追加の対話を使う。`--deepplan` が明示された場合だけ deepplan スキルを読み込み、結果を親が対象コードと再照合する。通常は親が計画を作る。

計画には、次を実装可能な粒度で含める。

- 目標、非目標、確認済みの事実
- ステップごとの対象ファイル、排他的所有、変更禁止範囲
- 依存順序、完了条件、変更した挙動に対応する検証
- 主要なリスク、復旧方法、追加調査またはユーザー判断が必要な条件

ユーザーが提示した計画や既存の計画がある場合は、完了項目と決定済み事項を保持し、影響する箇所だけを更新する。計画全体を破棄して作り直さない。計画・記録の作成自体はこのスキルの目的だが、作業用の一時 report、handoff、台帳を別途固定しない。

## 2. 実装記録の初期化

`docs/plans/` がなければ作成し、`docs/plans/YYYY-MM-DD-<feature>.md` に次を保存する。保存先はユーザーに提示する。既存ファイルと衝突する場合は勝手に上書きせず、別名を選ぶか親が判断する。

```markdown
# [タスク名] 実装記録

_作成: YYYY-MM-DD | ステータス: 進行中_

## 目標

[タスクの概要]

## 実装計画

- [ ] ステップ 1: [ステップ名]
- [ ] ステップ 2: [ステップ名]

## 設計詳細

[対象、変更理由、依存関係、受入条件、検証方法]

## 実装ログ
```

brainstorm の設計書や、ユーザーが指定した既存資料がある場合は参照先を記録する。追加の一時パスは、長い run で実益がある場合にのみ親が選ぶ。

## 3. ステップごとの実装と記録

各ステップについて、親が次を行う。

1. 対象、所有範囲、完了条件、依存が満たされているか確認する。
2. 全体文脈と密結合した小変更は直接実装し、独立した明確な単位は現在のランタイムの委譲機構へ渡す。複数単位を並列化するのは所有ファイル、共有契約、生成物、lockfile、共通 helper、実装順序が分離され、親が統合確認できる場合だけにする。
3. 委譲時は目的、確認済み事実、許可・禁止範囲、維持する制約、終了条件、focused check、返却事項を渡す。担当が別担当を勝手に起動したり、計画を変更したりしない。
4. status、対象 diff、実在する変更ファイル、完了条件、実行結果を親が照合する。自己申告や終了コードだけで受入しない。
5. 計画の checkbox を更新し、実装内容、変更ファイル、実施した確認、未確認事項をこの記録の実装ログへ追記する。

既存のユーザーまたは他担当の未コミット変更を保全し、所有範囲外の差分を戻さない。`reset`、`checkout`、`restore`、`stash`、自動的な revert、commit、push は、ユーザーが明示した範囲を除き行わない。

## 4. リスクに応じたレビューとテスト

レビュー観点は各ステップの実差分と失敗時の具体的な実害から選ぶ。`--reviewers=<roles>` が明示された場合は有効な指定を使い、`--all-reviewers` が明示された場合は利用可能な全観点を使う。未指定時に全観点、固定人数、特定の起動順、起動前宣言を既定にしない。

- correctness: 要件、制御フロー、データ整合性、回帰
- consistency: 既存パターン、命名、関連箇所の適用漏れ
- quality: 局所的な保守性、重複、テスト可能性、scope
- security: 認証・認可、入力、秘密情報、外部境界、権限
- architecture: API・schema、レイヤー、責務、依存境界

小さな文書・機械的変更は、親の diff 照合と focused check で足りる場合がある。公開挙動、複数モジュール、生成物、永続化、入力・権限境界に影響するステップは該当する review/test を追加する。高リスク・破壊的変更では、実装担当と独立した review と実動作確認を省略しない。security、権限、データ損失、不可逆操作、外部または本番状態の確認を人数や形式の理由で削らない。

テストは変更した挙動と防ぐ実害から選び、プロジェクトの必須検証、再現・回帰、静的・構文・設定、必要な利用側・生成整合性を実行する。フルスイートは影響範囲またはプロジェクト規約が必要とする場合だけにする。独立 tester が有効な変更では使い、実装担当の自己申告で代替しない。

レビューやテストの FAIL は、報告と実差分を照合して根本原因を特定し、影響する最小修正を行う。修正後は影響した観点と挙動だけを再確認し、無関係な PASS 済み確認を機械的に全再実行しない。同じ呼び出しが原因不明のまま続けて失敗したら3回目を試さず、実測した blocker と必要な判断を記録する。原因が特定され、変更で成功する合理的な根拠がある場合だけ再試行する。

## 5. 最終化

すべての要求ステップと必要な確認が完了したら、ステータスを完了にし、総括へ実際のレビュー観点、テスト、未確認事項を追記する。未完了や判定不能な項目がある場合は完了にせず、次の作業と blocker を記録する。計画書の削除や移動はユーザーの確認後に行う。

```markdown
## 総括

- 完了ステップ数: N/N
- 実行したレビュー: [観点と結果。不要なら理由]
- 実行したテスト: [挙動と結果]
- 未確認事項・blocker: [なければ「なし」]
```

完了報告は、タスク、実装記録の実在するパス、変更ファイル、実施したレビューとテスト、未確認事項・blocker を簡潔に示す。未起動の担当、未生成の artifact、推測の verdict を補完しない。
