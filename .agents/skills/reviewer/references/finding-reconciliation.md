# 指摘の事後照合

reviewer・refactor-advisor・外部 PR bot の指摘を採用・却下する前に、親が行う照合手順。評価者は単一の差分だけを見ていて、直前の会話で確定したユーザー方針や実測結果を持たない。その文脈を持つのは親だけなので、無批判に転送せず、親が照合してからユーザーへ示す。

## 照合する3点

1. **直前の実測との照合**：親がコマンド実行・ファイル読み取り・検索などで確認した事実と、指摘が矛盾していないか。
2. **ユーザーの明示判断との照合**：ユーザーが「これは触らない」「この仕様で OK」と明示した範囲を、指摘が「直すべき」としていないか。
3. **確定した方針との照合**：計画段階でユーザーが明示的に承認した方針を、指摘が無自覚に否定していないか。

## 却下根拠の出どころを先に確認する

矛盾と判定する前に、却下の根拠が親自身の出力に由来していないかを確認する。

- 親がブリーフ・計画・担当への指示に書いた記述（「既存パターン準拠」「この設計で確定」など）は、照合に使う事実ではなく、指摘が争っている当の主張である。却下に使わない。
- 却下に使えるのは、(a) 親の出力の外にある一次情報（`path:line`、コマンドの実行結果、実測値）と、(b) ユーザー本人の明示発話の2つだけ。
- どちらも用意できない指摘は却下せず、指摘と論点をユーザーに示す。
- `NEEDS_USER_DECISION` / `USER_DECISION_REQUIRED` は親の判断で閉じない。閉じられるのはユーザーの発話だけ。
- 「確定した方針」は、ユーザーが明示的に承認したものに限る。親が計画に書いて自分で採用しただけの方針は含めない。

違反の兆候：却下理由に親自身の指示・計画の文言をそのまま引いている／`NEEDS_USER_DECISION` をユーザーに見せずに解消した／却下根拠に `path:line` もユーザー発話もない。

## 比較集合は評価者に列挙させる

consistency や既存先例との照合を任せるとき、親は対象と観点だけを渡す。

- 「既存の X と揃っているか」のように比較先を名指ししない。比較集合が必要なら列挙条件（同一ディレクトリの全ファイル、同じ引数の形を持つ関数など）で渡す。
- 評価者が列挙した比較集合が1〜2件しかない場合は、集合が狭すぎるとみなし、列挙条件を広げて再度評価させる。

一貫性は属性ではなく関係であり、比較集合を選んだ側が答えを決めてしまう。実装側が選んだ比較先を渡すと、自明に PASS する。

## 矛盾を見つけたとき

- 該当する指摘に「自己検証済み事実と矛盾：<内容>」と付けてユーザーに示す。
- 「指摘 N 件のうち M 件は直前の検証と矛盾」のように件数を明示する。
- 直前の会話の文脈を踏まえて指摘を再評価する選択肢をユーザーに示す。
