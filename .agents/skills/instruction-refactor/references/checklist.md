# 指示を評価する観点

依頼された範囲と実害に関係する観点だけを使う。全検査では対象全件を確認する。仕様と出典は [official-criteria.md](official-criteria.md)、改善方法は [strategies.md](strategies.md) を必要なときに読む。

## 1. サイズと形式

`wc -l` と frontmatter の文字数・名前を測り、共通仕様と対象 runtime の制約を分けて照合する。500行は推奨目安であり、短いファイルにも誤った発火条件や重複はあり得る。同種ファイル中央値の3倍以上は読解優先度の目安にとどめる。

未知フィールド、一覧での短縮、本文のロード可否を混同しない。仕様違反と実際の validator の失敗を別々に報告する。

## 2. 責務・原本・重複

- **責務越境**: 評価・提案だけの担当が実装や外部操作を始めないか。役割に必要な具体例と、担当外の工程を区別する。
- **SSOT 逸脱**: 原本と複写を実際に読み比べる。モデルや推論量の既定値を説明へ複製して古くしていないか。削除前に消費側の読込経路を確認する。
- **DRY 違反**: 対象群を横断比較する。連続5行以上の一致や対応見出しを手掛かりに、意味と固有差分を読む。runtime 固有の接続や指示の配達に必要な複写は許容する。
- **同一ファイルの重複**: 言い換えも含めてクラスタを作り、各箇所の固有情報と統合先を示す。統合の検証は strategies の戦略6に従う。

原本の責任を取り違えない。進行は親用Skill、専門評価と結果契約は `code-review-guidance`、常時制約は対象の `AGENTS.md`、runtime の仕様はその公式資料・実装と照合する。

## 3. 発火条件

description を本文と近接スキルの用途に照らして確認する。

- 能力と適用する仕事を短く示し、重要な適用条件が先頭にあるか。
- 広い関連語、長い機能一覧、強調だけの発火要求により、専門手順が不要な仕事まで拾わないか。
- 似た依頼との境界が必要なら明確か。明示起動限定など、既存のユーザーの選択を保持しているか。
- 本文へ置く工程・ツール選択・出力形式を説明へ詰め込んでいないか。

トリガー語の個数や一律の自動発火要求を合格条件にしない。適用すべき依頼と近接する非適用の依頼を当て、選択の根拠が本文の責務と一致するかを見る。description の編集では利用可能な `skill-creator` を参照する。

## 4. 読込・工程・終了条件

- 複数モードの資料を無条件で全部読ませていないか。入口から該当モードだけへ到達できるか。
- 明示的な必須工程と推奨を区別しているか。固定の文書数・担当数・周回数に具体的な必要性があるか。
- 既存の承認後も確認を取り直す指示や、最初の実装で依頼済みの検証・修正を止める指示がないか。
- 必要な検証が通った後も、変更や具体的な懸念なしに確認を広げる指示がないか。

具体的なコマンド・安全な順序・結果契約・停止条件が correctness、security、data loss を防ぐ場合は保持する。説明・監査だけの依頼を実装へ広げず、実アクセス制御も守る。

## 5. ユーザースコープの汎用性

この観点を依頼された場合、または全検査のユーザースコープでは、対象全件の固有名を独立に検索する。構造読解のついでだけで済ませない。

1. 特定プロジェクトの絶対パス、会社・サービス名、固有のコマンド・クラス・DB項目を候補として抽出する。
2. 親が実在確認した利用範囲・履歴・記憶と照合し、特定プロジェクトを前提にしているか確認する。単に履歴に登場するだけで違反としない。
3. 公開技術名、複数環境で使う一般ツール、明示的な仮名は区別する。照合資料がなければ未確認にする。
4. 修正後は候補語を必要な対象範囲で再検索し、残る用途と理由を確認する。

問題ごとに箇所、成立条件、影響、根拠、推奨戦略を返す。好みや文字数だけの指摘で作業を停止しない。
