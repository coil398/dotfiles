# 指示の整理戦略

必要な指示が読者へ届くことを保ち、原因に対応する最小の変更を選ぶ。仕様・出典は [official-criteria.md](official-criteria.md)、評価観点は [checklist.md](checklist.md) を必要なときに参照する。

## 性能保全ゲート

外出し・削除・統合の前に各候補を確認する。

1. **同一ファイル内の重複か**: 外出しを増やさず、戦略6で固有情報を統合する。
2. **原本の複写か**: 原本を読み、内容が満たされることと、消費側が必要な場面で読む手順を確認する。唯一の配達経路なら削らない。
3. **子が実行する指示か**: 親の読込状態は継承を前提にしない。外出しする場合は子へ実体pathと読む条件を渡す。コマンド・必須チェック・結果形式が届くことを確認できなければ inline を保つ。
4. **常時本文での案内か**: 実行手順は専門原本に保ち、必要になる条件と参照先を残す。
5. **固有だが不要な指示か**: 単なる重複と区別し、不要と判断した根拠と削除による行動の変化を示す。必須の安全順序・明示された承認境界を削らない。

読込経路を維持できない候補は「性能保全のため見送り」として理由を返す。行数だけを採否の基準にしない。

## 戦略の選択

| 原因 | 戦略 |
|---|---|
| 責務越境、不要な原本複写 | 1: 必要性を確かめて削除・参照化 |
| 複数モード、長い条件別資料、複数ファイルの重複 | 2: 段階的開示 |
| runtime が対応する常時指示の分割 | 3: import |
| ドメイン固有の長い手順が常時ロードされる | 4: スコープに合う配置 |
| 実際に使われない入口・参照 | 5: 未使用部分の整理 |
| 同一ファイル内の意味的重複 | 6: 固有情報を保つ統合 |
| 過剰・曖昧な発火条件 | 7: description の見直し |
| ユーザー共通領域のプロジェクト固有前提 | 8: 配置移動・一般化 |

## 1. 必要性を確かめて削除・参照化

各記述が誰のどの判断を変えるか確認する。担当外の工程や、読まれる原本で満たされる複写だけを削る。固有の安全・運用情報は保持する。原本があるという事実だけで配達経路を削除しない。

## 2. 段階的開示

`SKILL.md` には目的、必須制約、必要な資料を選ぶ入口を置く。モード別の詳細・大きな例・スキーマは既存の `references/`、決定論的な処理は `scripts/`、成果物に使う素材は `assets/` を使う。

呼出側には「どの条件で何を読むか」を示す。全referenceの一括読込や、入口とreferenceの二重掲載にしない。別packageを使うなら消費側から解決できる原本pathを渡す。短い単用途のスキルや将来の拡張だけのために階層を増やさない。

## 3. import

対象 runtime が実際に対応するときだけ使う。Claude Code の `@path` のような記法を他の runtime に自動適用しない。非対応なら既存adapterや明示的な読込経路を使う。

## 4. スコープに合う配置

常時必要な制約はAGENTSに残す。特定ドメイン・作業だけの長い手順は既存の該当Skillへ置き、AGENTSには必要な場面の案内を残す。別runtimeの具体的手順を共有原本に一律適用しない。

## 5. 未使用部分の整理

呼出元・参照・利用記録を確認し、未使用と判断できる範囲だけを整理する。最近呼ばれていないだけで不要と決めない。削除した入口や用語を同じファイル全体と関係する呼出側で検索し、出力欄・手順・返却形式の残骸がないことを確認する。

## 6. 固有情報を保つ統合

1. 通読して同じ意味の箇所をクラスタにまとめ、各箇所の固有差分と統合先を決める。
2. 編集前に「誰が・何を・どの条件で」という情報点を1行1点の番号付きチェックリストへ抽出する。
3. 固有差分の和集合を統合先へ残し、二つ目以降の重複を削除または内部参照にする。
4. 編集後の文面と情報点を1点ずつ照合し、全点の包含を確認する。欠落があれば修正する。
5. 変更前後のdiffと包含の確認結果を示す。実施・確認の承認は呼出元の依頼と既存承認に従う。

不要な指示そのものを削る判断は戦略1・5と区別して根拠を示し、情報を失った統合を「重複削除」と報告しない。

## 7. description の見直し

利用可能な `skill-creator` を参照し、能力と適用条件を短く明確にする。近接する非適用例でも意味を確認する。語数や発火の強さを増やすことを目的にせず、既存の明示起動限定・暗黙起動の選択を保持する。

## 8. 配置移動・一般化

固有前提は適用されるプロジェクトへ移すか、意味を保つ一般的な表現・参照へ変更する。公開技術名や具体例を機械的に仮名へ置き換えない。

## 確認の選択

複雑な変更や指示の配達に影響する変更は、独立レビューや代表的な依頼での確認を選ぶ。ファイル数だけで別workflow・担当数・全検査を強制しない。進行と受入は親が持ち、必要な確認が通った後は具体的な未解決リスクがない限り検証を増やさない。
