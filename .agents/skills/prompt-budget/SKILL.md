# /prompt-budget：プロンプト面の計測つき整理

プロンプト変更は計測してから完了とする。効果は「送信バイト数」と「挙動不変」の2点で示す。

## 計測対象の全体像（census）

モデルへ実際に送られるテキストは4層ある。層を分けて数えること:

| 層 | 内容 | 頻度 |
|---|---|---|
| system prompt | ベース指示 + role + プロジェクト指示 + per-model 注記 | 毎リクエスト |
| 注入ブロック | transform_context / middleware が毎回追記する索引・ヘッダ | 毎リクエスト |
| tool surface | 各ツールの name + description + JSON スキーマ（TypeBox 等） | 毎リクエスト |
| 副プロンプト | judge / verifier / compaction / 要約などの一回きり指示 | 呼出ごと一回 |

文字列を削るだけでなく、inline 埋め込み文字列を名前付き定数にする。名前がない文面は計測できず、重複や内容のずれが起きる。

## 手順

1. **baseline**: 既存の計測スクリプトで現状を JSON 記録する。scriptがない場合、新規作成は明示依頼があるときだけ行う。実測できない場合は概算と区別して報告する。
2. **整理**: 下記「整理の基準」に従って編集。
3. **描画同一性の検証**: 純粋な整理（dedup・定数化）では、変更前後で**レンダリング結果が同一**であることを機械的に確かめる。`git show HEAD:<file>` の旧版と新版を同じ抽出器に通し、解決済み文字列を `SAME/DIFF/NEW/GONE` で突き合わせる。DIFF があったら意図した文面差か確認する。
4. **after**: 同じスクリプトで再計測し、baseline と差分を報告する（総量だけでなく項目ごと）。
5. **挙動検証**: 描画が同一なら既存テストで足りる。文面を変えた場合は、その文面が担う振る舞い（tool 選択・denial 応答・要約品質）を検証する。live bench は文面差があるときだけ使う。

## 整理の基準

やる:

- 同一文面・同一 bullet の繰り返しを共有定数へ（描画結果を変えない）
- inline の `## ヘッダ` / 注入ブロックを名前付き定数へ（計測可能にする）
- 同一文中の重複語・回りくどい言い換え（意味不変の範囲）

やらない:

- **運用上の警告を省く**：「この引数を小さくすると worker が死ぬ」系の記述は長くても削らない。具体例を含む警告は、モデルが弱い場合にも役立つ。
- SDK/外部ライブラリ側の tool description：自前の面だけを対象にする。それらは計測するが編集しない
- 減らした bytes 自体を成果にする：副プロンプトの重複解消は一貫性のためであり、毎リクエストの token 節約にはならない。毎リクエスト層を優先する

## 計測スクリプトを作成する依頼

`scripts/prompt-budget.ts`（Node/TS プロジェクト想定）依頼された場合に限り、次を参考にする:

- **prompt blocks**: `src/` を走査し `const NAME = \`...\` | '...'`（NAME に PROMPT/BLOCK を含む）を抽出。`${NAME}` 補間は全定数から再帰解決（WORKER_PROMPT ⊃ BASE_PROMPT 型の入れ子に対応）。エントリポイントが import で main を実行する場合は **ソース抽出**で回避
- **tools**: 実際の tool factory を lazy なスタブ deps で構築し、`name + description + JSON.stringify(parameters)` のサイズを計る
- 出力は表 + `--json`（前後 diff 用）。トークン推定は chars/4 でよい。目的は同じ物差しで比較することで、絶対精度は求めない。

## 報告

- before/after の総量と、変化した項目の一覧（SAME/DIFF/NEW/GONE）
- 「描画同一」を機械検証した旨と、文面差があればその意図
- 挙動検証に使ったコマンドと結果
