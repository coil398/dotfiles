# 変更の影響と検証範囲

実装前に、計画と実コードから公開契約への波及、実行時の挙動、データ・権限への影響を確認する。これは検証を選ぶための判断材料であり、固定の件数・キーワード・担当数を満たすための機械ゲートではない。

## 確認する影響

- 公開 API・型・設定の名前、必須性、削除、入力・出力の意味
- データの永続化、migration、認証・認可、秘密情報、外部操作
- 生成元から生成物への連鎖と、実際に影響する利用側、snapshot、golden
- 分岐、状態、順序、非同期処理、エラー処理など実行時の挙動
- 互換性要件、リリース条件、プロジェクト固有の必須検証

生成処理への言及や変更ファイル数だけで、全観点・全テスト・全スイートを要求しない。生成物を変更する場合は生成元との整合と、期待値を変える理由を確認する。

## 検証の選定

各リスクを、どの diff 確認、レビュー、テスト、承認で検証するかを計画へ記録する。独立した記録が役立つ長い run では、ランタイムが提供する run/artifact path にこの判断を保存してよい。短い run では親の返却と実測結果だけで足りる。

- 挙動を変えない文書・設定変更は、内容整合、対応 parser、実効設定、生成結果を確認する。
- 挙動変更は対象経路の再現・回帰テストを実行し、必要な利用側を確認する。
- API・型・生成物の変更は利用側と生成整合を確認する。
- データ損失、権限、security に影響する場合は不変条件を独立 review と検証で確かめる。
- 影響範囲が広い、統合で結果が変わる、またはプロジェクト規約が必須とする場合は、該当する統合テスト・フルスイートを実行する。

全観点、refactor-advisor、tester、反復回数を一律の完了条件にしない。ただし必要な検証を実行できない場合は未確認リスクを明記し、成功として扱わない。安全性、正しさ、権限、データ損失に対応する既存の検証を、コストだけを理由に緩めない。

本番・削除・不可逆な操作の権限は、レビューやテストの選定とは別に確認する。対象、影響、復旧方法を親が示し、必要な明示承認を得る。権限拒否を別の経路で迂回しない。
