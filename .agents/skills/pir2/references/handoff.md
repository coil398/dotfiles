# PIR² handoff

複数回の実行にまたがる長いタスクを、次回の実行で未完了部分から再開するための引継ぎ記録。PIR²、debug、およびこの reference を指定する workflow の親が使う。

## 使う条件と所有

- 長い run で次回の再開に実益がある場合、またはユーザーが引継ぎ・記録を求めた場合だけ使う。1 回で完了する run、短い run では作らない。
- 親だけが作成・更新・保管する。実装・探索・レビュー・テストの担当は handoff を書かず、進捗、新しく判明した TODO、証拠を親へ返す。振り返り担当は必要な場合に読むだけとする。

## 場所と安全境界

- handoff はプロジェクト単位の 1 ファイル（`HANDOFF_PATH`）とする。plan、report、完了後の保管など run 固有の記録は、その run が専有する `RUN_DIR` に置く。
- `HANDOFF_PATH` と `RUN_DIR` は、現在のランタイムが提供する run directory 手順、または親・ユーザーが指定して実在を確認した path で確定する。ランタイムに手順がない場合、親は対象 repo の外側にある書込可能な artifact root を確認し、`<artifact root>/<project bucket>/handoff.md` と、同じ project bucket 配下に排他的に作成した `RUN_DIR` を使い、選んだ path を報告する。対象 repo 内や未確認の HOME path を推測で使わない。
- project bucket 名を path から導出する場合は [sanitized-cwd.md](sanitized-cwd.md) の正規化式に従う。親から検証済みの値を受け取った場合は再計算しない。
- 読み書きの前に、artifact root と project bucket が symlink でない実体 directory で対象 repo の外側にあること、`HANDOFF_PATH` が存在する場合は symlink でない通常ファイルであること、`RUN_DIR` が今回排他的に作成した実体 directory であることを確認する。確認に失敗した場合は読み書き・移動をせず、確認できた状態を報告する。

## 形式

見出しは次の順序で固定する。ユーザーが手で編集しても、親が特定セクションだけを読み書きできるようにするため。

```markdown
# PIR² Handoff

> 最終更新: YYYY-MM-DD HH:MM (run: <RUN_DIR の basename>)
> タスク: <引き継ぐ目的の一行要約>

## 背景・決定事項

- <確定した設計・選定と、その根拠>
- <維持する制約>

## 残 TODO

- [ ] <未完了の要件> (files: <対象>, 確認方法: <テスト・確認>)
- [ ] <依存のある要件> (依存: <先行項目>)
- [x] <受入済みの要件> (証拠: <実行した確認・差分>) <!-- done: YYYY-MM-DD -->

## 既知の問題 / 要確認

- <未解決事項、ユーザー判断が必要な事項。なければ「なし」>

## 関連 artifact

- <実在する plan・report・検証結果の path>
```

## 開始時の判定

| 条件 | 判定 | 挙動 |
|---|---|---|
| ユーザーが明示的に再開を指示した（「引継いで」「続きから」「resume」など）、または handoff path を渡した | explicit resume | handoff を読み、下記の再開手順に従う |
| 再開指示はないが `HANDOFF_PATH` に既存 handoff がある | passive notice | 存在と path をユーザーへ伝え、新規タスクとして進める。既存 handoff は今回のものと仮定せず、読み書きしない |
| 再開指示も既存 handoff もない | new | 使う条件を満たす場合だけ、計画確定後に handoff を作成する |

再開指示は依頼文の意味で判定する。タスク説明に「続き」などの語が偶然含まれるだけでは explicit resume にしない。

explicit resume では次を行う。

1. handoff の内容を、現在の status、差分、関連 artifact と照合する。食い違いは「既知の問題 / 要確認」へ追記し、推測で解消しない。
2. 「背景・決定事項」に確定済みの判断は再度の要件整理や brainstorm で作り直さない。
3. 未チェック `[ ]` の項目だけを計画対象にし、`[x]` 項目は再計画・再実装しない。
4. 同じ `HANDOFF_PATH` を増分更新する。新しい handoff で置き換えない。

## 作成と更新

- 作成: new で使う条件を満たす場合、親は計画確定後に、タスク要約、計画の実装手順を `[ ]` にした「残 TODO」、空の「背景・決定事項」「既知の問題 / 要確認」を書く。`HANDOFF_PATH` に採用していない既存 handoff がある場合は上書きせず、今回の記録は `RUN_DIR` に置き、既存 handoff の存在を報告する。
- 更新: 親が実測した受入結果で項目を `[x]` にし、証拠と `<!-- done: YYYY-MM-DD -->` を付ける。担当の自己申告だけでは `[x]` にしない。新しく判明した TODO は根拠とともに `[ ]` で追記し、「最終更新」を更新する。
- 「背景・決定事項」と「既知の問題 / 要確認」はユーザーの編集を優先し、親は追記だけを行う。既存の記述を自動で書き換えない。
- 項目の対応はテキストで照合する。ユーザー編集などで対応が一意に決まらない場合は、既存項目を書き換えず追記する。

## 終了時の保管

1. `HANDOFF_PATH` が開始時に確定した path と一致し、上記の安全境界を満たすことを再確認する。
2. 「残 TODO」の各項目を受入の証拠と照合する。項目がない、書式が読めない、未確認の項目がある場合は完了と推測しない。
3. 未完了項目があれば内容を保ったまま、進捗と「最終更新」だけを更新して残す。
4. 全項目の完了を確認できた場合は、`RUN_DIR` 配下の未使用 path（例: `handoff-completed.md`）へ既存ファイルを置き換えない方法で移動して保管する。移動先が存在すれば別の未使用名を選ぶ。削除しない。
5. 最終報告に保管先、または残る未完了項目と `HANDOFF_PATH` を記載する。

passive notice で通知しただけの handoff、存在しない handoff、今回採用していない handoff は操作しない。handoff を使わない run では、専用ファイルや完了メッセージを作らない。

## 古い情報の誤参照を防ぐ

- handoff は前回の記録であり、受入の証拠ではない。受入は現在の status、差分、検証結果で判断する。
- 完了した handoff は `HANDOFF_PATH` から `RUN_DIR` へ移し、次の新規タスクへ混入させない。
- 「最終更新」と完了日で時系列を追えるようにする。
- 書式が壊れている場合は作業を止めず、読み取れた範囲だけを使い、破損箇所を報告する。読み取れない項目から完了を推測しない。
