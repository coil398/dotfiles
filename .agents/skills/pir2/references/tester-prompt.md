# tester への依頼内容

親が実差分、計画、利用側、プロジェクトの検証規約から、変更した挙動と防ぐ具体的な実害に対応する `TEST_SCOPE` を決める。固定のフラグ、ファイル数、テスト回数で範囲を決めない。

## 検証範囲

- 変更した挙動の再現・回帰テストと、必要な利用側・生成整合性を含める。
- 文書・設定でも実行指示、権限、生成、公開挙動に影響すれば、その挙動を検証する。影響しない変更は構文・リンク・内容照合などで足りる場合がある。
- フルスイートは影響範囲から必要な場合、またはプロジェクト規約で必須の場合に実行する。
- データ損失、認証・認可、security、OS 権限、不可逆操作、外部または本番状態に関わる安全確認を省略しない。

## 担当への入力

独立した動作検証に分離価値がある場合は、現在のランタイムの tester/collaboration primitive を使う。小規模な確認は親が直接行える。担当には次を渡す。

- 対象リポジトリ、対象 diff、必要な受入条件、実在する計画や report の path
- `TEST_SCOPE` のコマンド、実行ディレクトリ、必要な環境、期待する結果
- 変更禁止範囲と、外部サービス・本番データ・不可逆操作への権限境界
- report を保存する場合だけ、実行前に確定した固有 path

追加確認が必要になったら、理由と影響を親へ戻す。親が依頼範囲内で安全に実行できる確認は行い、権限、費用、外部データなど新たな承認が必要な場合だけユーザーへ確認する。テストデータ以外の既存データをクリーンアップしない。

## 結果と再実行

実行したコマンド、終了コード、確認結果、未実行・判定不能の理由を返す。必要な確認が未完了なら PASS にしない。FAIL は再現した根本原因を修正経路へ戻し、変更後の影響に応じて必要な確認だけを再実行する。関係のない成功済み検証を取り消さず、同じ失敗を根拠なく繰り返さない。
