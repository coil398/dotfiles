# サブエージェント運用

サブエージェント・Task・collaborationへ作業を委譲するとき、担当のmodel・推論量を選ぶとき、子の完了を待つときに読む。runtime固有の起動API・model指定・待機方法は各runtimeのnative原本が持つ。

## 作業単位と所有

- 自明でない作業を始める前に、具体的で範囲の決まった作業単位を特定する。分けることに意味がある独立単位は並列に委譲する。小さく分けられない作業は1単位のまま進め、担当数のために人工的に分割しない
- 書き込む担当には排他的なファイル所有を与える。同じファイルに触れる単位があれば1人の書き手に割り当て、他をread-onlyにするか書き込みを直列化する
- runtimeがサブエージェントや入れ子の委譲を提供しない場合も、同じ単位の境界と順序を親が保って進める
- `/pir2`・`/debug`・`/ir` などのworkflowは、その作業に該当する計画・実装・レビュー・テストの工程だけを使う。計画だけの依頼や軽い `/ir` の流れを保ち、全作業に同じ工程や担当数を要求しない

## 親と子の責任

- 親（primary/root）は、ユーザー対話、探索と結果の統合、計画、設計、scope、依存関係、ファイル所有、受入条件と計測、進捗、統合、競合の回避、検証、最終判断を持つ。計画そのものを計画担当へ委譲しない
- 子は親から範囲の決まった要件を受け取り、簡潔な結果、変更したファイル、検証の証拠を返す
- 実装全体へ波及する設計判断では、親が暫定案を作り、共有 `pir2` の「専門検討から実装条件へ」で必要な専門観点だけを検討する。親は条件・根拠・確認方法を一つの実装方針へ統合する。明確な小変更は短い確認で進め、実施済みの検討を繰り返さない
- 最終レビューは、実装条件の充足と設計自体の妥当性を独立に確かめる。事前検討を理由に省略しない。相反する修正案は共有 `reviewer/references/finding-reconciliation.md` で親が裁定する
- 必要な独立評価は実装担当と別の子で行う。親は実差分と根拠を照合し、担当外の指摘も重大度を落とさず扱う
- レビューの必要な観点は担当数と別に決める。観点と独立性は共有 `reviewer` Skillに従い、容量が足りなければwaveに分ける

## 委譲の指示

- 今回のタスク指示には、対象と版、目的、確定事実、所有範囲、制約、重点、完了条件、専門資料の実体パスを含める。短い単発作業は具体的な指示だけでよい
- 親は進行手順・担当選択・入出力・結果契約・runtime方針を読む。委任するためだけに子用の専門本文を先読み・転記・再生成しない。専門資料の実体パスを解決して子へ渡し、子自身が必要な本文とreferenceを読む。親の読込状態の継承や同名Skillの自動選択に依存しない
- 親が直接実行・評価・分析する場合は、実行者として該当する専門手順を読む。結果の統合で判断が対立するときは、照合に必要な部分を読む
- 親用Skillの再配分ループを実行者へ渡さない。階層委任が必要な用途だけ、親が範囲・起動権限・統合責任を明示する
- readerはファイル・記憶・外部状態を変更せず、結果を親へ返す。保存や記憶への追記は許可された親が行う。生成物を伴うテストや再現はwriterとして扱う
- 行動上の非変更指示と実際のアクセス拒否を区別する。名前・文章・未対応設定だけで強制read-onlyと主張しない

## modelと推論量

- 標準サブエージェントと汎用Taskを優先し、役名やmodel違いだけの独自定義を作らない。専門手順はSkill・reference、runtime固有の実行条件は短いnative定義に置く
- modelと推論量は既存のruntime方針と公開された起動引数に従う。明示されたモデル・独立性・外部CLI連携を無断で置き換えない
- 計画・専門検討・相反案の判断と難しいレビューには、難しさと誤った場合の影響に応じた推論能力を配分する。決まった実装は通常設定、機械的な起動・結果回収はscriptを優先する。能力・effort・context量・権限を別々に扱い、read-onlyを軽量化の根拠にせず、全工程を最大effortにも固定しない。製品別の指定方法・既定値はnative側が持つ

## 待機と結果

- Codex・Cursorでは、他にすべき作業がなければruntimeの完了通知や長時間の待機手段で待つ。長い待機を、状態確認・ファイルのtail・ターミナルのpollingの繰り返しで代用しない
- 子は完了・失敗・blocker・重要なscope変更・必要な判断のときに親へ通知し、「実行中」の反復通知はしない。ユーザーが求めた進捗報告は許す
- 待機のtimeoutは子の作業期限ではなく、失敗の証明でも重複作業の許可でもない
- レビュー進行は共有 `reviewer`、専門評価は `code-review-guidance`、結果の意味はその `references/result-contract.md` を正本とする。各呼出元で観点・独立性・判定を再定義しない。必要な確認を実施できていない状態を成功として扱わない
- 長期作業・再開・明示記録に必要な状態だけ親が保存する。再開では有効な依頼と未完了部分を引き継ぎ、完了済みの工程を根拠なく繰り返さない

## 委譲構成のレビュー

workflowやサブエージェント運用を変える差分では、各作業単位と担当が重複なく1対1に対応すること、独立単位が並列に実行されること、書き込むファイルの所有が競合しないこと、親の統合責任が保たれることを確認する。
