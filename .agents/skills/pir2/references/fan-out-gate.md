# 観点別レビューの分担と統合

レビュー担当の分担を決めるための共有ガイド。名前や起動方式はランタイムごとに異なるため、この文書は担当観点と受入判断だけを定める。

対象となる reviewer の詳細契約が今回読み込んだ SKILL 本文にある場合は、その本文を優先し、このガイドで同じ契約を重複定義しない。

## 観点の選定

親は実差分、要件、変更範囲、失敗時の具体的な実害から必要な観点を選ぶ。ユーザーが明示した観点は尊重し、全観点を求められた場合は全観点を実施する。未指定時に全観点、固定人数、固定順を既定にしない。

- `correctness`: 正確性、性能、挙動の回帰、データ整合性
- `consistency`: 既存パターン、命名、同じロジックの適用漏れ
- `quality`: 局所的な保守性、テスト可能性、重複、scope
- `security`: 認証・認可、入力、秘密情報、外部境界、権限
- `architecture`: API・schema、レイヤー、責務、依存境界

低リスクの局所変更では親の diff 照合と focused check で足りる場合がある。高リスク・破壊的変更、security、権限、データ損失、不可逆操作、外部または本番状態に関わる場合は、実装者から独立した該当観点を省略しない。

## 起動と分担

独立した観点が複数ある場合は、ランタイムが提供する委譲機構で並列に渡せる。単独観点は単独で起動し、委譲機構がない場合は親が直接確認してよい。並列 wave、起動前宣言、同一メッセージ、担当数の一致、特定の report 形式は品質条件ではない。

各担当には対象 diff、計画が実在する場合はその内容、受入条件、担当観点、変更禁止範囲を渡す。report は後続判断に必要な場合だけ実行前に固有 path を割り当てる。未生成の path や起動していない担当の verdict を作らない。

## 受入と再確認

親は返却された指摘を仕様、実差分、再現結果、テストで照合する。採用した重大指摘を解消し、誤検知・判断不能・未確認を区別する。担当数が少ない、起動順が異なる、宣言形式がないという理由だけで有効な結果を破棄しない。必要な観点が未確認または判定不能なら PASS にせず、不足した観点や確認だけを追加する。

修正後は変更範囲と失敗原因に関係する観点だけを再確認する。以前 PASS だった無関係な観点を機械的に全再実行しない。変更範囲が広がった場合は、追加されたリスクに対応する観点を選ぶ。

refactor-advisor は不具合レビューとは別の任意改善であり、必要な場合だけ `refactor-advisor-gate.md` のガイドを使う。
