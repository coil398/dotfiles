# 実装の委譲と統合

PIR² の実装経路を、親の計画・所有境界・終了条件に接続する共有ガイド。具体的な actor 名、モデル、起動 API、report schema は、「既定の実装担当」節を除き、ランタイム自身の契約に従い、この文書で固定しない。

## 責任境界

親（main）がユーザー対話、探索、設計、scope、依存関係、担当の選択、統合、受入、最終判断を所有する。親は専門担当の返却を裁定・統合してから、担当へ目的、対象と版、確認済み事実、変更箇所・禁止範囲、採用構造、守る具体的な挙動、理由と根拠の実体パス、終了条件、確認方法、設計を再検討する条件、返却事項を渡す。返却の転送だけで実装方針を代用しない。担当の自己申告、完了報告、終了コードだけを受入根拠にしない。

密接に関連する実装は1人の書き込み担当へまとめる。実装中に前提の誤りが分かったら、担当は根拠と影響を親へ返し、その前提に依存する実装を広げない。依存しない作業と、計画で留保されていない局所的な書き方は進める。親は必要な箇所の計画を更新して担当へ返し、通常の局所判断を承認待ちにしない。

## 既定の実装担当

この節を実装担当の既定に関する唯一の正本とする。

| 親runtime | 既定 | 切り替え先 |
|---|---|---|
| Claude Code | `codex-luna`（`/codex` runner、`gpt-6-luna`。effortは共有 `/codex` の目安で選択） | `claude-sonnet`（`general-purpose`、呼出時に `model: "sonnet"` を指定し、呼出時modelが優先） |
| Codex | dotfiles の Codex native collaboration 設定にある既定 | — |
| その他 | 各runtimeの既存primitive | — |

Claude Code親は、ユーザーが実装担当を `codex-luna` と `claude-sonnet` の間で指定した場合に、その指定を同じセッションの以後の委譲へ適用する。`--claude` はSonnet、`--codex` は既定経路の明示。指定がなければ既定を使う。親は次のrunner完了条件を満たす場合に限り、`gpt-6-luna` から `gpt-6.1-sol` / `high` へ引き継ぐ。難所は共有 `codex` Skillのexpert（`gpt-6.1-sol` / `medium`）などを最初から選べる。

引き継ぎは、runnerが `wait_status=completed` かつ `done.created=true` で終了し、`EXIT` とDONE markerの値が一致したjob（EXIT=0またはturn failed）の後に、親が実差分とレビュー・テストから実装能力の不足と判断した場合に限る。新しいRUN_IDで先行diffと失敗内容を渡す。invocation error、`worker_start_failed`（EXIT=125・DONEなし）、timeout、supervisor異常終了、wait error、環境・CLI・認証・入力の失敗では引き継がない。

## 経路の選択

- 実装・修正は最上位の親が直接行わず、書き込み担当へ委譲する。全体文脈と密結合した変更は1人の担当へまとめる。挙動に影響しない文書・コメント・単一の設定値の修正と、委譲の経路が使えないときは、親が直接書いてよい。
- 所有ファイルと終了条件が独立している通常作業は、現在のランタイムの worker/collaboration primitive へ委譲できる。
- 原因推論、状態所有権、競合、性能、厳しい整合性など難しい作業は、利用可能な高推論担当へ最初から渡せる。

引き継ぎは上記「既定の実装担当」の条件だけで行い、入力不足、仕様未決定、権限、環境、外部サービス、CLI の失敗を理由にしない。親が解消できる不足を先に確認し、解消できない正しさ・安全性・権限の問題はユーザー判断または blocker として扱う。

## 独立単位の並列化

複数担当を並列に使うのは、書き込みファイル、共有契約、生成物、migration、lockfile、共通 config/helper、実装順序に競合がなく、親が統合後の確認をできる場合だけとする。同じファイルや共有契約を複数担当に割り当てず、依存する単位は直列化する。人工的な分割や、体数・形式を満たすための分割はしない。

必要な境界が明確なら、初回実装とレビュー FAIL 後の修正のどちらでも独立単位を並列化できる。競合、未確定の命名・抽象・データ形状、共有契約への波及がある場合は単一担当に戻す。tester FAIL 後は、再現可能な原因と対象所有を親が確認してから、影響する最小単位だけを選ぶ。

## 返却と受入

担当には、必要なら実在する計画・対象 diff・保存先だけを渡す。報告ファイルは後続判断に役立つときだけ実行前に固有 path を割り当て、未生成 path を必須にしない。返却には変更ファイル、実装内容、実行した確認、未確認事項、blocker を含める。

親は各書き込み wave の後に status、対象 diff、実在する変更、所有/禁止範囲、終了条件、必要な確認出力を照合する。担当の変更が要件や scope と一致しない場合は原因を調べ、最小修正へ戻す。既存のユーザーまたは他担当の未コミット変更を保全し、自動的に revert、reset、restore、checkout、stash しない。

## 再実装

reviewer/tester の FAIL は、親が報告と実差分・仕様・再現結果を照合して根本原因を特定し、`../../reviewer/references/finding-reconciliation.md` の手順で指摘の採否と相反する案を裁定し、その結果を実装者へ返す。

担当の終了はruntimeの終了状態で判定する。Codex runnerのjobの終了判定は`../../codex/references/runner.md`の終了契約に従う。runner jobでDONEが出ていない場合は、runner referenceのとおりprocessとhelperが無いことを確かめてから終了とみなす。`invocation_error`と`worker_start_failed`はjob未開始なので、原因確認後にこの節の再試行規則に従う。processが生きているjobのCWDには再委譲しない。終了確認後に再委譲する場合は、先行diff・失敗内容・未完了部分を新しい担当へ渡し、runnerでは新しい`RUN_ID`を使い、この再委譲ではmodelを変えない。委譲の経路が使えない場合は親が直接書いてよい。

修正後は影響した reviewer 観点と挙動だけを再確認し、無関係な担当を機械的に全再実行しない。同じ呼び出しを原因不明のまま繰り返さず、同じ失敗が続いた場合は実測した blocker と選択肢を親が報告する。原因が特定され、変更後に成功する合理的な根拠がある場合だけ再試行する。

安全性、正しさ、権限、データ損失に関わる確認を、委譲コストや担当数の都合で省略しない。commit、push、不可逆操作、OS/外部状態の変更は、ユーザーが明示した範囲と必要な承認に限る。dotfiles管理下の承認は[dotfiles-autosync](../../dotfiles-autosync/SKILL.md)に従う。
