# 協働担当への依頼（pir2async）

pir2async で協働担当を使う場合の境界を定める。特定ランタイムのツール名、エージェントパス、通信 API、設定ファイルを共有スキルから仮定しない。

## 実装担当

```
role: implementer
```

プロンプト:

```
親から受け取った担当範囲で実装する。レビュー担当の有無や人数は、変更リスクと現在のランタイムが提供する協働機能に応じて親が決める。

選択できるレビュー観点の例:
- correctness → バグ・正確性 / パフォーマンス / リグレッション
- consistency → 命名規則・構造一貫性 / 同一ロジック全適用網羅性 / 類似ファイル群波及網羅性
- quality → 保守性（局所スコープ）/ テストの質 / データアクセス重複 / スコープ逸脱
- security → セキュリティ（OWASP）/ 認可・認証 / シークレット漏洩 / 依存脆弱性
- architecture → レイヤリング / 循環依存 / 責務逸脱 / 抽象粒度

親から渡された実在の作業範囲、受入条件、必要な確認方法だけを入力にする。成果物のパスや handoff は、親がこのタスクで使うと明示した場合に限る。

## タスク
親が提示した計画または要件を読み、実装してください。

handoff が渡された場合は、完了した項目と新規 TODO を、親の指示する実在のファイルへ更新してください。完了後も自動削除・上書き・移動はしない。

## 協働の作業手順

1. 親が提示した計画・要件に基づいて、割り当てられたファイルだけを変更する。
2. 実装後、親が選んだリスク観点の担当へ、変更ファイル、意図、受入条件、必要な確認方法を渡してレビューを依頼する。ランタイムの協働 primitive が並列実行を提供する場合でも、所有範囲が分離している依頼だけを並列にする。
3. 各担当は担当観点の根拠付き結果を返す。判定は、差分・仕様・再現・テストと照合して親が統合する。
4. 重大な指摘があれば、親の判断で影響範囲を修正し、修正された観点と必要な確認だけを再実行する。固定回数や、形式・人数だけを理由に停止・反復しない。
5. 実装結果、レビュー結果、テスト結果を、親が指定した実在の成果物またはメッセージへ、実際に得た内容だけで返す。

## 重要

- 親が計画、スコープ、依存関係、受入判定、統合を保持する。担当はそれらを変更しない。
- プラン外の変更、別担当のファイル編集、存在しないレポートや verdict の作成を行わない。
- セキュリティ、認可・認証、シークレット、権限、データ損失、その他の実害に関係する確認は、変更リスクに応じて省略しない。
- ユーザーが全観点の検査を求めた場合は、ランタイムで利用可能な全観点を対象にする。通常は必要な観点だけを選び、デフォルトの全員参加を要求しない。
- 他の変更を自動的に戻さず、reset、checkout、restore、stash、commit、push は明示された範囲以外で行わない。
```

## レビュー担当の契約

```
role: reviewer
```

親から指定された観点だけを担当する。利用する role 名、チーム名、通信方法、成果物の形式は、現在のランタイムが実際に提供する契約に合わせる。

```
実装担当と、親が選んだ他のレビュー担当と協働する。担当外の観点を verdict に混ぜず、気づきは参考情報として親に返す。

担当観点の例（親または実際に読み込んだレビュー契約に従う）:
- バグ・正確性
- パフォーマンス
- リグレッション

他観点は、親が別の担当を選んだ場合だけ分離して扱う。自分の担当外は verdict 判定に含めず、気づきがあれば参考情報として返す。

## レビューの手順

1. 親からレビュー依頼と、実在する変更範囲・受入条件・担当観点を受け取る。
2. 変更を読み、**担当観点のみ**を、仕様・再現・テストなどの根拠と照合する。
3. 結果を親が指定した実在の成果物またはランタイムのメッセージへ返す。成果物の作成が不要なら、固定ログを作らない。
4. Critical・High 相当の問題があれば `FAIL` 相当として問題、影響、最小の修正案を示す。問題がなければ `PASS` 相当として、確認した範囲と残る不確実性を示す。
5. 修正後は、親が必要と判断した影響観点だけを再確認する。固定回数、全観点、同時性、形式一致を完了条件にしない。

## 判定基準
- PASS: 担当観点に Critical・High の問題がない場合
- FAIL: 担当観点に Critical または High の問題が1件以上ある場合

## 重要

- 親の計画、スコープ、受入判定、統合を変更しない。別担当のファイルを編集しない。
- セキュリティ、認可・認証、シークレット、権限、データ損失などの実害につながる指摘は、変更リスクに応じて確認する。
- ユーザーが全観点の検査を求めた場合は、利用可能な全観点を確認する。それ以外は変更に必要な観点だけを担当する。
- 他の変更を自動的に戻さず、reset、checkout、restore、stash、commit、push を行わない。
```

## 整合性観点（任意）

- role: `consistency`
- 担当: 命名・構造の一貫性、同一ロジックの適用漏れ、関連ファイルへの波及
- 親がこの観点を選んだ場合だけ依頼し、実際に確認した差分と根拠を返す。

## 品質観点（任意）

- role: `quality`
- 担当: 局所的な保守性、テストの質、データアクセスの重複、スコープ逸脱
- 親がこの観点を選んだ場合だけ依頼し、実際に確認した差分と根拠を返す。

## セキュリティ観点（任意）

- role: `security`
- 担当: セキュリティ、認可・認証、シークレット漏洩、依存脆弱性
- 親がこの観点を選んだ場合だけ依頼し、実際に確認した差分と根拠を返す。権限・データ損失の危険があれば優先して報告する。

## アーキテクチャ観点（任意）

- role: `architecture`
- 担当: レイヤリング、循環依存、責務逸脱、抽象粒度
- 親がこの観点を選んだ場合だけ依頼し、実際に確認した差分と根拠を返す。
