# UI / UX

ユーザーが画面を理解し、操作を完了し、失敗から回復できるかを評価する。まず同directoryの`ui-ux-principles.md`を必ず読み、そこにある応答時間体系、RAIL、Doherty、Core Web Vitals、3層フレーム、WCAG閾値、モバイル検出法、アンチパターンを判断軸にする。呼び出し元が指定したプロジェクトのデザイン原則、対象プラットフォーム、適用アクセシビリティ基準も読む。指定された原本やスタックアダプターが読めなければ、未確認範囲として返す。

## 判断軸

- 入力には原則100ms以内の反応を返す（RAIL Response / Nielsen 0.1s）。フレーム予算を侵すブロッキング処理を確認する。
- 遅延への対処を、層1（スピナー・フェードで隠す）、層2（ブロッキング・無駄処理）、層3（無条件再フェッチ）に分ける。層1だけで層2・層3を残す提案は不完全とする。
- Nielsen #1（システム状態の可視化）、#4/#8（整列・一貫性）、#5/#9（エラーからの回復）を、対象のプラットフォーム原則と合わせて適用する。

## 確認すること

1. **応答性・知覚パフォーマンス**: 押下や入力への反応、ブロッキング処理、フレーム予算、待ち時間の分類。スピナーやフェードだけで原因を隠していないか。
2. **状態の可視化・フィードバック**: 押下フィードバック、ロード中・成功・失敗の表示、重複操作、待ち時間に合ったスピナー・スケルトン・プログレス。短い処理で一瞬だけ表示されるインジケーターも確認する。
3. **データ取得・状態設計**: 画面遷移ごとの無条件再フェッチを避け、必要ならキャッシュとSWRで即時表示後に再検証する。楽観的UIは適用可能性と誤表示の実害を確認する。
4. **空・エラー・ローディング状態**: 0件、未取得、通信失敗、権限なし、再試行、回復導線が設計されているか。
5. **レイアウト・ビジュアル一貫性**: 整列、余白、階層、読みやすさ、既存デザイントークン、コンテンツ出現時のレイアウトシフト。
6. **アクセシビリティ**: 適用基準に従い、コントラスト（テキスト4.5:1、大きな文字3:1、UI部品3:1）、タップターゲット（最低24px、推奨44px。iOS 44pt / Android 48dp）、可視フォーカス（WCAG 2.2 2.4.7）、Name/Role/State（4.1.2）、点滅（3回/秒以下）、テキスト拡大200%を確認する。

## 境界と証拠

プログラム一般のバグ、セキュリティ、保守性、レイヤリングは対応する観点へ返す。実行時に壊れる結線や型は、UI/UXに直接影響する場合だけ対象にする。別のアクセシビリティ専門担当がある場合は深いARIA・SEO・セマンティックHTMLを重複確認しない。

静的コードだけで視認性、体感時間、実デバイスの操作を確認済みとしない。画像、実行記録、利用可能なテスト等の証拠を使い、未確認部分を明記する。問題や改善案には層タグ `[知覚]` `[実]` `[データ]` と適用した原則の出典を付ける。

数値基準は対象の正式な版とプラットフォームに合わせる。Webの単位をそのままnative UIへ適用しない。本referenceを口実に未承認の画面操作やFigma編集を行わない。既存UI評価原本に固有の基準・例外が指定されていれば追加で読み、一般項目だけに置き換えて専門性を失わない。
