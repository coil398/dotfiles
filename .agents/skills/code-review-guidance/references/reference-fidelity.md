# Reference Fidelity

参照実装、仕様書、プロトタイプ等からの移植が依頼された場合に、保持すべき意味が落ちていないかを評価する。

## 確認すること

- 正しい参照元、対象版、移植対象範囲が確定しているか。
- API、schema、既定値、分岐、エラー処理、単位、変換規則の対応。
- 仕様上重要なprompt、model設定、コスト計算、描画・状態分岐等の移植漏れ。
- ユーザーが明示的に変更を求めた部分と、同じ意味を維持すべき部分の区別。
- 移植先の言語・frameworkで自動処理される条件の違い。
- 参照元にある偶然的な実装や不具合を、忠実性のためだけに残していないか。
- プロンプト原文を、記号・改行・大文字小文字・空白・優先順位・Step順まで対応付ける。
- JSON schemaのフィールド名・型・required・description・enum値と順序を対応付ける。
- model名（版を含む）、temperature、top_k、top_p、thinking_level、max_tokens、response_format等の生成パラメータを対応付ける。
- input/output、text/audio/image/video、reasoning等のコスト・料金定数を取りこぼしていないか確認する。
- 空値・null・エラー等の全rendering分岐と、参照元が列挙する表示対象の集合を照合する。
- dict/mapの更新順、マージ規則、上書き優先度を照合する。

## 根拠

参照元と移植先の具体的な箇所を対応付ける。短い説明や要約だけで同等と判断しない。参照元が未取得なら、その範囲は未確認とする。

同一バイト列を求める要件と、同じ振る舞いを求める要件を区別する。必要がないのに全文hashや新しい契約JSONを生成しない。

リファレンスがSoTである。既存リポジトリの慣習、別reviewerの提案、自分の推論だけを理由に乖離を許容しない。意図的な随伴差分（たとえばハードコード値の汎用化やシステムプロンプトの言語置換）は要求と照合して除外し、判別できなければ未確認または親の判断事項として返す。
