# Concurrency

同じ資源を、別のリクエスト・再送・バッチ・非同期処理が同時に、または前後して扱ったときに、状態が壊れないかを評価する。正常系を1本ずつ読むだけでは見つからないので、競合する経路を先に列挙してから判定する。承認済み操作の重複実行など、security観点にも関わる操作の競合はここで評価する。

## 確認すること

- 差分が読み書きする資源（行、枠、残回数、ファイル、キャッシュ、画面の状態など）ごとに、同時に、または前後して触る経路（別のリクエスト、再送、クライアントの自動再試行、バッチ、非同期の完了）を列挙する。経路が1本だけだと断定する前に、呼び出し元を検索する。
- 判定に使った値を読んでから書き込むまでの間に、別の経路がその値を変えられないか。変えられるなら、ロック・条件付き更新・一意制約・世代の照合のどれで防いでいるか。
- 同じ要求が2回届いたとき（再送、自動再試行、連打）、付与・消費・記録・生成が二重にならないか。2回目の応答が1回目と矛盾しないか。
- 取り消された・切断された・破棄された要求の続きで、状態を確定していないか。

### データベース

- 更新判断に使った値の有効性が更新時にも保証されているか。ロック下の読み取り、version 等を条件に含む更新と更新件数による競合検知など、採用した方法で古い値に基づく更新が成立しないかを確認する。
- 行ロック（`SELECT ... FOR UPDATE` など）で直列化する場合、対象DB・分離レベル・検索条件で実際にどの行や範囲がロックされるかを確認する。0件の検索が何もロックしないとは一律に扱わず、行がまだない場合を含む競合経路で不変条件が守られるかを調べる。
- 同じ資源を扱う全経路について、実際の競合順序で必要な不変条件が守られるかを確認する。共通の親行を同じトランザクション内でロックして直列化する方法、条件付き更新、一意制約など、経路全体で有効な手段を評価する。手段の一致自体を要件にせず、ロックを使う経路ではロック順序の不整合や省略が競合を生まないか確認する。
- 上限・枠・残回数の消費では、確認から予約・記録までの間に別経路が不変条件を破れないかを確認する。条件付き更新や一意制約のほか、同じトランザクション内の有効な直列化で守られているかを評価する。
- 重複してはいけない行は、存在確認と挿入の間に競合する実経路がないかを確認する。一意制約、または全経路を直列化する有効なロックなどで重複を防いでいるかを評価する。
- 状態遷移は、遷移前状態を条件にした更新と更新件数による判定など、競合する更新に対して一度だけ有効な遷移となるかを確認する。全経路を直列化する有効な方法も評価する。
- 照合から更新までを原子的に行う必要がある場合、その必要な操作全体を保証する手段が成立しているか。複数操作を原子的に扱う必要があるときは同じトランザクションなどの保証を確認し、外部APIの待ち時間にロックを保持する設計が必要性に照らして妥当かを確認する。

### クライアントと非同期処理

- 開始した側の画面・コンポーネント・セッションが閉じる・破棄される・再利用されるとき、キャンセルが下位の呼び出し（通信、読み込み、再生、待機）まで渡っているか。キャンセル後に遷移・表示・保存が続かないか。キャンセルを失敗として扱い、エラー表示を出していないか。
- 遅れて返った応答が、すでに別の対象に切り替わった後の状態へ反映されないか。要求ごとの識別子や世代で、最新の応答だけを反映しているか。
- 前の処理の完了を待たずに、それを前提にする次の処理を始めていないか。後から始めた保存が、先に始めた保存の遅い完了で上書きされないか。
- 取り消した・失敗した処理が確保したハンドル、プールのオブジェクト、一時ファイルを返却・解放しているか。外部の応答を待つ処理に、タイムアウトや終了条件があるか。
- 自動再試行する通信路では、失敗の種類と再試行で成功する可能性を確認する。サーバー側に記録・付与・消費を起こす呼び出しは、再試行で重複効果が生じないよう冪等性、条件、冪等キーなどが成立しているかを評価する。

## 根拠

競合の指摘には、2つの経路と、それが交互に進む具体的な順序を書く。順序を示せない懸念は指摘にしない。テストが1本の経路しか通していない場合、その成功を並行時の安全性の根拠にしない。並行性の確認に実DBや実機の実行が必要なら、その内容と条件を親へ返す。
