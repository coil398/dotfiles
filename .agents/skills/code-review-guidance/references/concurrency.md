# Concurrency

同じ資源を、別のリクエスト・再送・バッチ・非同期処理が同時に、または前後して扱ったときに、状態が壊れないかを評価する。正常系を1本ずつ読むだけでは見つからないので、競合する経路を先に列挙してから判定する。

## 確認すること

- 差分が読み書きする資源（行、枠、残回数、ファイル、キャッシュ、画面の状態など）ごとに、同時に、または前後して触る経路（別のリクエスト、再送、クライアントの自動再試行、バッチ、非同期の完了）を列挙する。経路が1本だけだと断定する前に、呼び出し元を検索する。
- 判定に使った値を読んでから書き込むまでの間に、別の経路がその値を変えられないか。変えられるなら、ロック・条件付き更新・一意制約・世代の照合のどれで防いでいるか。
- 同じ要求が2回届いたとき（再送、自動再試行、連打）、付与・消費・記録・生成が二重にならないか。2回目の応答が1回目と矛盾しないか。
- 取り消された・切断された・破棄された要求の続きで、状態を確定していないか。

### データベース

- 更新の可否を決めた値を、ロックを取った後に同じトランザクション内で読み直しているか。ロック前やトランザクション外で読んだ値のまま更新していないか。
- 行ロック（`SELECT ... FOR UPDATE` など）で直列化する場合、該当行が0件だと何もロックされない。行がまだない状態で競合しうる経路では、必ず存在する行か一意制約で直列化しているか。
- 同じ資源を扱う全経路が、同じロックを同じ順序で取っているか。一部の経路だけがロックを省いていないか。
- 上限・枠・残回数の消費は、確認と予約を条件付きの1文の更新、または一意制約で原子的に行っているか。件数を数えてから別の文で記録していないか。
- 重複してはいけない行を、DBの一意制約で防いでいるか。アプリ側の存在確認と挿入の組だけにしていないか。
- 状態の遷移は、遷移前の状態を条件に含めた更新で行い、更新件数で成否を判定しているか。
- 1つの判断に属する照合と更新が、別々のトランザクションに分かれていないか。外部APIの待ち時間をトランザクションの中に含めていないか。

### クライアントと非同期処理

- 開始した側の画面・コンポーネント・セッションが閉じる・破棄される・再利用されるとき、キャンセルが下位の呼び出し（通信、読み込み、再生、待機）まで渡っているか。キャンセル後に遷移・表示・保存が続かないか。キャンセルを失敗として扱い、エラー表示を出していないか。
- 遅れて返った応答が、すでに別の対象に切り替わった後の状態へ反映されないか。要求ごとの識別子や世代で、最新の応答だけを反映しているか。
- 前の処理の完了を待たずに、それを前提にする次の処理を始めていないか。後から始めた保存が、先に始めた保存の遅い完了で上書きされないか。
- 取り消した・失敗した処理が確保したハンドル、プールのオブジェクト、一時ファイルを返却・解放しているか。外部の応答を待つ処理に、タイムアウトや終了条件があるか。
- 自動再試行する通信路で、サーバー側に記録・付与・消費を起こす呼び出しを再試行の対象から外しているか。

## 根拠

競合の指摘には、2つの経路と、それが交互に進む具体的な順序を書く。順序を示せない懸念は指摘にしない。テストが1本の経路しか通していない場合、その成功を並行時の安全性の根拠にしない。並行性の確認に実DBや実機の実行が必要なら、その内容と条件を親へ返す。
