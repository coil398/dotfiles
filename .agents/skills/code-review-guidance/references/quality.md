# Quality

今回の要求に対して、局所的な実装・保守・検証の負担が不必要に増えていないかを評価する。

## 確認すること

- 現在の要求に必要のない抽象層、汎用フレームワーク、二重管理、先回りした設定。
- 同じ判断や状態を別々に保守する重複。
- 読解・変更・失敗原因の追跡を具体的に困難にする分岐や責任混在。
- テストが要求された振る舞いを確認せず、実装文言や偶然の値だけを固定していないか。
- 失敗を隠すskip、無根拠なretry、例外の握りつぶし、テストの弱体化。
- 読む人が責任や意味を判断できない命名。作業番号や一時的経緯への依存。
- 調査・評価のための成果物や制御基盤が、本体より大きな保守対象になっていないか。

## 境界

短いことやファイル数が少ないことだけを品質としない。既存の有用な契約・安全境界・再開機能は保守負担があっても必要な場合がある。

改善提案には、今の具体的な不利益と、より単純な修正で何が変わるかを示す。無関係な全面リファクタを完了条件へ追加しない。

### 既存の評価基準

- 新しいデータアクセスメソッドが同一データソースの既存メソッドと統合可能かを確認する。ただし、取得列やfilterが異なるだけで意味が異なる場合は無理に統合しない。統合による具体的な保守・性能上の利益を示す。
- 依頼や仕様にないfallback、代替mapping、防御分岐、迂回ロジックを追加していないか確認する。既存の設定（例: Inspector）や配列データ等で解決できる場合は、その代替を示して不要な追加を指摘する。
- 境界で検証済み、または型・schema・constructorで保証された値を内側の層で再検証していないか。到達経路を示せない状態への分岐、発生を確認していない例外の広い捕捉は、不要な追加として指摘する。
- 今回の差分で、一度しか呼ばれず、複雑な境界も隠さず、名前が呼出し側を読みやすくしないhelperを先回りで切り出していないか。
- 競合やsecurity上の端への対策を、失敗する順序や到達経路を示せないまま追加していないか。追加するなら、失敗経路・起こりやすさ・増えた実装量がユーザーへ示されているか。
- テストの確認範囲は[testerのテスト手順](../../tester/references/test-procedure.md)に従う。

### 過剰な契約

契約・ゲート・fingerprint・再利用判定を設計・実装・レビューするときに使う。追加・拡張にはユーザーの明示許可が要る。許可があっても、実害が契約不足でない限り入れない。典型形:

- `package.json` や lockfile の sha256 を closure・pre-commit・checker のゲートへ焼き込む
- 同じ条件を複数の契約ファイル・fixture・hashへ重ねて記録し、同期負担を増やす。網羅性だけを理由に、すべての型と項目の組合せをfixtureへ追加する
- drift を直すたびに全 contract JSON・authority fixture・closure hash を再同期することを標準の修復ループにする
- 成功条件が振る舞いではなく contract ファイルの hash 一致だけの CI・pre-commit ゲート
- 型・lint・テストを、別の JSON contract・oracle・closure 層で二重化する
- 時点・実行ID・固定hashなど偶然的な値への依存を、回帰防止のために通常経路へ置く
- 再発防止だけを目的とした meta gate
