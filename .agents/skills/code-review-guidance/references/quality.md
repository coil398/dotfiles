# Quality

今回の要求に対して、局所的な実装・保守・検証の負担が不必要に増えていないかを評価する。

## 確認すること

- 現在の要求に必要のない抽象層、汎用フレームワーク、二重管理、先回りした設定。
- 同じ判断や状態を別々に保守する重複。
- 読解・変更・失敗原因の追跡を具体的に困難にする分岐や責任混在。
- テストが要求された振る舞いを確認せず、実装文言や偶然の値だけを固定していないか。
- 失敗を隠すskip、無根拠なretry、例外の握りつぶし、テストの弱体化。
- 読む人が責任や意味を判断できない命名。作業番号や一時的経緯への依存。
- 調査・評価のための成果物や制御基盤が、本体より大きな保守対象になっていないか。

## 境界

短いことやファイル数が少ないことだけを品質としない。既存の有用な契約・安全境界・再開機能は保守負担があっても必要な場合がある。

改善提案には、今の具体的な不利益と、より単純な修正で何が変わるかを示す。無関係な全面リファクタを完了条件へ追加しない。

### 既存の評価基準

- 新しいデータアクセスメソッドが同一データソースの既存メソッドと統合可能かを確認する。ただし、取得列やfilterが異なるだけで意味が異なる場合は無理に統合しない。統合による具体的な保守・性能上の利益を示す。
- 依頼や仕様にないfallback、代替mapping、防御分岐、迂回ロジックを追加していないか確認する。既存の設定・Inspector・配列データ等で解決できる場合に限り、不要な追加を指摘する。
- テストは正常・異常・境界を意味のあるassertionで確認しているかを読む。配列を返すAPIで1件だけの応答に依存する場合は、複数要素や境界を検証できない実害を説明する。
