# Correctness

要求された振る舞いが実装・状態・失敗経路・データに成立するかを評価する。

## 確認すること

- 正常系だけでなく、空・欠落・境界・失敗・再試行・取消・再開の経路。
- 条件の包含と除外、同型引数の順序、単位、符号、範囲、null等の扱い。
- 状態の所有者と寿命。画面・セッション・キャッシュ間で不要に共有または残留しないか。
- 非同期の完了順、重複実行、競合、冪等性、トランザクションの境界。詳細は concurrency 観点で評価する。
- データ取得・保存・移行と呼び出し側の契約が一致するか。
- 既存の必須挙動が維持されるか。要求が挙動変更なら旧挙動を無条件に正としない。
- 想定負荷で具体的に操作遅延、停止、過大な資源消費を生む経路。
- テストが今回の不具合を検出できるか。通ったテストが今回の対象状態に対応するか。

### 重点項目

- 仕様・コメント・関数名に「以降」「以前」「以上」「以下」「未満」「超」や inclusive / exclusive がある場合、境界ちょうどの比較演算子と一致するか。
- 同一型の引数が並ぶ関数では、定義側の意味と呼び出し側の順序を照合する。型検査だけでは順序違いを検出できない。
- 外部・ユーザー由来の数値は、負数・範囲外・ゼロ除算・無限ループ・意図しないスコア増加の経路を確認する。
- SQL等の変更ではJOIN条件、WHERE、ORDER BYの列と実スキーマの索引経路を照合する。複合索引の左端プレフィックス、否定述語、列への関数適用を考慮し、索引の存在だけで絞り込みを保証しない。索引定義の必要性もこの観点で評価する。
- 結合・述語・並び・集約の変更では、意味の正しさと想定負荷での性能リスクを分けて評価する。性能上の結論が実行計画に依存する具体的なリスクがある場合は、その判断に必要な代表的条件で計画や走査量を確認する。確認できない範囲は未確認として親へ返し、不要な計画確認や変更前経路の保存を一律に求めない。
- JOIN先のフィルタ列がJOIN元へ非正規化されていないか、親子関係でWHERE条件が被覆されるため冗長になっていないかを確認する。
- fallbackや既定値の削除は、それ自体を問題にしない。空値が実際に流入し、呼び出し元が旧fallbackを前提にする破綻経路を確認した場合だけ指摘する。
- null・型・範囲の検査が欠けているという指摘は、未検証の値がその地点へ到達する経路を示した場合だけにする。境界で検証済み、または型・schema・constructorで保証された値の再検査を求めない。

## 根拠

問題が生じる入力・状態・順序と、該当コードの経路を示す。型検査やテストの成功だけで未確認の実行経路を保証しない。観測できない性能や内部挙動を断定しない。

再現に書き込みが必要なら親へ渡す。評価者は自分で対象を修正しない。
