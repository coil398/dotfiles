# Consistency

既存の利用側や同種箇所と今回の変更が正しく接続されるかを評価する。

## 確認すること

- 同じ契約を使う呼び出し元、別分岐、別画面、別プラットフォームへの適用漏れ。
- 既存の状態管理、エラー処理、命名、構造と異なることで誤用や欠落が起きないか。
- 型、設定、ドキュメント、生成元、生成物の変更が対応するか。
- 同じ意味を持つフィールド・単位・戻り値が、箇所ごとに異なる意味になっていないか。
- 既存の再利用可能な実装を無視して、意味の異なる重複実装を増やしていないか。
- 実際の仕様変更に伴って、変更すべき全利用側が追従しているか。

### 重点項目

- 変数・引数・フィールド名が実際に保持するデータの意味と一致するか。似たIDや同じ型の値を取り違えていないか。
- 新しい層・パッケージ・サブディレクトリでは、同じ親にある既存コンポーネントを読み、分割単位・配置・ファイル構造の慣例を確認する。将来の拡張性だけを逸脱理由にしない。
- 対称ペアの配置対称性: 対称的な機能ペア（A機能とB機能、FreeとPremium等）の対応物を特定し、ドメイン層を `rg` で検索して、新規ファイル・型・主要関数の配置と責務を比較する。非対称な配置が依存境界や利用側の探索・生成に与える影響を確認する。循環import回避が理由なら相互参照を調べて検証する。非対称という事実だけで重大度を固定しない。
- API schemaにフィールドを追加した場合、同種フィールドの型、日時表現、required/nullable、enum命名・値を全件照合する。
- 数値キャップ、filter、JOIN、switch、sort等の新規ロジックは同じデータ型・テーブル・概念を扱う全メソッドへ適用漏れがないか確認する。Get/List/Search、Count等の対称メソッドも含める。
- 取得結果に上限がある場合、外部へ公開するcount/totalも同じfilter・論理削除条件・上限と整合するか確認する。
- 既存のPreferences、visibility、locale、status等の設定が新しい同種メソッドでも適用されるか確認する。
- 変更がエージェント総数や内訳などの統計値を変える場合、同じ値を記載するREADME・指示・設計書が同期しているか確認する。
- index定義の必要性: ORMのindexタグやSQLのCREATE INDEXを、実際のWHERE / JOIN / ORDER BY、制約、テーブル分類（マスタ・単調増加・集計）、推定行数、クエリ頻度と照合する。既存類似テーブルだけを追加理由にせず、小規模なマスタでは効果と更新コストを比較し、増加するテーブルでは必要な検索経路を支えるindexの欠落を調べる。実行計画や利用条件から影響を示し、定義の有無だけで重大度を固定しない。

## 境界

多数派の構造だから必ず従う、という判定はしない。異なる設計が必要なら、その理由と接続条件を確認する。ファイル名やスタイルの好みだけを重大な問題としない。

「同種箇所がある」という理由でユーザーの指定範囲外まで勝手に修正しない。必要な波及は親へ根拠を返す。
