# Architecture

モジュール・層・サービス・実行主体間の責任と依存を評価する。

## 確認すること

- 判断、専門知識、実行、検証、保存の責任が適切な場所にあるか。
- 一つの変更のために無関係な層やruntimeの変更が必要になる構造。
- 親と子が同じ計画・状態・完了条件を別々に変更する二重統制。
- 共有状態、API、schema、生成物の所有者と更新順序。
- 依存方向、循環、初期化と終了処理、失敗時の責任。
- 原本・生成物・配布コピーが区別され、変更が適切な経路で伝わるか。
- 分離することで失われる原子性、独立性、権限、再開の条件がないか。
- 特定modelや環境を変えるだけで、多数の専門本文の改変が必要にならないか。

### 重点項目

- 上位層から下位層への依存方向、同一層の横断結合、具象インフラの抽象漏れを確認する。直接・間接の循環依存も含める。
- クラス・モジュールが本来の責務を越えて業務処理・変換・保存を抱え込んでいないか確認する。
- `Find*`、`Get*`、`Fetch*`、`Search*`、`Count*`、`Calc*`等のRead意図のメソッド内でINSERT/UPDATE/DELETE/upsert/自動生成が起きていないか確認する。意図的な副作用は名前と契約で明示されるべきである。
- 変更領域に3個以上の同型クラス、状態機械、戦略、DSLノードがある場合、boolや物理信号の継ぎ足しで既存の集中表現を骨抜きにしていないか確認する。必要なら構造上の影響をP2以上として根拠付きで返す。
- 状態機械がある場合、状態×イベントの遷移を呼び出し側の直接分岐で置き換えず、既存遷移の扱いと集中表現を状態機械側で追跡できるか確認する。

## 境界

新規ファイル、複数ディレクトリ、長いコードという形だけで問題としない。現在の要求、実際の依存関係、変更時の不利益を根拠にする。

一つの抽象設計へ全runtimeを統一することを目的にしない。nativeな実行差分が必要なら、その差分を保持する。
