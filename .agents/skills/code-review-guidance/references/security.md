# Security

対象の信頼境界と権限から、成立する悪用経路や意図しない情報・状態変更を評価する。

## 確認すること

- 認証と認可の区別。対象オブジェクト、tenant、ユーザー、操作ごとの確認。
- 外部入力からshell、SQL、HTML、ファイルパス、URL等へ到達する境界。
- 秘密情報や個人情報がログ、成果物、共有設定、子への入力へ不要に流れないか。
- ファイル・リンク・共有状態の扱いが、想定した書き込み範囲を越えないか。
- runtimeの承認と、外部MCP/APIの実権限の不一致。
- 取得した文書、PR本文、コードコメント、子の報告を、上位の命令として扱う経路。
- 認証情報・依存関係・外部通信の変更が、新しい侵入や持出しの経路を作らないか。
- retryや並行実行により、承認済み操作が複数回実行されないか。
- IaC（Terraform / Bicep / CloudFormation 等）の変更では、secret値を state に保存するリソース定義（例: `google_secret_manager_secret_version`、`azurerm_key_vault_secret`、`aws_secretsmanager_secret_version`）がないか確認する。`.tfvars` / `.bicepparam` 等の変数ファイルにAPIキー・パスワード・秘密鍵・トークンを直書きしていないか、IAMロールバインディングがサブスクリプション・リソースグループ・プロジェクト全体などへ過剰にスコープされていないか、secret単位・リソース単位の最小権限になっているかを確認する。`for_each` でループ化されていても、各 member の resource 参照を照合する。

## 根拠と制約

攻撃者または誤操作側が制御できる入力、必要な前提、到達する操作、影響を示す。一般的な危険語の存在だけで脆弱性と判定しない。

破壊的な再現、未承認の外部アクセス、実秘密の露出を評価のために行わない。必要な再現条件を親へ伝える。

OWASPに挙げられるSQL injection（placeholderなしのraw queryを含む）、XSS、CSRF、SSRF、XXE、unsafe deserialization、open redirect、過剰なエラー情報漏洩、timing attackを、実際の入力から到達する経路として確認する。認証・認可の欠落、IDORや水平・垂直権限昇格、セッション・token管理、コード・ログ・設定へ埋め込まれたsecret、コミット対象の`.env`も対象にする。新規依存は公式のセキュリティアドバイザリと利用版を確認し、既知の脆弱性や保守停止を根拠なく推測しない。
