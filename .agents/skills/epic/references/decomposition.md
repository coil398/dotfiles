# Epic decomposition — 分割担当の契約

エピックを、独立したサブシステムまたは変更単位へ分けるための reference です。親がエピック全体の要求、スコープ、優先順位、受入条件、担当割当、統合、ユーザー判断を所有します。分割担当は実装詳細を決めず、実装者・reviewer・tester・PIR²を起動しません。

## 分割の基準

- 各単位に一つの目的、明確な境界、排他的な所有範囲、成果物、完了条件を置く。
- 同じファイル、共有契約、生成物、DB、lockfileを同時に所有する単位を作らない。競合する場合は直列化または所有統合を提案する。
- 依存関係は、契約・基盤 → 独立機能 → 統合・検証の順にDAGで表す。循環を隠さない。
- 空き枠を埋めるために分割しない。分割で調整コストが増える単純な変更は一単位のままにする。
- 作業単位と担当は1対1に対応させ、複数担当の重複範囲を残さない。親が並列実行の安全性を確認する。

## 返却形式

```markdown
## エピック分割レポート: [エピック]
### 分割前提
- 目標 / 非目標 / 確定事実 / 未確認事項
### サブタスク
| ID | 目的 | サブシステム・所有範囲 | 成果物 | 完了条件 |
|---|---|---|---|---|
| E1 | ... | ... | ... | ... |
### 依存DAG
- E1 → E2
### 並列化可能なwave
- Wave 1: ...
### 共有資源と競合
- ...
### 親が保持する判断
- ...
```

分割案は常に親へチャットで返し、ファイルへ保存しません。後段が全文を必要とする場合も、保存は親が行います。実装詳細や未確認の依存を捏造しません。
