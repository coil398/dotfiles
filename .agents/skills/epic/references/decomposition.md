# Epic decomposition — 親の分割手順

エピックを、独立したサブシステムまたは変更単位へ分けるために親が使う reference です。親がエピック全体の要求、スコープ、優先順位、分割、依存関係、受入条件、担当割当、統合、ユーザー判断を所有します。分割と計画の作成を子へ委譲しません。子へ渡すのは、分割に必要な事実を集める bounded な read-only 探索だけです。

## 分割の基準

- 各単位に一つの目的、明確な境界、排他的な所有範囲、成果物、完了条件を置く。
- 同じファイル、共有契約、生成物、DB、lockfileを同時に所有する単位を作らない。競合する場合は直列化するか所有を一単位へ統合する。
- 依存関係は、契約・基盤 → 独立機能 → 統合・検証の順にDAGで表す。循環を隠さない。
- 空き枠を埋めるために分割しない。分割で調整コストが増える単純な変更は一単位のままにする。
- 作業単位と担当は1対1に対応させ、複数担当の重複範囲を残さない。並列実行の安全性は親が確認する。

## 計画の記載項目

```markdown
## エピック分割: [エピック]
### 分割前提
- 目標 / 非目標 / 確定事実 / 未確認事項
### サブタスク
| ID | 目的 | サブシステム・所有範囲 | 成果物 | 完了条件 |
|---|---|---|---|---|
| E1 | ... | ... | ... | ... |
### 依存DAG
- E1 → E2
### 並列化可能なwave
- Wave 1: ...
### 共有資源と競合
- ...
### ユーザー判断が必要な事項
- ...
```

分割は親の計画の一部として保持し、長い run や再開で必要な場合だけ親が選んだ実在の保存先へ記録します。実装詳細や未確認の依存を捏造しません。
