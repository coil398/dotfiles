# Deepplan — 深い計画

**タスク**: `$ARGUMENTS`

deepplan は実装可能な計画を作るための入口です。親が目的、非目的、対象、所有範囲、依存関係、受入条件、最終判断を保持します。実装、レビュー、テストの完了をこのスキルが代行したとは扱いません。

## 1. 開始状態

親から渡された対象、既存計画、探索結果、ユーザー決定、保存先を実在確認して使います。保存先、RUN_DIR、メモリパス、ホーム配下のパスを推測・新規作成しません。既存計画がある場合は完了項目と決定済み事項を保持し、影響箇所だけ増分更新します。

計画には少なくとも目的・非目的、確認済み事実、対象ファイル、排他的所有、実装順、依存、検証、主要リスク、未解決の判断を含めます。正しさ、安全性、権限、データ損失に関わる未確定事項は、形式を整えて完了扱いにしません。

## 2. 必要な探索

実在する資料で足りるなら追加探索を行いません。不足があり、独立した問いに分ける価値がある場合だけ、現在のランタイムの標準 read-only child または汎用 Task を起動します。担当へは対象、確定事実、具体的な問い、編集禁止、返却事項、必要な実行者用 Skill / reference の実体 path を渡し、担当自身に必要な資料を Read させます。親が直接確認する場合だけ、必要な資料を親が Read します。担当同士の再委譲とファイル保存は前提にせず、結果は親がチャットで受け取ります。

調査対象は既存パターン、再利用可能なAPI、依存・生成境界、テスト影響、失敗経路に絞ります。ライブラリや外部仕様は必要な場合だけ一次資料で確認し、取得不能・未読・タイムアウトを成功扱いにしません。

## 3. 独立した熟考

設計案の反証、トレードオフ、失敗時の実害、既存構造との整合を、問いの独立性とリスクに応じて親または別コンテキストへ割り当てます。小さな判断は親が直接行い、独立評価に価値がある場合だけ複数担当を使います。子へ親用のdeepplanの進行手順を渡して同じ計画工程を再起動させません。

ユーザーが single / panel、特定モデル、特定の独立性を明示した場合はその意味を維持します。runtime が要求を満たせない場合は、別方式へ黙ってフォールバックせず `INCOMPLETE` として親へ返します。通常の計画ではモデル名・担当数・ラウンド数・Fan-Out宣言を固定しません。

## 4. 計画の統合

親は結果を対象コード、既存計画、ユーザー要件と照合し、事実と推測を分けます。実装順・ファイル所有・依存DAG・局所確認・レビュー/テストの必要性を決定し、完了条件を要求結果と必要な検証に限定します。非致命的な改善は計画外の候補として記録します。

計画を保存する場合は、親または呼び出し元が指定した親directoryの実在を確認し、その配下の今回未使用のファイルpathだけへ新規作成します。後段の消費者がない中間 report、空の台帳、固定の rubric を先行生成しません。保存しない場合は計画の要約と未解決事項をチャットで返します。

## 5. 返却契約

返却には目的、非目的、対象と所有、依存順、各ステップの完了条件、検証、リスク、残る判断、実際に保存した場合だけ保存先を含めます。deepplan は実装、commit、push、外部投稿、計画の受入判定を行いません。既存のユーザー変更を戻さず、未確認の問題を `PASS` と表現しません。
