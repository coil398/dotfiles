# Agent / Skill Migrate

移行を担当する親が、指定された設計・既存の点検結果・対象範囲から変更と確認を進める。定義の数を減らすことだけを目的にしない。

## 入力と範囲

- `mode=apply|audit`: 明示移行はapply、点検のみはaudit。
- `runtime=codex|cursor|both|auto`: autoは依頼と実在する設定で決める。
- `scope=repo|dotfiles`: 省略時repo。個人共通設定の変更はdotfilesが対象の場合だけ行う。
- 対象ローカルGit rootの明示一覧。省略時は現在の一つ。
- 指定された設計書・既存の点検結果・アーキテクチャ文書。

auditでは変更・再生成・配布をしない。applyでも認証・課金先・親モデル・承認・実験機能・公開方式を移行だけの理由で変更しない。commit/pushは既存の明確な承認範囲に従う。

## 既存の根拠から始める

現在のHEAD・未コミット変更・指定基準版からの後続変更を確認して、現在の実装を起点にする。指定された点検結果は対象版を照合し、解決済みの指摘を現行の問題へ戻さない。外部の旧資料が取得できなくても、現在の実装と依頼で判断できる部分は進める。

対象の実体から管理対象Skill・reference・必要な例外入口と生成配布経路を列挙する。全体統一を依頼された場合は、指定された統一基準で全管理対象を一巡する。過去の件数を固定せず、代表Skillだけで全体完了としない。一方、専門内容の一般的な正誤や無関係な実装の全監査へ広げない。

各入口について用途、主な読者、専門原本、誰が何を読むか、呼出し先、結果の消費先、runtime差分、必要な例外を確認する。名前だけで同じ本文と判断せず、runtime・原本・実効読込先を区別する。個人・プロジェクトの上書き、入れ子配置、plugin、互換読込、リンク・配布コピーを確認し、管理外本文と取得できない外部原本は別扱いにする。

## 整理の判断

- 親の配分・統合、実行者の専門手順、参照知識、script、常時必要な制約を分ける。各Skillを機械的に二分しない。
- 専門本文は既存Skill/referenceを第一候補に移管する。元の固有の失敗条件・例外・必要資料を照合してから元を除く。安全・権限の必須制約を任意Skillへ移して弱めない。
- 標準子と汎用Taskを優先する。model/effortは既存config・公開起動引数へ置き、標準起動で不足する実行条件や実在する互換入口だけ短いnative定義を残す。
- 委任する親は進行、担当選択、入出力、結果契約とruntime方針を読む。子用専門本文の先読み・転記を委任の条件にしない。実行者へ専門原本の実体パス、対象版、目的、所有範囲、確定事実、制約、重点、完了条件を渡し、子自身が必要な資料を読む。親が直接評価・分析する場合は実行者用資料を読み、統合時も対立の照合に必要な部分を読む。
- 親は委任入力の十分性を受け持つ。親の全会話・部分会話を子へ渡す例外を設けず、既知の事実と仮説・未確定事項を区別した自己完結する依頼を渡す。子が必要な原本を確認しても不足する情報は親が補い、履歴forkで代用しない。同じ子の担当作業の継続・再開と、新しい子への親履歴のコピーは区別する。
- 親用の配分Skillを通常の実行者へ渡して同じ工程を再起動させない。階層委任が必要な用途は親が範囲・起動権限・統合責任を明示する。readerは親へ返却し、保存と記憶追記は親または明示されたwriterが行う。生成物を伴うテストは書き込みとし、既存実装・データの無断変更とは区別する。
- 必要な独立評価、同じ対象版、明示されたモデルと別runtime bridgeを保持する。枠不足ならwaveを分け、要求された観点を捨てない。
- 評価の進行は[reviewer](../reviewer/SKILL.md)、実行者の専門基準は[code-review-guidance](../code-review-guidance/SKILL.md)、結果の意味は[共通契約](../code-review-guidance/references/result-contract.md)、テストは[tester](../tester/SKILL.md)とその実行者referenceへ接続する。呼出元は必要な入力を引き渡し、観点一覧・独立性・未知観点・判定を別に保守しない。研究・熟考・提案・同期など固有結果を持つ手順はその意味を保ち、評価集約に参加するときだけ共通契約へ接続する。
- 固定人数・工程・成果物・確認待ちは目的に必要な場合に限る。長期作業の実在する再開記録と後段のconsumerは保持する。確定した学びの記録を毎回の規則追加へ広げない。

## 履歴・待機・設定の移行

Codex / Cursorを対象にする場合は、変更前に[実行制御の移行確認](references/runtime-controls.md)を読む。履歴なしの要求、公開設定で強制できる範囲、起動引数・指示による選択を別々に確認する。未対応の設定キーや独自の引数書換hookを追加して、要求を実現したことにしない。

待機値は所有するconfigの既存値を正本とし、専門Skillや各repoへ複製しない。V2の待機タイムアウト、子の実行期限、CursorのForeground / Backgroundを混同しない。明示承認済みの待機調整は生成先まで保ち、別repoの移行だけを理由に個人共通の実験機能を有効化しない。

## 適用と確認

原本・専門評価・呼出元・集約・Agent定義・seed/checker・生成配布を依存順に更新する。同じ原本を複数の子へ同時編集させない。移管済み定義をseedや互換読込で復活させず、他runtimeの有効な原本を無断で消さない。

旧Agent名は表示用の担当ラベル、実在する互換入口、誤った必須起動識別子に分類して扱う。名前が残るだけで削除せず、削除済み定義への必須起動を修正する。一般的なモデル方針は既存runtime原本を参照し、専門Skillへ表を複製しない。

生成物だけを手書きしない。変更したscriptの既存試験と、影響する代表経路を確認する。小作業、複数観点、明示五観点独立評価、必読資料欠落・未知観点・途中終了、reader返却、親の直接評価、修正後の限定再評価、明示モデル、再開、配布後の新規発見、再実行の冪等性から今回に必要なものを選ぶ。文字列・ファイル数・子の自己申告だけを実動作の証明にしない。

新しい常設DB、署名台帳、scheduler、model proxy、汎用loaderや監査基盤を作らない。同じ整理を再実行して同義Skill・wrapper・原本を増やさない。許可済みの変更を最後まで進め、未確認の実機項目はそのまま報告する。

## 正式文書と返却

既存の設計・運用文書を現行の採用形に統合する。読者ごとの読込、責任と原本、全管理対象一覧、実行例、必要な例外、追加先の判断、最小確認、配布方法を記す。詳細な専門本文やモデル表・判定規則は原本へリンクし、文書側に再実装しない。READMEから到達可能にし、`git check-ignore`と差分で文書が追跡可能であることを確認する。ignore対象全体を解除せず、外部の個人ログを取り込まない。

dotfilesの正式文書は`AI-WORKFLOW-SPEC.md`。別リポジトリでは既存の文書構造を優先し、個人設定のパス・人数・Agent集合を持ち込まない。同義の移行Skillや別の常設台帳を増やさない。

作業履歴は規範と分け、一つの完了報告に対象HEAD、変更箇所、共通原本、必要な例外と理由、正式文書、適用済み・実行確認済み・未確認、Git状態、復元方法を記載する。Git管理外の変更先は必要なものだけ退避し、ユーザーの未コミット変更・認証・履歴を保持する。過去のpushだけを新しい公開承認と扱わない。

完了報告はリポジトリ反映、対象端末への配布、新規セッションの実効動作、公開機能が対応しない要求を区別する。pushだけで端末反映済みとせず、指示や一回の`none`起動だけで履歴継承の強制禁止が完成したとも報告しない。
