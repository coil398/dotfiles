# 修正を続けるかの判断

確認が失敗したとき、メイン Cursor agent は実際の差分、コマンド出力、reviewer / tester の報告を読み、同じ失敗を盲目的に繰り返さず、原因に対応する最小の修正と確認を選ぶ。この参照は固定のループ回数やファイル数の上限を導入しない。

## 継続

- 失敗の直接原因が実測で特定でき、対象範囲内の修正方針が一つに絞れる場合は、その修正後に影響を受ける確認だけを再実行する。
- 原因が入力、環境、権限、実装のどこにあるかを分ける。知識や設計判断が不足する場合は、所有スキルに従ってメインまたは適切な Cursor `Task` に委任する。
- 独立した reviewer / tester が有効な場合だけ `Task` を起動する。通常の Task の `model` は省略または `inherit` とし、Cursor agent 定義の `role` に従う。

## 待機・報告

追加の仕様、権限、費用、外部状態の変更、不可逆操作が必要な場合は、影響範囲を限定してユーザー判断を待つ。安全な一意の修正がなく、実測の根拠が食い違う場合や、合理的な範囲で原因を確認できない場合は、原因・選択肢・未確認リスクを親エージェントへ報告し、成功や未実行を PASS と扱わない。

## 禁止事項

- 固定されたカウンタ、ファイル数、同一原因の出現回数だけで続行・停止を決めない。
- 存在しない test / implementation / user-decision report や、実行していない verdict を作らない。
- 変更されていない無関係な確認を反復せず、ツール拒否や安全境界を迂回しない。
