# プラン選択肢のユーザー確認ゲート

PIR² 系スキル（/pir2）のステップ 4.6。`plan.md` に複数案・USER_DECISION_REQUIRED・スコープ縮小・外部依存不足が含まれる場合に発動するユーザー確認ゲート。

## 検出トリガー

1. **複数案の提示**: 「案 A / 案 B / 案 C」「方針 1 / 方針 2」「選択肢」のような複数の実装方針が並列で記載されている
2. **`### USER_DECISION_REQUIRED` セクション**: `plan.md` が明示的にユーザー判断を求めている
3. **スコープ縮小・fallback・モック・簡易版の提案**: 「BE 不在のため簡易版で実装」「API 追加なしで○○のみ表示」「ダミーデータで仮実装」等、本来のフル機能から削減した実装案
4. **外部依存不足を前提とした実装方針**: 探索レポートまたはプランに「○○ API は未実装」「○○ データは取得不可」「BE 対応が必要」等が記載され、それを前提に実装方針が立てられている

## 確認フォーマット

メイン Cursor agent は `{RUN_DIR}/plan.md` の `### USER_DECISION_REQUIRED` セクション（および複数案を提示している該当セクション）を Read し、そこに記載した「推奨案」「判断要請の理由」「各選択肢の影響範囲・前提・トレードオフ」を以下のフォーマットでユーザーに提示してください。要約だけで済ませず、推奨案を必ず明示してユーザーが見落とさないようにすること。

```
## プラン段階のユーザー判断要請

[メインが plan.md に記載した複数案 / 縮小判断 / 外部依存ギャップの要約 — 1〜3 文]

判断要請の理由: [plan.md に記載した「なぜユーザー判断が必要か」をそのまま転記]

選択肢:
- (A) [案 A] — [メインが記載した内容と理由・トレードオフ]
- (B) [案 B] — ...
- (C) ...
- 別案: [自由記述で別アプローチを指示]

メインの推奨案: [plan.md で「推奨案」として挙げた選択肢と理由を転記。最終判断はユーザー]

どれで進めますか？
```

## 運用ルール

- **Auto mode でも例外なし**: 仕様変更判断はスキル本体ではなくユーザーに委ねる原則を徹底する（CLAUDE.md「スコープ厳守」「不要なフォールバック処理を作らない」）
- **「実装可能だから」を理由に独断採用しない**: フロント完結の簡易版が技術的に可能でも、ユーザーがそれを望んでいるとは限らない
- **推奨案の透明化**: メインが plan.md に記載した「推奨案」を確認フォーマットから省略してはならない。独断要約で推奨を消すと、ユーザーの判断材料が届かない
- ユーザー回答後、選択結果を `{RUN_DIR}/user-decisions.md` に追記する（ステップ 6.5 と同じファイル）
- ユーザーが提示済み選択肢と異なる案を選んだ場合（= 方針切替が発生した場合）は、確認結果を記録してから、影響する要件・スコープ・実装ステップだけを `plan.md` に Edit で増分反映する。完了済みの判断・ステップ・ユーザー決定を保持し、計画全体を破棄・再作成しない
- ユーザーが plan.md の推奨案または提示済み選択肢をそのまま採用した場合も、選択結果を記録し、メインが plan.md の必要箇所を確認して続行する
- **別案の字義解釈確認（必須・計画更新前に実行）**: ユーザーが提示済み選択肢から外れた **自由記述の別案**（「○○すれば良くね？」「○○じゃダメなの？」等）を提示した場合、メインは計画を更新する**前に**、必ず以下のフォーマットで別案の解釈をユーザーに確認する:

  ```
  ## 別案の字義解釈確認

  ご提示の別案を字義通りに解釈すると以下と理解しました:
  - 範囲: [ユーザー発話に明示的に含まれている要素のみを抽出]
  - 変更対象: [字義通りに読んで変更すべき箇所]
  - 変更しない対象: [字義範囲外で「既存案のまま」と推測される箇所]

  拡張解釈の可能性: [推論で拡張すれば含まれうる別軸・別箇所を列挙。なければ「なし」]

  この理解で正しいですか？
  - (A) 字義解釈どおりで進める
  - (B) 拡張解釈の○○も含めて進める（複数あれば番号で選択）
  - (C) さらに別の意図がある（自由記述）
  ```

  - これは global `AGENTS.md (shared SSOT)` の「### ユーザー発話の字義範囲解釈」と対になる予防ゲート。SKILL 側で「字義範囲を超える別案解釈は必ず確認する」を強制する
  - 発火条件: ユーザー回答が「別案」「自由記述による方針提示」「疑問形での代替案提示」（「○○すれば良くね？」「○○じゃダメなの？」「○○で完結すれば？」等）を含むとき
  - 字義通りに読んでも 1 案に確定する場合（複数の解釈余地がない明確な指示）はこの確認をスキップしてよい。ただしスキップ判断は保守的に倒す（迷ったら確認する）
  - 確認結果は `{RUN_DIR}/user-decisions.md` に「別案の字義解釈確認: [選択結果と解釈差分]」として追記する
  - ユーザー確定後に、確認結果を記録してから `plan.md` の影響するセクションだけを増分更新する。確定前に計画を更新してはならない（過剰解釈による既存計画の破棄を防ぐ）
- **既存 plan 提示後の方針変更時の追加確認（必須）**: 既存 plan.md を提示した後に方針変更が発生した場合は、字義範囲を 3 軸（影響範囲・変更対象・既存維持対象）で明示的に切り分けて確認する。確認後は影響するセクションだけを増分更新し、完了済みの判断・ステップを保持する:

  ```
  ## plan.md 更新の真意確認

  現在の plan.md を提示しましたが、追加で以下の方針変更を読み取りました:
  - 字義通りの最小解釈: [ユーザー発話に明示的に含まれている要素のみを抽出]

  3 軸での具体案:
  - (A) 影響範囲のみ縮小: [変更対象は現在の plan.md と同じだが、影響範囲を○○に限定する案]
  - (B) 変更対象自体を別案に置換: [現在の plan.md の○○を△△に置き換える案。他要素は維持]
  - (C) 既存維持対象を増やす: [現在の plan.md では変更予定だった□□を「触らない」に変更する案]

  影響範囲の引用:
  - 現在の plan.md で変更予定だった箇所: [plan.md から該当行を引用]
  - 今回のご指示で「触らない」と読める箇所: [字義範囲を超える解釈を避けて明示]

  どれで進めますか？（A / B / C / 自由記述）
  ```

  - 発火条件: plan.md 提示後にユーザーが (i) 別案を提示 (ii) plan.md の特定箇所への異議を示した (iii) 「やっぱり○○じゃね？」等で方針変更を示唆した — のいずれか
  - 3 軸（影響範囲・変更対象・既存維持対象）の少なくとも 2 軸で字義解釈の余地がある場合は本ルールが優先発火する。1 軸のみなら従来サブルール（別案の字義解釈確認）でカバーされるため本ルールはスキップしてよい
  - 確認結果は `{RUN_DIR}/user-decisions.md` に「plan.md 更新の真意確認: [選択結果 (A/B/C/自由記述) と 3 軸での解釈差分]」として追記する
  - ユーザー確定後に `plan.md` の影響するセクションだけを増分更新する。計画全体を破棄・再作成してはならない
- 該当トリガーがどれも当てはまらない場合（明確に単一案で進むプラン）は本ステップをスキップしてステップ 5 へ
