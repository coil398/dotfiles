# 深掘りチャット

`/chat <問い>` が明示されたときに、表面的な短答で終わらず、ユーザーが判断または実行できるところまで答える。質問の深さは内容とユーザーの指定に合わせる。

## 調べる範囲

- 現在のversion、仕様、価格、release、news、比較など変わりうる事実は、公式一次情報を確認する。
- URLや特定documentを示された場合は、その内容を直接確認する。
- repositoryやユーザー環境が答えを変える場合だけ、関連fileや設定を確認する。無関係なdotfiles・OS・履歴を毎回探索しない。
- ライブラリの採用・更新・置換判断は `tech-validator` を使う。単一の公式document確認や小さなlocal調査は、メインClaudeが直接行ってよい。
- 独立した複数領域を並列に調べる価値がある場合だけAgentへ分ける。固定数のAgentや全source種別を要求しない。

確認できない事実を推測で埋めない。公式資料と実装が食い違う場合は、確認した範囲、現在の観測、残る不確実性を分ける。

## 回答

結論を先に置き、その判断に必要な根拠、具体例、tradeoff、次の行動を続ける。次の要素は、問いに役立つ場合だけ使う。

- 比較対象が複数あるときの表
- 実装や設定を説明するときのcode例
- 失敗しやすい手順のtroubleshooting
- ユーザーの実環境に関係する補足
- 確認に使ったURLまたはlocal file

固定見出し、固定文字数、補足の個数を完了条件にしない。単一事実は簡潔に答え、設計・比較・How-toは必要なだけ詳しくする。「短く」「要点だけ」などの指定を優先する。

一般論だけで結論を避けず、条件によって答えが分かれるなら主要な分岐を具体化する。質問に必要な前提が足りない場合は、独立して確認できる範囲を調べたうえで、結論を変える不足だけを尋ねる。
