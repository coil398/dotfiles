# ブレインストーミング

**テーマ**: $ARGUMENTS

要件と設計判断を対話で具体化する。standalone起動では、設計が合意されるまでコードを変更しない。親workflowから呼ばれた場合は、決定事項を親へ返し、親の継続条件に従う。

## 1. 必要なcontext

ユーザーが既に示した目的、制約、決定事項を整理する。既存repositoryの構造や先例が判断を変えるときだけ調べる。

- pathが既知の小さな確認は直接行う。
- 独立した複数領域の探索が役立つ場合だけ `explorer` へ分ける。
- 新規構造を提案する場合は同一layerの既存形を確認し、逸脱があれば差分と理由を示す。
- 最新仕様やlibrary選定が必要なら、適切な公式資料または `tech-validator` を使う。

## 2. 未決事項

実装方針を変える不足だけを質問する。質問は関連するものをまとめ、ユーザーが答えやすい粒度にする。既に答えがあること、実装時にrepositoryから決められる詳細、小変更に不要な将来要件は聞かない。

確認候補:

- 達成したい結果と対象利用者
- scopeと明示的な非対象
- 外部interface・互換性・data migration
- 受入条件とmaterialなtradeoff

## 3. 選択肢

複数の成立するapproachがある場合だけ、2〜3案を比較する。各案には次を添える。

- 仕組みと変更範囲
- 既存patternとの整合
- 利点、失うもの、可逆性
- 推奨案と理由

既存patternに沿う案が成立するなら比較に含める。将来の可能性だけを理由に大きな構造を選ばない。ユーザーが既に方針を決めている場合は、採用不能な案を形式的に並べない。

## 4. 設計の確定

選ばれたapproachについて、実装に必要な範囲でarchitecture、interface、data flow、error handling、verificationを具体化する。複数Agentやcomponentが関わる場合は、起動責任、resource所有、依存関係を明記する。

決定同士の矛盾、scope膨張、隠れた前提、既存機能への影響を確認する。懸念が結論を変える場合だけユーザーへ戻す。

## 5. 出力

合意した設計、保留事項、実装時の受入条件を簡潔に返す。文書保存を依頼された場合、または再開・共有に具体的な価値がある場合だけ、projectの既存配置へ保存する。保存先を固定の `docs/brainstorm/` に決め打ちせず、repository規約を優先する。

親workflowから呼ばれた場合は、親が次工程へ進める形式で返し、standalone時は次に実行できる作業を示して終了する。
